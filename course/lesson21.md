# 第 21 课：GPU 芯片架构——给自家芯片写编译器前，先把它拆开

> 本课风格：逐部件拆解 + "编译器为什么关心它" + 概念配实例。
> 目的：自研 GPU 工具链的第一步，是把芯片架构变成"编译器能决策的变量"。
> 前置：第 15 课（硬件基础）、第 11 课（调度）。

---

## 1. 一句话：GPU 和 CPU 的差别，就是"分工"不同

```
CPU: 少量强大的核, 每个核都能跑复杂逻辑、乱序执行、大缓存
GPU: 大量简单的小核, 牺牲"单个核智能", 换"成千上万个核同时算"
```

**代价**：GPU 的"小核"不会乱序、没有大缓存、分支处理能力弱。
这意味着：**怎么把这些小核用好，全压在编译器肩上**——
这正是 GPU 编译器比 CPU 编译器"难且重要"的原因。

---

## 2. GPU 的核心组织：SM（Streaming Multiprocessor，流式多处理器）

现代 GPU 内部是一堆 SM（NVIDIA 叫 SM，AMD 叫 CU）。每个 SM 是一个"小集群"：

```
一个 SM 内部:
├── 几十个 CUDA 核 (FP32/INT32 计算单元)
├── 几个 warp 调度器 (调度 warp 执行)
├── 寄存器文件 (register file, 256KB 左右)
├── 共享内存 (shared memory, 几十 KB ~ 几百 KB)
├── L1 缓存
├── 张量核 (Tensor Core, 大矩阵乘加速单元)
└── SFU (特殊函数单元, sin/exp 等)
```

**编译器视角**：SM 是"调度资源"的单位。你写的每个线程块（block）会被
分到某个 SM 上执行。SM 里的寄存器和共享内存，决定了**一个 block 能有多大、
能放多少线程**——这叫**占用率（occupancy）**，是 GPU 性能的头号敌人。

---

## 3. SIMT 执行模型：32 个线程"锁步"执行（warp）

### 3.1 warp：GPU 的执行单位

GPU 不是按"线程"调度的，是按 **warp（32 个线程一组）**调度的。
同一个 warp 里的 32 个线程**同一条指令同时执行**（SIMT：单指令多线程）。

```
warp 执行: 32 个线程走同一条指令
  - 读内存:  一起读(最好读连续地址)
  - 算:      一起算
  - 写内存:  一起写
```

**这直接决定了两个编译器优化**：

### 3.2 合并访问（Coalescing）

如果一个 warp 的 32 个线程访问**连续的内存地址**，硬件把 32 次访问
**合并成一次内存事务**（省 32 倍带宽）。如果访问地址分散，
硬件只能一个一个来，性能暴跌 32 倍。

**编译器要做的事**：调度循环让"相邻线程读相邻地址"。
第 11 课的 `reorder`/`tile` 在 GPU 上很大一部分就是为了合并访问。

### 3.3 分支发散（Branch Divergence）

warp 里 32 个线程执行**同一个指令**。如果出现 `if/else`：

```c
if (tid % 2 == 0) { /* A */ } else { /* B */ }
// warp 里一半线程要走 A, 一半要走 B
```

硬件会**串行执行两个分支**（先执行 A 的一半，再执行 B 的一半），
而不是并行——性能减半。这就是**分支发散**。

**编译器对策**：
- **predication（谓词执行）**：把分支变成"每条指令带一个布尔开关"，避免真分支
- **重排循环**：让同 warp 的线程尽量走同一路径
- **编译期提示**：告诉编译器分支大概率同向

## 4. 内存层次（GPU 版）：寄存器 → 共享内存 → 全局内存

第 15 课讲过 CPU 的层次，GPU 的层次**更极端、更需要编译器手工管**：

| 层 | 大小（每 SM） | 延迟 | 谁管 |
|---|---|---|---|
| 寄存器 | ~64K 个 | 0 周期 | 编译器分配 |
| 共享内存 | ~100KB | ~30 周期 | **显式分配**（要代码里写） |
| L2 缓存 | 几 MB | ~200 周期 | 硬件自动 |
| 全局内存(HBM/GDDR) | 几十 GB | ~400 周期 | 编译器决定搬几次 |

**关键区别**：共享内存（shared memory）是**程序可见、显式分配**的——
不像缓存"硬件自动管"。你要在 kernel 里写 `__shared__` 才能把数据放上去。
编译器要么替你加（自动），要么生成对应的访问代码。

**编译器的核心权衡**（第 13 课 meta_schedule 的搜索空间就在这里）：
- 数据放共享内存：快但容量小，还得手动搬
- 数据放全局内存：慢但不用搬

**分块（tiling）** 的真正意义：把一块数据搬进共享内存，让 32 个线程
在共享内存里反复用，不用每次都去全局内存。

## 5. 张量核（Tensor Core）：专门为大矩阵乘设计的硬件

现代 GPU 里有专门做矩阵乘加（MMA）的单元：

```
Tensor Core: 一条指令完成一个小矩阵乘加 (如 16x16x16 fp16)
```

**编译器要做的事**：
1. **识别**：发现"这是一段大矩阵乘"
2. **切分**：把大矩阵切成张量核能吃的 tile（如 16×16×16）
3. **生成**：生成 `mma.sync` / `wmma` 指令
4. **调度**：配好寄存器/共享内存让张量核不停转

这就是为什么 cuBLAS/CUTLASS 对 AI 这么重要——张量核的优化是
"GPU 性能的天花板"。TVM 可以集成 CUTLASS（第 7 课 BYOC），
就是因为手写张量核优化太难了。

---

## 6. 占用率（Occupancy）：最常被忽视、最影响性能的指标

### 6.1 定义

```
占用率 = 活跃 warp 数 / SM 能容纳的最大 warp 数
```

SM 的 warp 上限由**寄存器和共享内存**限制。例子：
- 一个 SM 有 64K 寄存器，你的 kernel 每个线程用 128 个寄存器
- 一个 warp = 32 线程 → 每 warp 用 4096 个寄存器
- SM 能放 64K/4096 = 16 个 warp
- 如果 SM 理论最大 64 warp，你的占用率 = 16/64 = 25%

### 6.2 为什么占用率低 = 慢

GPU 用"多 warp 并行"来**隐藏内存延迟**：一个 warp 等内存时，
切换到另一个 warp 继续算。占用率太低 → 没几个 warp 可切换 →
等内存时就真的停了。**编译器的任务：让占用率够高，同时不溢出资源。**

## 8. FAQ

**Q：为什么 GPU 用 warp 而不是线程调度？**
A：硬件上 warp 更省控制逻辑（一个指令译码器管 32 个核）。
代价是 warp 内锁步执行（分支发散）。

**Q：共享内存和缓存什么区别？**
A：缓存是硬件自动管的（你不知道里面有什么）；共享内存是**程序显式分配**的
（你决定放什么）。编译器要么帮你放，要么生成显式搬运代码。

**Q：张量核是不是只能跑矩阵乘？**
A：主要是矩阵乘加（MMA）。任何能化成矩阵乘加的计算（conv → GEMM，
第 20 课 im2col！）都能用张量核。

**Q：占用率是不是越高越好？**
A：不是。资源有限时，太高会挤压每个 warp 的寄存器/共享内存，
反而变慢。要平衡（第 13 课 meta_schedule 的搜索空间就在这里）。

## 9. 本课小结

- GPU = 大量小核的并行机器，SIMT（warp 锁步执行）
- SM 是资源单位：寄存器、共享内存、warp 数
- **合并访问**：32 个相邻线程读相邻地址 → 省 32 倍带宽
- **分支发散**：warp 内分歧会串行执行 → 编译器用 predication 缓解
- **共享内存**：显式分配、手动搬、比缓存快 → 分块的目的
- **张量核**：矩阵乘加专用单元 → CUTLASS / 大 GEMM 的天花板
- **占用率**：资源占用 vs 延迟隐藏的权衡，GPU 性能的头号指标
