# 第 21 课：GPU 芯片架构——给自家芯片写编译器前，先把它拆开

> 本课风格：逐部件拆解 + "编译器为什么关心它" + 概念配实例。
> 目的：自研 GPU 工具链的第一步，是把芯片架构变成"编译器能决策的变量"。
> 前置：第 15 课（硬件基础）、第 11 课（调度）。

---

## 1. 一句话：GPU 和 CPU 的差别，就是"分工"不同

```
CPU: 少量强大的核, 每个核都能跑复杂逻辑、乱序执行、大缓存
GPU: 大量简单的小核, 牺牲"单个核智能", 换"成千上万个核同时算"
```

**代价**：GPU 的"小核"不会乱序、没有大缓存、分支处理能力弱。
这意味着：**怎么把这些小核用好，全压在编译器肩上**——
这正是 GPU 编译器比 CPU 编译器"难且重要"的原因。

---

## 2. GPU 的核心组织：SM（Streaming Multiprocessor，流式多处理器）

现代 GPU 内部是一堆 SM（NVIDIA 叫 SM，AMD 叫 CU）。每个 SM 是一个"小集群"：

```
一个 SM 内部:
├── 几十个 CUDA 核 (FP32/INT32 计算单元)
├── 几个 warp 调度器 (调度 warp 执行)
├── 寄存器文件 (register file, 256KB 左右)
├── 共享内存 (shared memory, 几十 KB ~ 几百 KB)
├── L1 缓存
├── 张量核 (Tensor Core, 大矩阵乘加速单元)
└── SFU (特殊函数单元, sin/exp 等)
```

**编译器视角**：SM 是"调度资源"的单位。你写的每个线程块（block）会被
分到某个 SM 上执行。SM 里的寄存器和共享内存，决定了**一个 block 能有多大、
能放多少线程**——这叫**占用率（occupancy）**，是 GPU 性能的头号敌人。

## 3. SIMT 执行模型：32 个线程"锁步"执行（warp）

### 3.1 warp：GPU 的执行单位

GPU 不是按"线程"调度的，是按 **warp（32 个线程一组）**调度的。
同一个 warp 里的 32 个线程**同一条指令同时执行**（SIMT：单指令多线程）。

```
warp 执行: 32 个线程走同一条指令
  - 读内存:  一起读(最好读连续地址)
  - 算:      一起算
  - 写内存:  一起写
```

**这直接决定了两个编译器优化**：

### 3.2 合并访问（Coalescing）

如果一个 warp 的 32 个线程访问**连续的内存地址**，硬件把 32 次访问
**合并成一次内存事务**（省 32 倍带宽）。如果访问地址分散，
硬件只能一个一个来，性能暴跌 32 倍。

**编译器要做的事**：调度循环让"相邻线程读相邻地址"。
`reorder`/`tile` 这两个调度原语在 GPU 上很大一部分就是为了合并访问。

> **手算：合并访问 vs 分散访问，一笔账看清 32 倍从哪来**
>
> 一个 warp = 32 线程，每个线程读一个 float（4 字节），地址连续：
> - **合并后**：32 × 4 = 128 字节落在同一个 cache line 内，硬件**一次内存事务**
>   就把整块搬回来，所有线程同时拿到。
> - **分散后**：32 个地址散落在内存各处，硬件要**32 次独立事务**，
>   每次都搬一个 128 字节的缓存行，但只用其中 4 字节——**94% 的带宽被浪费**。
>
> 带宽受限时，同样一块数据：
> - 合并：`总字节 / 带宽` 一次传完
> - 分散：同样的字节数被拆成 32 笔小账，主存命中率骤降，
>   实际耗时接近 **32 倍**
>
> **编译器怎么保证合并？** 看线程索引怎么映射到地址：
> ```c
> // 好: 线程号连续 → 地址连续 (合并)
> a[tid]  = ...
> // 坏: 线程号连续 → 地址隔行 (不合并)
> a[tid * 32] = ...
> ```
> 所以 GPU 后端在生成代码时，**第一条规则就是
> "让最内层循环的线程号=地址的最后一个维度"**。看懂这一条，
> GPU 后端的代码就懂了一半。

### 3.3 分支发散（Branch Divergence）

warp 里 32 个线程执行**同一个指令**。如果出现 `if/else`：

```c
if (tid % 2 == 0) { /* A */ } else { /* B */ }
// warp 里一半线程要走 A, 一半要走 B
```

硬件会**串行执行两个分支**（先执行 A 的一半，再执行 B 的一半），
而不是并行——性能减半。这就是**分支发散**。

**编译器对策**：
- **predication（谓词执行）**：把分支变成"每条指令带一个布尔开关"，避免真分支
- **重排循环**：让同 warp 的线程尽量走同一路径
- **编译期提示**：告诉编译器分支大概率同向

## 4. 内存层次（GPU 版）：寄存器 → 共享内存 → 全局内存

CPU 的内存层次也是这么几层，GPU 的层次**更极端、更需要编译器手工管**：

| 层 | 大小（每 SM） | 延迟 | 谁管 |
|---|---|---|---|
| 寄存器 | ~64K 个 | 0 周期 | 编译器分配 |
| 共享内存 | ~100KB | ~30 周期 | **显式分配**（要代码里写） |
| L2 缓存 | 几 MB | ~200 周期 | 硬件自动 |
| 全局内存(HBM/GDDR) | 几十 GB | ~400 周期 | 编译器决定搬几次 |

**关键区别**：共享内存（shared memory）是**程序可见、显式分配**的——
不像缓存"硬件自动管"。你要在 kernel 里写 `__shared__` 才能把数据放上去。
编译器要么替你加（自动），要么生成对应的访问代码。

**编译器的核心权衡**：
- 数据放共享内存：快但容量小，还得手动搬
- 数据放全局内存：慢但不用搬

**分块（tiling）** 的真正意义：把一块数据搬进共享内存，让 32 个线程
在共享内存里反复用，不用每次都去全局内存。

#### 共享内存的"库里"：bank conflict（最容易被忽略的坑）

共享内存虽然快，但它被硬件切成很多个 **bank（内存库）**。

一个 warp（32 线程）同时访问共享内存时，硬件按 **地址 → bank 编号** 切分，
一次周期内**每个 bank 只能服务一个地址**（约 32 个 bank，每 4 字节一个）。

```
例: 32 个线程同时读 s_mem[i]
    - 如果 i 是 0,1,2,...,31  (每个都落在不同 bank)  → 一次完成, 快
    - 如果 i 是 0,32,64,...   (全落在 bank 0)       → 撞车: 拆 32 次, 慢 32 倍
```

**这就是 bank conflict（库冲突）**：多个线程访问同一个 bank，硬件只能
串行，一次变多次。它和"合并访问"是镜像关系：
- **全局内存看合并访问**：32 线程读相邻地址 = 快
- **共享内存看 bank**：32 线程读"阶梯错开"的地址 = 快，
  读同样的地址反而 **没有** conflict（广播），读刚好错开 32 的倍数才撞

**编译器对策**：
- 给共享内存数组**垫 padding**（每行多开 1 个元素），把"步长 32"变成"步长 33"
- 或**重排索引**，让同一周期访问的地址散布到不同 bank
- 这是写 kernel 和做调度搜索时一定会遇到的取舍

> 一句话区分：**合并访问 = 全局内存的带宽**；**bank = 共享内存的带宽**。
> 你自研的 profiler 要把"bank conflict 次数"当作一个指标暴露出来。

## 5. 张量核（Tensor Core）：专门为大矩阵乘设计的硬件

现代 GPU 里有专门做矩阵乘加（MMA）的单元：

```
Tensor Core: 一条指令完成一个小矩阵乘加 (如 16x16x16 fp16)
```

**编译器要做的事**：
1. **识别**：发现"这是一段大矩阵乘"
2. **切分**：把大矩阵切成张量核能吃的 tile（如 16×16×16）
3. **生成**：生成 `mma.sync` / `wmma` 指令
4. **调度**：配好寄存器/共享内存让张量核不停转

这就是为什么 cuBLAS/CUTLASS 对 AI 这么重要——张量核的优化是
"GPU 性能的天花板"。TVM 可以通过 BYOC 机制集成 CUTLASS，
就是因为手写张量核优化太难了。

## 6. 占用率（Occupancy）：最常被忽视、最影响性能的指标

### 6.1 定义

```
占用率 = 活跃 warp 数 / SM 能容纳的最大 warp 数
```

SM 的 warp 上限由**寄存器和共享内存**限制。例子：
- 一个 SM 有 64K 寄存器，你的 kernel 每个线程用 128 个寄存器
- 一个 warp = 32 线程 → 每 warp 用 4096 个寄存器
- SM 能放 64K/4096 = 16 个 warp
- 如果 SM 理论最大 64 warp，你的占用率 = 16/64 = 25%

### 6.2 为什么占用率低 = 慢

GPU 用"多 warp 并行"来**隐藏内存延迟**：一个 warp 等内存时，
切换到另一个 warp 继续算。占用率太低 → 没几个 warp 可切换 →
等内存时就真的停了。**编译器的任务：让占用率够高，同时不溢出资源。**

> **手算：到底要多少个 warp 才"够用"？——延迟隐藏的量化**
>
> 设你的芯片：内存请求**延迟 600 周期**，kernel 中每个 warp
> 平均每 60 条指令访问一次内存。
>
> ```
> 需要的 warp 数 = 内存延迟 / 两次访存之间的计算量
>                = 600 / 60 = 10 个 warp
> ```
>
> 含义：
> - 占用率 **25%（16/64 warp）**：10 个 warps 工作、6 个等待 →
>   延迟 100% 被隐藏，性能不损。
> - 把这个 kernel 改成"寄存器分块"的微内核写法，
>   每 warp 的寄存器从 32 涨到 128 → 占用率掉到 25%，
>   但访存间隔从 60 条变成 600 条 → 只要 1 个 warp 就够 →
>   **占用率 25% 照样满速**。
>
> **为什么 NVIDIA 官方工具说"够用即可"**：占用率的目标不是 100%，
> 是**足够隐藏延迟**。同一块芯片、同一个 kernel，编译器里
> "寄存器分配 / tile 大小 / 每线程工作量"三者的组合，
> 才是真正的决定因素。

## 7. 新一代 GPU 的关键特性（Hopper/Blackwell 时代，会议室必考）

前面 1~6 节是"通用 SIMT 架构"（Volta~Ampere 就成型了）。
Hopper（2022）/Blackwell（2024）加了四样东西，每一个都对应
你学过的某个瓶颈：

### 7.1 TMA（Tensor Memory Accelerator）：专职搬运工

```
以前: 数据从 HBM → SM 共享内存, 要 SM 的指令流水"一句一句搬"
现在: TMA 是独立 DMA 引擎: 给描述符(源地址/tile形状/目标), 硬件整块搬
      SM 的指令流水完全解放, 还能和计算异步重叠
```

**对照第 30 课**：TMA 就是"kernel 内部的命令队列+DMA"——
门铃/描述符/异步完成通知，一套微缩版。编译器的变化：TIR 的
`cache_read` 从"生成搬运指令"变成"生成 TMA 描述符"。

### 7.2 线程块集群（Cluster）：比 block 大、比 grid 小的新一层

```
以前: block 之间不能通信(只能通过全局内存)
现在: 一个 cluster = 最多 8~16 个 block, 可以互访彼此的共享内存
      (distributed shared memory), 还有 cluster 级 barrier
```

**为什么重要**：tile 可以切得比"一个 SM 的共享内存"更大——
跨 block 复用数据不走 HBM。原来 tile 的约束（tile ≤ 一个
SM 的 smem）被放宽成"tile ≤ 一个 cluster 的总 smem"。

### 7.3 warp specialization：生产者-消费者分工

```
以前: 一个 warp 既搬数据又计算(软件流水自己排)
现在: 一些 warp 专职"生产"(TMA 搬进 smem), 一些 warp 专职"消费"(张量核算)
      硬件队列衔接 → 延迟隐藏不再靠"多 warp 轮转", 靠角色分工
```

**对照第 6 节**：占用率模型从"多少个 warp 藏延迟"变成"生产线
配速"——这是 FlashAttention-3、cuBLAS 在 Hopper 上提速的主因。

### 7.4 FP8 与精度阶梯（硬件侧）

```
fp64 → fp32 → tf32 → fp16/bf16 → fp8(E4M3/E5M2) → int8/int4
算力:   1    2     4      8         16(相对 fp64 每档翻倍)
```

H100 的 FP8 张量核算力是 FP16 的 2 倍；Blackwell 再加 FP4。
**每一代新卡的"算力翻倍"，一半来自新精度格式**——编译器要会
按格式分发 kernel。

## 9. 课后答疑

**Q：为什么 GPU 用 warp 而不是线程调度？**
A：硬件上 warp 更省控制逻辑（一个指令译码器管 32 个核）。
代价是 warp 内锁步执行（分支发散）。

**Q：共享内存和缓存什么区别？**
A：缓存是硬件自动管的（你不知道里面有什么）；共享内存是**程序显式分配**的
（你决定放什么）。编译器要么帮你放，要么生成显式搬运代码。

**Q：张量核是不是只能跑矩阵乘？**
A：主要是矩阵乘加（MMA）。任何能化成矩阵乘加的计算（conv 经 im2col 化成 GEMM）都能用张量核。

**Q：占用率是不是越高越好？**
A：不是。资源有限时，太高会挤压每个 warp 的寄存器/共享内存，
反而变慢。要平衡。

## 10. 本课小结

- GPU = 大量小核的并行机器，SIMT（warp 锁步执行）
- SM 是资源单位：寄存器、共享内存、warp 数
- **合并访问**：32 个相邻线程读相邻地址 → 省 32 倍带宽
- **bank conflict**：共享内存读"步长 32"撞库 → 拆多次，垫 padding 解决
- **分支发散**：warp 内分歧会串行执行 → 编译器用 predication 缓解
- **共享内存**：显式分配、手动搬、比缓存快 → 分块的目的
- **张量核**：矩阵乘加专用单元 → CUTLASS / 大 GEMM 的天花板
- **占用率**：资源占用 vs 延迟隐藏的权衡，GPU 性能的头号指标

## 扩展阅读：GPU 架构的三个进阶问题

### A. 为什么 SM 里要分 warp 调度器？

一个 SM 有几十个核、64 个 warp。如果只有一个调度器，它每周期只能
发射一个 warp——其它 warp 就干等。**多个 warp 调度器让 SM 每周期能
同时推进多个 warp**，这才是"延迟隐藏"的硬件基础。

### B. 张量核为什么只支持特定尺寸（如 16x16x16）？

因为张量核是**硬件写死的矩阵乘单元**——它的寄存器布线、数据通路
都是按固定尺寸优化的。**编译器的活就是把任意矩阵乘"切"成张量核能吃的块**。
这就是为什么调度里"tile 到 16 的倍数"这么常见。

### C. bank conflict 和合并访问，本质是一回事吗？

是同一思想的两面：**让硬件"一次取到的数据"正好是你"一次要用的"**。
全局内存按 cache line 取 → 要连续（合并访问）；
共享内存按 bank 取 → 要错开（避免撞库）。
**核心都是"顺着硬件的取数方式安排数据"**。
