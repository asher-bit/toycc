# 第 22 课：GPU 编译器特有技术——给 SIMT 硬件写编译器和给 CPU 不一样

> 本课风格：从"给 CPU 编译"出发，逐步讲清"给 GPU 编译"多出来的难题。
> 对应代码：第 14 课 PTX 示例、第 15 课硬件模型。
> 前置：第 21 课（GPU 架构）、第 7 课（codegen）。

## 1. 为什么给 GPU 编译，比给 CPU 编译多一重复杂度

给 CPU 编译，你面对的是"一个顺序执行的核"——只要选好指令、分好寄存器。
给 GPU 编译，你面对的是"成千上万个小核同时执行"——你要额外处理：

1. **SIMT 语义**：32 个线程锁步执行，编译器要保证"锁步是安全的"
2. **海量线程**：线程数/块数/共享内存/寄存器的分配是**编译期决策**
3. **内存分层显式化**：共享内存不是缓存，要显式搬
4. **指令调度更敏感**：GPU 核更"笨"，指令顺序影响性能更大
5. **PTX → SASS 还有一层**：PTX 是"虚拟汇编"，真正跑的是 SASS（厂商私有）

## 2. SIMT 编译：让"锁步执行"变安全

### 2.1 SIMT 的核心约束

同一个 warp 的 32 个线程执行**同一条指令**。这意味着：

```
合法:  所有线程做同样的事 (比如 all: c[i] = a[i] + b[i])
危险:  线程间互相通信、分支分歧、共享内存的读写顺序
```

**编译器要验证和保证**：
- **一致性**：所有线程读/写共享内存的顺序要一致，否则数据竞争
- **同步点**：`__syncthreads()` 是 warp 内同步，但**编译器不能随意移动**它
- **分支**：如果两个分支各访问不同的共享内存，编译器要处理发散

### 2.2 Predication（谓词执行）：把分支变成"带开关的指令"

遇到 `if/else`，编译器有两条路：
- **真分支**：跳到不同地址（对 GPU 来说会发散）
- **predication**：每个线程带一个布尔位，一条指令同时执行两个分支，
  根据布尔位决定"实际写不写"

```
真分支:      if (cond) { A } else { B }
predication: A_if_cond; B_if_not_cond;   ← 一个 warp 同时算 A 和 B, 各写各的
```

**predication 避免了发散**，代价是"两个分支都算了一遍"。
分支越简单越适合 predication，复杂分支只能真分支。编译器要权衡。

> **原理深挖：predication 的本质是"用算力换掉串行"**
>
> 发散的本质是**串行化**：一个 warp 里 32 个线程被迫分成两波先后执行，
> 等效于"这个 warp 只干了一半活"。predication 的取舍很清晰：
>
> - **多算的一点**：两个分支都执行。若分支体很便宜（一次算术），
>   多算很少。
> - **省下的**：整段不再串行，warp 全体一步走完。
>
> 所以规则是"分支越简单越值得 predication"——因为**多算的成本**
> 和**分支体的复杂度**成正比，而**省下的串行**是固定的（一段 iff else
> 由 2 波变 1 波，最多省 2 倍）。简单分支多算 1 倍换省 2 倍，划算。
>
> **对编译器设计的启发**：决策不是"要不要发散"，而是**对比两条路的时间**。
> 这也是 TVM 的 `vectorize`（第 11 课）背后的同一个念头——把"多线程应做
> 相同的事"当作默认前提，然后用编译器安排把代价最小化。
>
> **一句话记住**：GPU 上最贵的不是"多算一点"，是"串行等待"。
> 编译器的一切花招（predication、重排线程、合并访问）都是
> 在减少"串行等待"。

### 2.3 发散处理

第 21 课讲过的分支发散，编译器可以**重排**让同 warp 线程尽量走同一路径。
比如把 `if (tid % 2 == 0)` 改成 `if (tid < 16)`（同 warp 全走一侧）。
这叫"线程编号重排"，是 GPU 编译器的常见优化。

## 3. PTX → SASS：两层汇编，两层优化

### 3.1 为什么有两层

```
CUDA C++ / 你的代码
  ↓
PTX (Parallel Thread Execution)   ← NVIDIA 定义的"虚拟汇编", 向前兼容
  ↓ ptxas (NVIDIA 的汇编器)
SASS (Shader Assembly)            ← 真实机器码, 绑定具体 GPU 架构
  ↓
GPU 执行
```

**为什么中间有个 PTX？**
- 你在 PTX 层写代码，NVIDIA 每代 GPU 出新的 SASS 时，
  PTX 层不用变（兼容）
- 编译器在 PTX 层做"平台无关"的优化
- ptxas 在 SASS 层做"平台相关"的优化（寄存器分配、指令选择）

### 3.2 PTX 层编译器干什么

PTX 层（NVPTX）做：
- 寄存器虚拟化（虚拟寄存器）
- SIMT 语义的初步处理
- 指令调度（重排指令减少依赖/stall）
- 向量化（如果目标指令集支持）

### 3.3 SASS 层 ptxas 干什么

SASS 层（ptxas）做"最后一步"：
- **真寄存器分配**：把虚拟寄存器映射到物理寄存器（考虑溢出）
- **指令选择**：选哪条指令（不同的指令延迟/吞吐不同）
- **指令调度**：重排指令以充分利用流水线、隐藏延迟
- **占用率计算**：根据寄存器/共享内存用量算 SM 能放几个 warp

**对你的启示**：自研 GPU 如果也想复用这套，可以：
- 出一个"类 PTX"的中间层 + 自己的 ptxas
- 或直接写 SASS 层（但更复杂）

## 4. 指令调度：GPU 上比 CPU 更敏感

CPU 有乱序执行（OOO）引擎，硬件自动重排指令。GPU **基本顺序执行**，
靠**多 warp 并行**隐藏延迟。所以指令的顺序直接决定性能：

```
坏:   load A[i]      ← 等内存 400 周期
      c[i] = A[i]*2  ← 这 400 周期在干等
好:   load A[i]
      load A[i+1]    ← 提前发起下一个 load
      c[i] = A[i]*2  ← 利用等待时间
```

**编译器的工作**：把"访存"提前、"计算"推后，让等待时间被其它 warp 填满。
这在 GPU 上比 CPU 关键得多——因为 GPU 没有硬件自动重排。

**相关术语**：指令调度（instruction scheduling）、双发射（dual-issue，
一条指令同时发射两条）、延迟隐藏（latency hiding，用并行 warp 盖住访存延迟）。

## 5. 占用率计算：编译器必须算出来

第 21 课讲了占用率。编译器在**编译期**就要算出占用率：

```
每 SM 可用寄存器 / 每 warp 需要寄存器 = 该 SM 能放几个 warp
每 SM 共享内存 / 每 block 需要共享内存 = 能放几个 block
```

**编译器要做的权衡**：
- 每个线程多用寄存器 → 每个 warp 快，但 SM 装的 warp 少 → 占用率低
- 占用率太高 → 寄存器溢出（spill），反而慢

**这就是为什么 meta_schedule 的搜索空间里有一项"线程数/块大小"**——
它在搜占用率的最佳平衡点。

## 6. 自研 GPU 时，编译器后端要回答的问题

给自家芯片写编译器后端（第 7 课 run_codegen.cc 的 `relax.ext.<target>`），
你要回答这些问题：

| 问题 | 怎么回答 |
|---|---|
| 有多少 SM/核？ | target 描述里写 |
| 每核多少寄存器/共享内存？ | target 描述里写 |
| 向量宽度？ | 决定向量化参数 |
| 指令集是什么？ | 写指令选择映射（TIR → 你的指令） |
| 内存层次？ | 决定 cache_read/shared_memory 策略 |
| 线程模型？ | 决定 bind 怎么映射（blockIdx/threadIdx） |

**这就是第 15 课 `hardware.py` 的 LATENCY/容量表在真实编译器里的角色**：
target description 就是这些数字。

## 8. FAQ

**Q：GPU 编译器里最重要的事是什么？**
A：三件事：① 合并访问（带宽）② 占用率（隐藏延迟）③ 不溢出资源（寄存器/共享内存）。
这三件事是相互矛盾的，编译器就是在它们之间做平衡。

**Q：PTX 和 SASS 的关系，像不像 MLIR 的方言下降？**
A：完全同构——PTX 是高层方言，SASS 是低层方言，ptxas 是"下降"。
你第 14 课学的 MLIR 分层思想，NVIDIA 的 GPU 编译器就是这么干的。

**Q：predication 是不是所有分支都用？**
A：不是。简单分支用 predication（少发散），复杂分支（大段代码、
循环、函数调用）只能真分支。编译器评估后决定。

**Q：自研芯片要不要做"类 PTX"中间层？**
A：如果你想长期演进、兼容未来芯片，建议做（像 PTX 一样向前兼容）。
如果只是当前一代芯片，直接出最终指令更省事——但升级时痛苦。

## 9. 本课小结

- GPU 编译 = CPU 编译 + SIMT 语义 + 海量线程分配 + 显式内存分层
- SIMT 要处理：同步、predication、分支发散
- PTX→SASS 两层：中间层管"平台无关"，汇编器管"平台相关"
- 指令调度在 GPU 上比 CPU 更关键（无乱序执行引擎）
- 占用率是编译期就要算清的指标
- 自研芯片后端 = 回答一张"硬件特性表"

## 深层拓展：GPU 编译器的三个"为什么这么难"

### A. 为什么 SIMT 的"锁步"让编译器束手束脚？

CPU 编译器可以随便重排指令（反正乱序引擎会兜底）。
**SIMT 里 32 个线程共享一个指令流——你重排一条，所有线程都跟着动**。
如果两个线程对共享内存有依赖，你重排可能就引入了数据竞争。
这就是为什么 GPU 编译器的指令调度要**带"线程间依赖"的额外约束**。

### B. 为什么"寄存器分配"在 GPU 上是多目标优化？

CPU 上寄存器分配只要"装得下就行"。GPU 上：
- 寄存器用多了 → 每 warp 快，但 SM 装的 warp 少 → 占用率低
- 寄存器用少了 → 占用率高，但每 warp 慢
**这是一个"单 warp 速度 vs 并行 warp 数"的权衡**——没有标准答案，
只有"针对这个 kernel 的最优点"。这就是为什么第 13 课要 autotune。

### C. PTX 的"向前兼容"是怎么做到的？

NVIDIA 承诺"今天的 PTX，明天的 GPU 也能跑"。做法是：
PTX 只描述**抽象指令**，具体怎么映射到新硬件由 **ptxas（每代更新）**决定。
**这给了 NVIDIA 换硬件架构的自由，又不让用户改代码**——
你自研芯片如果想"长期演进"，值得学这一招。
