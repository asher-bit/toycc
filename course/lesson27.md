> 目的：搞懂"芯片流片前，编译器/kernel/调试器全跑在什么上"——**模拟器**。
> 前置：第 2 课（参考执行器）、第 15 课（硬件参数表）、第 24 课（工具链全景）。

## 1. 为什么模拟器是工具链的第一件交付物

自研芯片的残酷现实：**从立项到流片回片要 1~2 年**。期间编译器、
kernel 库、调试器、AI 框架适配——全都不能等。它们跑在什么上？

```
无芯片时代:  编译器 ──► 模拟器(Simulator) ──► 扮演"硬件"
有芯片时代:  编译器 ──► 模拟器 ──► (永久保留: 回归测试最快通道)
                        │
                     硬件(硅片) ──► 第一次"真机"验证
```

**模拟器 = ISA 规范的可执行版本**。芯片团队写 ISA 白皮书（文字），
模拟器团队把它翻译成代码（可执行的规范）。以后硬件实现的每一条
指令、编译器生成的每一段机器码，都以模拟器为对照基准。

> **关键认知**：工具链全景图画了 compiler/assembler/driver 一堆盒子，
> 但没画"这些盒子在流片前都要插在模拟器上"。模拟器是**最底下的地基**——
> 没有它，上面所有盒子都是空转。自研芯片团队通常**第一周就启动模拟器**。

**模拟器有三个层次，速度与精度互为代价**：

```
功能模型(ISS)   指令精确        ~10^7~10^8 条/秒   回答"对不对"
周期模型        周期精确(近似)  ~10^5~10^6 条/秒   回答"快不快"
RTL 仿真        时钟/信号精确   ~10^3~10^4 条/秒   回答"硬件电路对不对"
```

## 2. 功能模型（ISS）：只回答"对不对"

### 2.1 它做什么

ISS（Instruction Set Simulator）逐条执行 ISA 的**语义**，不管时序：
执行一条指令花几个周期、缓存有没有命中——一概不关心。
它只保证：寄存器值、内存值、异常行为 == 真实硬件。

```python
# toycc-ISA 的概念 ISS：只有两条指令 load_i / add
def run_iss(prog, mem0):
    regs = [0, 0, 0, 0]            # 4 个寄存器
    mem  = mem0.copy()
    pc   = 0
    while pc < len(prog):
        op, a, b, c = prog[pc]
        if   op == "load_i": regs[a] = b                       # 常数装入
        elif op == "add":   regs[a] = regs[b] + regs[c]
        else: raise ValueError(f"非法指令 {op} @ pc={pc}")
        pc += 1
    return regs, mem

prog = [("load_i", 0, 5, 0), ("load_i", 1, 7, 0), ("add", 0, 0, 1)]
print(run_iss(prog, {}))     # ([12, 7, 0, 0], {})
```

**两条物理事实**：
1. 解释器式 ISS 速度 ≈ 1e7~1e8 条/秒（这就是 `switch(op)` 分发循环）。
2. 真实 GPU kernel 动辄上千万条指令——全量跑 ISS 太慢，所以
   测试策略是"小 kernel 全跑、大 kernel 按边界抽跑"。

### 2.2 指令是有"副作用"的：异常路径别忘

新手写 ISS 只写正常路径。真实的芯片有：除零、越界、对齐错误、
非法指令——**模拟器必须连异常路径一起模拟**，否则编译器生成的
错误处理代码在模拟器上"测不出来"。

> **手算：为什么寄存器"回滚"这么难**
>
> 设指令 `add r0, r1, r2` 执行到一半发现 r2 是非法寄存器号。
> 真实硬件：异常的**原子性**由流水线保证（写回阶段才提交结果）。
> 你的模拟器呢？如果不小心先把 r0 写坏了再报异常，
> 调试器看到的状态就和真机不一致——**模拟器必须模拟"提交点"**。
> 这就是为什么 ISS 里每条指令都应该是：
> "先算出结果 → 检查异常 → 通过才写寄存器"。

## 3. 周期模型：回答"快不快"

编译器"优化对没对"要 ISS 判；"优化快不快"要**周期模型**判。
周期模型模拟真实硬件的资源：流水线阶段、寄存器堆端口、缓存、
带宽、warp 调度器、bank 冲突……

```
指令           ISS 输出               周期模型(5 级流水)
add r1,r2,r3   r1 = r2 + r3           取指→译码→发射→执行→写回
                                      (逐级推进, 每级 1 周期;
                                       还要看执行单元被谁占用)
```

> **手算：同一段代码，两个模型的"输出"完全不同**
>
> ```
> 代码:  load r0, [g]      add r1, r0, r0      store r1, [g]
>
> ISS 输出:    r1 = 2*g[0]              ← 只回答正确性
> 周期模型:    12 周期（示例值）         ← 回答性能
> ```
>
> 12 周期只是示例值，真实周期数按**依赖链最长的路径**推：发射 load 后
> 400 周期才返回，期间若能发射与 load 无关的独立指令，等待就被这些
> 指令填满；这里 add 依赖 load 的结果、store 依赖 add，没有独立指令
> 可填，只能干等——整条链串行到底，约 400 + 1 + 1 ≈ 402 周期。
> 周期模型输出的是这种逐周期推演，不是拍脑袋的数。
>
> 所以**基准测试（benchmark）永远跑在周期模型上**——这就是
> benchmark 方法论的"硬件前提"：没有真芯片时，roofline 分析的
> 实测点来自周期模型。硬件团队最怕"模型太乐观"，让编译器团队
> 拿着假的性能数据调一整年。

**精度与速度的取舍**：周期模型有两种做法——
- **解析式**（直接算：这个 kernel 的访存量 × 带宽 = 时间）：快，只会估"整体"
- **逐周期模拟**（每个周期推进流水线状态）：精确，但慢 2~4 个数量级

`hardware.py` 里的 LATENCY/带宽表 + 公式估算，就是**解析式
周期模型的雏形**——将来在模拟器上排 schedule 时用的就是它。

## 4. 差分测试：模拟器的"金标准"

模拟器自己怎么验证？——**差分测试（differential testing）**：

```
随机生成指令序列/测试程序
        │
        ▼
模拟器执行 ──┐
             ├──► 终态(寄存器+内存) 一致? ── 不一致 → 查到底谁错
独立参考实现 ┘   (真机 或 RTL试验台 或 另一人写的模拟器)
```

这就是"参考执行器 vs 被测对象"的方法论**原样搬到硬件层**：
做编译器时拿 numpy 参考执行器验证 pass；这里拿"参考模型"验证模拟器。
**两份独立实现**是关键——同一个人写的两份代码会犯同样的错。

> **手算：差分测试的覆盖率门禁**
>
> 假设你的 ISA 有 32 条指令。随机生成 1000 个程序，统计：
>
> ```
> 指令覆盖        32/32        ← 全覆盖(必过, 否则那 1 条没人敢用)
> 边界覆盖        load 地址=0 / 地址=最大 / 负数偏移
> 异常路径覆盖    除零 / 非法寄存器号 / 存储越界
> ```
>
> 覆盖率报告（coverage report）是模拟器团队每天看的数字。
> 覆盖率不到 100% 的那条指令——**编译器和硬件都不敢碰**。

**公司里的真实分工**：模拟器 bug → 全公司工具链全部受影响。
所以模拟器的 CI 通常配**每晚全量回归 + 覆盖率门禁**。

## 5. 模拟器与编译器怎么配合

```
编译器 ──► 目标文件(第29课) ──► 加载器 ──► 模拟器
                                            │
              └── 调试器(第24课) ◄── 断点/单步 ┘
```

1. **编译器喂**：把生成的二进制直接丢进模拟器跑；模拟器报错 = 编译器 bug
2. **调试器挂**：cuda-gdb 在真机上工作靠驱动暴露调试接口；
   调试器同样支持"模拟器后端"——没流片时模拟器就是你的"目标机"
3. **性能调优**：autotune 的 Runner 在流片前指向模拟器，
   数据库里的"该芯片最优参数"全是模型跑出来的；流片后重跑一遍校准

## 6. 课后答疑

**Q：为什么不直接用 RTL 仿真（Verilog testbench）当模拟器？**
A：速度差 3~4 个数量级。编译一个 kernel 的正常流程是分钟级，
RTL 仿真是小时级。**ISS 管日常开发速度，RTL 仿真管最终验收**。

**Q：模拟器要精确到什么程度才够用？**
A：分用途。**正确性测试用 ISS**（行为对就行）；
**性能/调度决策用周期模型**（行为对 + 时序近似）。
别让编译器团队对着 ISS 调性能——他们什么都调不出来。

**Q：模拟器 vs 真实硬件不一致时听谁的？**
A：回看 ISA 白皮书。白皮书说 A、模拟器实现 B → 改模拟器；
白皮书本身含糊 → 开"规范评审会"（模拟器/硬件/编译器三方），
**结论写进白皮书下一版**——这就是 ISA 规范迭代的真实机制。

**Q：为什么我们不用 QEMU 或 gem5 这类现成模拟器？**
A：可以起步。但它们模拟的是 CPU（qemu）/通用内核（gem5）。
GPU 的 warp/SIMT/共享内存/Tensor 单元没有通用模型——
**GPU 模拟器只能自己写**。gem5 之外有 GPGPU-Sim 这类研究用
GPU 模拟器（独立项目），但那是研究工具，商用自研芯片都要自研，
团队里一般有专职模拟器小组。

## 7. 本课小结

- **模拟器 = 流片前唯一的"硬件"**，工具链第一件交付物
- 三层模型：**功能模型(ISS)** 管对错，**周期模型**管快慢，**RTL** 管验收
- ISS 要模拟**异常路径 + 提交点**，否则调试器看到的状态是假的
- **差分测试** = 模拟器的参考执行器（独立实现 + 覆盖率门禁）
- 编译器/调试器/autotune 全部挂在模拟器上，流片后切真机再校准

行为对"，但多线程芯片还有第二个问题：**线程之间怎么协作才不出错**。

## 扩展阅读：模拟器设计的三个常见坑

### A. 为什么自动驾驶级别的模拟器还要"随机种"回溯

差分测试跑出不一致时，要能**一键复现**——随机数生成器全部
外部注入（seed）、模拟器状态每 N 条指令做一次 checkpoing。
真实团队里"没法复现的 bug"是最贵的 bug。

### B. 性能模型太乐观的连锁反应

周期模型按"最理想流水线"建模 → 编译器团队据此调满 90% 占用率
→ 流片出来只到 60% → **全部 autotune 数据库作废，重跑**。
所以商用模拟器要做"悲观校准"：拿已流片的老芯片（或竞争对手公开
数据）标定误差，再外推到新芯片。误差阈值由团队按项目定（比如 5%），
关键是同一基准、同口径对比。

### C. 模拟器开发的职业含金量

模拟器是 ISA 空间的"第二份规范"，团队里说话最硬的人之一。
它把三样东西焊在一起：**ISA 语义、硬件微架构、编译器生成的机器码**。
模拟器给编译器同学暴露的接口有三个：**指令语义查询**（ISS）、
**周期统计**（周期模型）、**差分测试框架**（验证双方）。
