# 第 18 课：量化与数值精度——工业部署的第一道坎

> 本课风格：代码驱动 + 亲手量化一个算子 + 量化误差分析。
> 对应代码：`toycc/passes/quantize.py`（int8 量化模拟器）
> 准备：跑 `python -m course.runner 18` 对照看。
>
> **为什么这是必修课**：你在公司里看到的部署任务，很大一部分带"量化"二字。
> int8 量化能让模型：体积减 4 倍、带宽受限场景下推理快 2~4 倍、还跑得上专用硬件。
> 但代价是精度损失——如何量化、如何验证、如何取舍，是编译器工程师日常。

## 1. 为什么要量化？先算一笔账

一个 fp32 模型换成 int8：

| 指标 | fp32 | int8 | 收益 |
|---|---|---|---|
| 内存占用 | 4 字节/元素 | 1 字节/元素 | **减 4 倍** |
| 带宽需求 | 4 字节/次 | 1 字节/次 | 带宽瓶颈缓解 |
| 计算单元 | 一般 | 专用 int8 单元（Tensor Core） | 快 2~4 倍 |
| 模型体积 | 大 | 小 | 下载/加载更快 |

**关键**：现在推理的瓶颈往往是**带宽**，不是计算。
int8 把每次搬的数据减 4 倍，等于直接松绑瓶颈。

> **手算：int8 到底把"带宽受限 kernel"加速了多少？**
>
> 拿最简单的 vector_add 算子：`c[i]=a[i]+b[i]`，算 100 万元素。
> - fp32：算 1M 次加法，搬 `3 × 4MB = 12MB` 数据
> - int8：算 1M 次加法，搬 `3 × 1MB = 3MB` 数据
>
> 假设带宽 100 GB/s、没算位：fp32 kernel 用时 ≈ `12MB/100GB/s = 120µs`，
> int8 ≈ `3MB/100GB/s = 30µs`——**正好快 4 倍**，和计算位数无关，
> 纯粹是"搬的数据少了"。
>
> 现在关键来了：**你要在 int8 那条路上额外付出什么？**
> 量化 + 反量化（toycc 的 quantize 实现）：把 float 转成 int8 再转回来，
> 这些都是**额外搬数据 + 额外计算**。所以量化的净收益要看这笔账：
> 省下的 4 倍搬运量 是否 > 量化/反量化带来的额外量。在带宽严重受限的
> 场景（大模型推理），几乎总是赢。**这就是为什么"量化是带宽受限算子的解药"**。
>
> 由此你也理解了为什么注释里常写"**kernel 要是计算受限，量化收益就小**"——
> 计算受限时少搬数据没用，瓶颈在算力不在带宽。

> 注意上面这笔是**带宽账**：它解释的是"为什么推理选低精度"。
> 至于"NVIDIA Tensor Core 主推 int8/fp16"、手机 NPU 全是 int8，那是
> **吞吐账**——硬件把低精度运算做成专用单元，int8/fp16 的吞吐远高于
> fp32。两笔账是两码事，但结论一致：量化不是"可选优化"，是**硬件生态的默认要求**。

## 2. 数值格式全家福：先搞清楚"精度"到底指什么

| 格式 | 位数 | 范围 | 精度 | 用途 |
|---|---|---|---|---|
| fp32 | 32 | ±3.4e38 | ~7 位十进制 | 训练基准 |
| fp16 | 16 | ±65504 | ~3 位 | 训练/推理（有范围限制） |
| bf16 | 16 | 同 fp32 | ~3 位 | 训练（不丢范围） |
| tf32 | 19 | 同 fp32 | ~4 位 | 训练加速 |
| int8 | 8 | -128~127 | 量化值 | 推理主力 |
| int4 | 4 | -8~7 | 更低 | 极限压缩 |

**关键区别**：
- **fp16/bf16 是"浮点"，只是位数少**——不需要"量化"，直接低精度算
- **int8 是"整数"**——必须先把 float 变成整数（量化），才能用 int8 单元

> bf16 为什么重要？它范围和 fp32 一样（指数位一样），只丢精度。
> 训练大模型时用 bf16 不会溢出。这是为什么大模型训练都 bf16。

> **手算：把每种格式拆成"符号/指数/尾数"——范围与精度从哪来**
>
> ```
>         符号 指数 尾数    能表的最大值        相邻两数的间隔(1.0 附近)
> fp32    1   8   23      ≈ 3.4e38           2^-23 ≈ 1.2e-7
> bf16    1   8    7      ≈ 3.4e38           2^-7  ≈ 7.8e-3   ← 范围同 fp32, 精度差 64 倍
> fp16    1   5   10      65504              2^-10 ≈ 9.8e-4   ← 精度好 8 倍, 但 65536 就溢出
> tf32    1   8   10      ≈ 3.4e38           2^-10 ≈ 9.8e-4   ← 范围+精度的折中(硬件内部 19 位)
> fp8-E4M3 1  4    3      448                2^-3  = 0.125    ← 前向权重/激活
> fp8-E5M2 1  5    2      57344              2^-2  = 0.25     ← 梯度(范围优先)
> ```
>
> 三个一眼能用的判断：
> 1. **指数位决定范围**：bf16/tf32 和 fp32 一样 8 位指数 → 不溢出；
>    fp16 只有 5 位 → 65504 封顶，训练里梯度一冲就 Inf。
> 2. **尾数位决定精度**：bf16 的 7 位尾数意味着 1.0 附近间隔 0.0078——
>    权重更新量小于 1% 就"加了等于没加"，所以优化器状态（master
>    权重）永远存 fp32，这就是**混合精度训练**的根源。
> 3. **E4M3 vs E5M2 的分工**：尾数多 = 精度高，指数多 = 范围大。
>    前向数值集中（要精度）用 E4M3；梯度分布散（要范围）用 E5M2。
>    这不是惯例，是位数分配的直接推论。

> **loss scaling：fp16 时代的补丁（理解 AMP 的关键）**
>
> fp16 尾数 10 位，梯度经常 < 2^-14（fp16 最小正规数 6e-5）→ 直接
> 变 0（下溢）。补丁：**loss 乘一个大常数 S（如 1024）**，梯度被
> 链式法则同乘 S 抬进 fp16 能表示的范围，更新前再除回去：
>
> ```
> 手算: 梯度 1e-6 在 fp16 里 = 0(下溢)
>       ×1024 → 1e-3 ✓ 能表示 → 反向传播全程 fp16
>       更新前 ÷1024 还原 → 数学等价, 一次乘除的代价换 fp16 的 2 倍算力
> ```
>
> bf16 普及后 loss scaling 用得少了（8 位指数不溢出）——但会议室
> 里"AMP 要开 loss scale 吗"的答案是：**看格式，不看框架开关**。

> **FTZ 与 fast-math：编译器动的两处"数值手术"**
>
> - **FTZ（flush-to-zero）**：把极小的非正规数（denormal）直接当 0。
>  硬件处理非正规数要额外微码路径，慢 10~100 倍——GPU 默认 FTZ
>  换速度。代价：极小的数变成 0，数值验证时 `max|Δ|` 会跳变。
> - **fast-math**：编译器开关，允许重排/合并浮点运算（`(a+b)+c` →
>  `a+(b+c)`）、用快速倒数代替除法。**结果不再逐位确定**——
>  正确性测试里 `max|Δ|≈5e-17` 会变成 `1e-6` 量级。所以正确性测试
>  的阈值必须考虑"编译器开没开 fast-math"（真实工程的 CI 里常见）。

## 3. 量化的数学：三分钟讲透 scale 和 zero_point

### 3.1 对称量化（我们 toycc 用的）

```
q = clamp(round(x / scale), -127, 127)
x ≈ q * scale
scale = max|x| / 127
```

- `scale`：把 float 压缩到 int8 的"比例尺"
- 对称 = 正负范围对称（零点 = 0）

> **手算：一个真实数值走完量化全过程（并解释实验的 1.1%）**
>
> 设某层激活范围是 `[-3.175, 3.175]`，则：
> ```
> scale = 3.175 / 127 = 0.025
>
> 量化 x = 1.2:   q = clamp(round(1.2/0.025), -127,127)
>                       = round(48.0) = 48
> 反量化:  x' = 48 × 0.025 = 1.2   ← 恰好无损(整除)
>
> 量化 x = 3.2:   q = clamp(round(3.2/0.025), -127,127)
>                       = clamp(128, ...) = 127     ← 撞上 clamp!
> 反量化:  x' = 127 × 0.025 = 3.175  ← 丢了 0.025
> ```
>
> 由此推出两个**理论误差上界**：
> - **舍入误差** ≤ `scale/2 = 0.0125`（任何 x 四舍五入后最多差半个刻度）
> - **相对误差** ≤ `1/127 ≈ 0.79%`（对满量程信号）
>
> 实验里 per-tensor 的 1.1% 是激活量化误差与权重量化误差的合成：
> 激活量化的理论相对误差上界是 0.79%，其余来自 clamp 截断与权重量化。
> **上界给的是最坏情况保证，实验再验证实际误差**。
> 反过来说，如果你看到误差远大于 1/127（比如 10%），那不是舍入问题，
> 是 **outlier 毁掉了 scale**（一个巨大的异常值把 max|x| 拉高，
> 其余数据全挤在几个刻度里）——这就是 scale 选择误差的来源。

### 3.2 非对称量化（带 zero_point）

当数据全是正的（如 relu 输出），对称量化浪费一半范围。非对称用
`zero_point` 平移：

```
q = clamp(round(x / scale) + zero_point, 0, 255)
x ≈ (q - zero_point) * scale
```

- `scale` + `zero_point` 两个参数
- 对 relu 输出这种"非负数据"更高效（不浪费负数范围）

### 3.3 per-tensor vs per-channel（重要！）

| 方式 | scale 粒度 | 精度 | 实现 |
|---|---|---|---|
| per-tensor | 整个张量一个 scale | 较差 | 简单 |
| per-channel | 每个输出通道一个 scale | **更好** | 稍复杂 |

**为什么 per-channel 更好**？权重不同通道的数值范围差异很大，
一个全局 scale 会"牺牲大通道、浪费小通道"。每通道一个 scale，
每层都踩在最佳精度上。**工业界几乎都用 per-channel 权重量化**。

> 实验会验证：per-tensor 1.1% 误差 → per-channel 0.6%，误差降约 45%。

### 3.4 量化误差从哪来

1. **舍入误差**：`round` 丢了小数
2. **clamp 误差**：超出 [-127,127] 的被截断（值域外数据）
3. **scale 选择误差**：scale 不完美，整体偏

**累积**：误差经过多层传播会放大。这就是为什么量化后要跑**完整模型验证**，
而不是只看单层。

## 4. 两种量化时机：PTQ 和 QAT

### 4.1 PTQ（训练后量化 Post-Training Quantization）

```
训练好的 fp32 模型 → 跑一遍校准集 → 统计每层的 scale → 转 int8
```

- **优点**：不需要重新训练，快（几小时）
- **缺点**：精度损失可能不可控（尤其小模型、异常值多的模型）

### 4.2 QAT（量化感知训练 Quantization-Aware Training）

```
训练时就在模型里"模拟量化"(前向走量化, 反向正常) → 模型自己适应 → 转 int8
```

- **优点**：精度损失小得多（模型学会了扛住量化误差）
- **缺点**：要重新训练

> **编译器工程师的重点是 PTQ**：把校准、scale 计算、算子替换自动化。
> 你能控制的是"怎么算 scale、怎么选量化策略"，让 PTQ 损失最小。

## 6. 真实编译器怎么做量化（TVM / ONNX Runtime）

| 阶段 | 干什么 |
|---|---|
| 校准 | 跑一批校准数据, 统计激活的 min/max |
| scale 计算 | 由 min/max 和位宽算出每层 scale |
| 算子替换 | conv/matmul → int8 版本, 插 Quantize/Dequantize |
| scale 折叠 | 把连续 quantize/dequantize 合并(省一次转换) |
| 精度验证 | 全模型对比, 超阈值则降级策略(per-channel/换层回 fp32) |

**TVM 里的对应**（新代码，`relax/op` 的量化算子 + `topi` 的 int8 kernel）：
```python
# 概念对应(不是完整 API):
#   "nn.quantize"  / "nn.dequantize"   → 插转换
#   "nn.conv2d" 的 out_dtype="int32"   → int8 卷积
#   cutlass fpA_intB → 大厂 int8 kernel 集成(第7课 BYOC)
```

**ONNX Runtime**：`static_quant` / `dynamic_quant` 是 PTQ 的实现；
**TensorRT**：INT8 校准有专门的 calibrator。

## 7. 你该会说的"量化黑话"

| 词 | 含义 |
|---|---|
| PTQ / QAT | 训练后量化 / 量化感知训练 |
| scale / zero_point | 量化的两个参数 |
| symmetric / asymmetric | 对称 / 非对称量化 |
| per-tensor / per-channel | scale 粒度 |
| calibration | 校准（统计 scale 的过程） |
| outlier | 异常值（毁掉 scale 的元凶） |
| mixed precision | 混合精度（部分层 int8、部分层 fp16） |
| fp16 / bf16 / tf32 | 低精度浮点格式 |

## 8. 课后答疑

**Q：为什么量化后精度会掉？能保证不掉吗？**
A：因为信息丢了（舍入 + 截断）。不能保证不掉，但能控制：
per-channel、校准集质量、混合精度（敏感层不量化）都能减少损失。
**任务就是"在误差和收益之间找平衡"。**

**Q：int8 卷积的中间结果不是会溢出吗？**
A：所以中间用 **int32 累加**（8bit×8bit 积最大 127×127，累加 128 次
也就 200 万，int32 装得下），算完再转回 int8/float。
这就是 `_conv_int8` 里 `dtype=np.int32` 的原因。

**Q：量化一定比 fp16 快吗？**
A：看硬件。NVIDIA Tensor Core 有专门的 int8 单元（比 fp16 快）；
有些老硬件 int8 不一定更快。**"快不快"永远绑定硬件看**。

**Q：我应该先学 PTQ 还是 QAT？**
A：编译器工程师先学 **PTQ**（它就是你工作内容：校准+替换+验证）。
QAT 是训练侧的事（数据科学家干）。

## 扩展阅读：量化里的三个常见坑

### A. 为什么 per-channel 比 per-tensor 准得多？

per-tensor 用**一个 scale** 覆盖整层所有权重。但不同输出通道的权重
分布可能差几个数量级——一个 scale 只能"照顾大多数"，极端通道就失真。
per-channel 给每个输出通道一个 scale，**每行权重各归各的**，精度自然高。
代价是硬件要支持"每通道一个 scale"——这就是为什么新芯片都把它做成硬件特性。

### B. int8 累加为什么要用 int32？

两个 int8 相乘结果是 int16 级别，但**累加**几十上百次就会溢出 int16。
所以硬件里"乘法是 int8、累加器是 int32"——这就是你第 18 课看到的
"int8 输入 + int32 累加"。**这个细节决定了你们芯片的乘法器怎么设计**。

### C. 量化误差的"上限"怎么估？

量化引入的误差，理论上界是 `scale / 2`（每个值最多偏半个量化步长）。
**知道这个上界，你就能预判"这层能不能量化"**——如果上界已经大于
这层输出的关键差异，量化就会把有用的信号抹掉。
