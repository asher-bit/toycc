## 1. 先回答一个尖锐的问题：调度为什么不能靠"写好模板"？

第 11 课讲了调度的各种原语。你可能会想：那我把所有核都写成
"最优模板"不就行了？

**不行，三个理由**：

1. **参数爆炸**：分块大小 8/16/32/64？向量宽度 4/8？线程数 64/128/256？
   每个参数组合都是"一个调度"。总数是天文数字，模板只能覆盖少数。
2. **硬件多样性**：A100 的最优分块、手机上就不对；新 CPU 一出，老模板作废。
3. **算子形态不同**：卷积、矩阵乘、Attention、LayerNorm……最优调度都不一样。

所以 TVM 想了一条更聪明的路：**让机器自己搜索**。
输入"这个算子长什么样"+"目标硬件是谁"，输出"最快的那组调度参数"。
这就是 **autotuning（自动调优）**，TVM 的实现叫 **meta_schedule**。

## 2. 核心循环：autotune 到底在跑什么

任何一个 autotuner 的本质都是这个循环：

```
for 轮次:
  1. 生成候选    : 从"搜索空间"里采样一组调度参数
  2. 编译        : 把这组参数应用成可执行 kernel
  3. 测量        : 在真实硬件上跑一遍, 记录耗时
  4. 学习        : 用所有已测结果训练"成本模型"
  5. 下一轮采样  : 让成本模型引导, 避开慢的, 聚焦快的地方
```

**三件最关键的事**：搜索空间、成本模型、测量（Runner）。

### 2.1 搜索空间（SearchSpace）：合法的调度都有哪些？

它不是"所有参数乱组合"，而是**符合规则的调度集合**。比如 matmul：

```
块大小:     8 | 16 | 32
向量宽度:   4 | 8
循环重排:   2 种经典顺序
线程数:     1 | 2 | 4 块并行
```

"合法"由规则保证：不能违反依赖、不能产生错误的内存访问。
TVM 里用"调度规则（ScheduleRule）"生成候选，保证都是能编译的。

> **手算：搜索空间到底有多大？乘一下就知道了。**
>
> 就拿上表那 4 组参数算：`3(块大小) × 2(向量宽度) × 2(循环顺序) × 3(线程数)
> = 36 个候选`。看起来不多？这只是**一个维度没展开而已**。
>
> 真实 matmul 还有：每个维度的 split 次数、是否 cache_read/cache_write、
> 是否 unroll、unroll 深度、是否双缓冲……每加一个维度，候选数就乘一次。
> 一个真实算子的搜索空间轻松到**数百万级**。
>
> 现在算笔账：实测一个候选 = 编译 + 目标硬件运行 ≈ 50ms（乐观）。
> 100 万个候选全实测 = 50ms × 1,000,000 = **50,000 秒 ≈ 14 小时**。
> 而且你知道的（第 19 课），其中 99% 是慢的——浪费 14 小时在垃圾上。
>
> **这就是成本模型存在的全部理由**：它用 500 次采样训练的预测器，
> 把候选**先按预测速度排序**，优先实测"预测快的"，把 99% 的垃圾直接跳过。
> 最终"实测几百个候选就找到最优"——这比 14 小时快两个数量级。
> **没有成本模型，autotune 就是没有灵魂的暴力穷举。**

### 2.2 成本模型（CostModel）：没测过的调度，预测它快不快

**关键问题**：搜索空间可能有几百万个候选，全部实测不现实
（实测一次要编译+运行，毫秒到秒级）。

所以需要**成本模型**：从"已测的那些样本"学习规律，
然后**预测**没测过的候选大概多快。这样下一轮采样就能"避开明显慢的"。

TVM 的成本模型是**机器学习模型**（基于 XGBoost / 神经网络），
特征是调度的结构、循环规模、内存访问模式等。它越测越准。

**类比**：像网购的推荐系统——只看你点过几样，就能预测你大概率喜欢什么。

> **更深一层：成本模型喂进去的"特征"到底长什么样？**
>
> 每个候选调度都会被编码成一串**特征向量**，供模型预测。比如 matmul：
>
> ```
> 候选 A: tile_i=16, tile_j=8, tile_k=4, unroll=2, 向量宽=4, 三层循环嵌套
> 候选 B: tile_i=32, tile_j=8, tile_k=32, unroll=8, 向量宽=8, 三层循环嵌套
>          ↓ 编码成特征
> 特征 A: [16, 8, 4, 2, 4, 3, ...]
> 特征 B: [32, 8, 32, 8, 8, 3, ...]
> ```
>
> 这些特征为什么**能**预测性能？因为它们决定了两个物理量：
> - **循环结构 → 缓存行为**：tile 大小决定数据块是否放进 L2/L1（第 15 课）
> - **向量宽度 → 指令数**：宽 8 比宽 4 少一半条指令（第 11 课 vectorize）
>
> 模型从几百个"特征→实测时间"样本里学到的，就是"哪种组合在这个硬件上
> 更快"——它甚至能学到你写不出的规律（比如"tile_k 偏大反而慢，因为
> 缓存行不全"）。
>
> **关键认知**：成本模型的指标不是"预测准"，而是"**排序对**"。它只要
> 把快的候选排到前面（让 Runner 先实测好的），预测数值差 2 倍都没关系。
> 这大大放宽了模型的精度要求——这也是为什么 XGBoost 这种"足够好"的模型
> 就能胜任，不需要精确的性能公式。

### 2.3 Runner：实测的"裁判"

候选再快，也得**真跑一次**验证。Runner 负责：
- 编译候选成可执行代码
- 在目标硬件上运行（本机 / 远程 RPC 设备）
- 测多次取中位数（排除噪声）
- 把"调度 → 耗时"写进**数据库**

> **为什么"取中位数"而不是"取平均"？一个手算例子：**
>
> 同一个候选跑 5 次，得到：`1.01ms, 1.00ms, 1.02ms, 1.00ms, 3.50ms`
> （第 5 次赶上系统其他进程占 CPU）。
>
> ```
> 平均值 = 1.506ms    ← 那个 3.5ms 的异常值把平均拉高 50%
> 中位数 = 1.01ms     ← 按大小排序取中间: [1.00,1.00,1.01,1.02,3.50]
> ```
>
> 如果拿平均值当判据，一个本来更快（1.01ms）的候选可能因为一次系统抖动
> 被判成 1.5ms——**搜索就选错了方向**。中位数对"偶发噪声"免疫。
> 所以 Runner 的实现里永远有 warmup（先跑几次不计数，让缓存/频率稳定）
> + 多次测量取中位数。这就是第 19 课 benchmark 方法论在 autotune 里的应用。
>
> **另一个隐藏细节**：Runner 跑的是"目标硬件"，不一定是本机——
> 通过 RPC 把 kernel 发送到远程设备（比如手机/服务器 GPU）执行。
> 这意味着 autotune 天然支持"开发机上搜、真实设备上量"的流程，
> 也是第 24 课自研芯片工具链的标配姿势。

### 2.4 Database：把好结果"固化"下来

搜索完不是就完了。最好的调度要**保存**，供：
- 下次编译同一算子直接复用（不用重搜）
- 导出成可读的 schedule 固化进代码
- 记录"什么调度在什么硬件上快"，积累知识

## 3. 一整套流程走查（真实 TVM 的用法）

装好 tvm 后，典型用法（`tune` → `export` → `build`）：

```python
import tvm
from tvm import te, meta_schedule as ms

# 1. 定义计算(只描述"算什么", 不写调度)
M, N, K = 1024, 1024, 1024
A = te.placeholder((M, K), name="A")
B = te.placeholder((K, N), name="B")
C = te.compute((M, N), lambda i, j: te.sum(A[i, k] * B[k, j], axis=k), name="C")

# 2. 描述"这是一个什么工作负载" + "目标硬件是谁"
workload = ms.TuneContext(
    mod=tvm.IRModule({"main": te.create_prim_func([A, B, C])}),
    target=tvm.target.Target("llvm --num-cores=8"),
    space_generator=ms.space_generator.PostOrderApply(),   # 搜索空间
    search_strategy=ms.search_strategy.Evolutionary(),     # 搜索策略
)

# 3. tune: 跑核心循环(生成→测量→学习), 记录进数据库
database = ms.database.JSONDatabase(path_prefix="tune_logs")
ms.tune_tir(
    mod=workload.mod,
    target=workload.target,
    space_generator=workload.space_generator,
    search_strategy=workload.search_strategy,
    runner=ms.runner.LocalRunner(timeout_sec=10),
    database=database,
    max_trials_global=1000,          # 最多试 1000 次
    num_trials_per_iter=64,          # 每轮 64 个
)

# 4. 从数据库拿最好的调度, 编译成模块
sch = database.get_best_schedule(...)   # 取出最优调度
mod = ms.build_from_schedule(sch, ...)  # 用最优调度编译

# 5. 验证 + 部署
```

**对照第 11 课**：tune 出来的 `sch` 里就是一堆
`split/reorder/vectorize/parallel/bind` 调用——你在 toycc 模拟器手写过的那些。

## 4. 一个关键概念：tune 出来的调度，人和机器怎么都能看懂？

meta_schedule 的产物是 **Schedule（调度记录）**，它既能让机器重建
kernel，也能被人类读：

```
tune 日志里大概长这样:
  for i in range(64):        # split 外层
  for j in range(32):
    vectorize(...)           # 向量化
    parallel(...)            # 并行
```

这就是为什么"自动调度"没有把程序员淘汰：**人可以审阅、修改、复用它**。
tune 是起点，不是终点——很多团队是"tune 出来 → 人工微调 → 固化"。

## 5. 概念地图：meta_schedule 全家福

| 组件 | 英文 | 一句话 |
|---|---|---|
| 工作负载 | `TuneContext` | "要优化什么 + 在哪个硬件上" |
| 搜索空间 | `space_generator` | 生成候选调度的规则 |
| 搜索策略 | `search_strategy` | 怎么挑下一批候选（进化/随机/引导） |
| 成本模型 | `cost_model` | 预测未测候选的耗时 |
| 测量器 | `runner` | 真机实测 + 取中位数 |
| 数据库 | `database` | 存"调度→耗时"，可复用/导出 |
| 采样器 | `sampler` | 在搜索空间里按策略采点 |

**历史沿革**（讨论时有用）：
- 老一代：**AutoTVM**（模板 + 成本模型）
- 新一代：**Ansor**（自动生成搜索空间）→ 合并进 **meta_schedule**
- 现在 TVM 统一用 meta_schedule，AutoTVM 已基本退役

## 6. 什么时候该 autotune？什么时候不该？

| 场景 | 该不该 | 原因 |
|---|---|---|
| 训练时的探索 | 该 | 速度不关键，tune 一次收益巨大 |
| 推理部署（固定模型） | 该 | tune 一次，之后每次都快 |
| 频繁换模型 | 看情况 | tune 成本高，可用数据库缓存 |
| 超短任务 / 单元测试 | 不该 | tune 时间比执行时间还长 |

**关键权衡**：autotune 花的是**编译时间**，换来**运行时性能**。
这就是第 5 课那条"编译期 vs 运行时"分界线的又一次体现——
只不过这次是**用机器搜索**换取性能。

## 8. FAQ

**Q：tune 出来的调度一定是全局最优吗？**
A：不是。它是"搜索到的局部最好"（取决于搜索空间和策略）。
真实世界也没有"全局最优"——调度优化本身是 NP-hard 的启发式问题。

**Q：成本模型会不会预测错？**
A：会，但没关系。错的预测只是让搜索"多走点弯路"；
最终结果以**真机实测**为准（Runner 是裁判）。成本模型是加速器，不是裁判。

**Q：tune 一次能用于所有硬件吗？**
A：不能。调度和硬件强相关（缓存大小、指令集、核数）。
所以数据库要按"target"分开存，换硬件就得重 tune。

**Q：meta_schedule 和"图优化 pass"是什么关系？**
A：图 pass（Relax 层）决定算什么、怎么排布；meta_schedule 在 TIR 层
搜索"循环怎么写"。两者是流水线里先后两段：先图优化，后自动调度。

## 深层拓展：autotune 的三个"为什么"

### A. 为什么搜索空间不能随便"全展开"？

一个 matmul 的调度参数有：tile 大小、循环顺序、向量宽度、线程绑定、unroll 层数……
组合起来是**天文数字**。meta_schedule 的聪明处不在"搜得全"，在**"会剪枝"**——
成本模型预测"这个方向没戏"就直接跳过。这就是为什么**成本模型是 autotune 的灵魂**，
没有它，搜索就是暴力穷举。

### B. 为什么 cost model 用"机器学习"而不是"公式"？

理论上你可以写一个"性能 = f(tile, 向量宽度...)"的公式。但真实硬件太复杂——
缓存行为、指令调度、bank conflict 全都影响。所以工业界用**机器学习模型**：
跑几百个真实测量，训练一个"预测器"。这就是 XGBoost/CostModel 的由来。
**它不追求"准"，只追求"排序对"**——能把快的排前面就行。

### C. tune 出来的结果，能跨硬件复用吗？

**不能**。tile 大小/向量宽度全绑定硬件（寄存器数、缓存大小）。
所以第 24 课讲"给自研芯片跑 autotune"时，第一步就是**重新 tune**——
数据库是"每颗芯片一份"的。这也是为什么第 24 课说"target 描述"是核心：
它决定了 autotune 的搜索空间长什么样。
