# 第 5 课：常量折叠——把能提前算的，全在编译期算完

> 本课风格：代码驱动 + 手算"折叠前后运行成本差异"。
> 对应文件：`toycc/passes/constfold.py`（约 20 行）
> 准备：跑 `python -m course.runner 5` 对照看。

---

## 1. 先建立一个贯穿全课的二分法：编译期 vs 运行时

任何一段代码执行的时间点，只有两种：

| | 编译期 | 运行时 |
|---|---|---|
| 发生几次 | **一次**（出产物之前） | **每次都发生** |
| 慢点要紧吗 | 不要紧（慢一点无妨） | 要紧（每毫秒都贵） |
| 知道什么 | 知道所有权重、形状 | 只拿到当前的输入数据 |

**编译器的一切优化，本质都在往左边搬东西**：把"反正每次都要做的事"
挪到编译期只做一次。这就是"编译期 vs 运行时"这条分界线的意义。

---

## 2. 一个具体的浪费场景（衔接上一课）

布局 pass 给 conv 的权重插了 4 个 `layout_transform`：

```
conv1_lt_1 = layout_transform(conv1_w, nchw→nhwc)   ← 转权重
conv1_lt_2 = layout_transform(bias1,  nchw→nhwc)    ← 转偏置
conv2_lt_1 = layout_transform(conv2_w, nchw→nhwc)
conv2_lt_2 = layout_transform(bias2,  nchw→nhwc)
```

**问题来了**：`conv1_w` 是权重——它是常量，**永远不变**。
那这个转置，是应该：
- (a) 每次推理都执行一遍 → 白花 4 次搬移，且永远算的是同一个结果？
- (b) 编译期算一次，把结果直接存下来，运行时直接读？

显然是 (b)。这个"把只吃常量的算子提前算掉"的操作，就叫**常量折叠
（constant folding）**。

> 类比：菜谱有"把面粉过筛"这步，但你每次做菜都重新筛。
> 更好：提前筛好装袋（编译期），做菜时直接倒（运行时）。

---

## 3. 逐行读 `toycc/passes/constfold.py`

整个 pass 就这么短：

```python
class ConstantFoldPass:
    def __call__(self, graph: Graph) -> Graph:
        g = graph.clone()
        for node in list(g.nodes.values()):
            # 所有输入都是常量,就可以在编译期把算子算出来
            if all(i in g.constants for i in node.inputs):
                ins = [g.constants[i] for i in node.inputs]
                fn = getattr(RefImpl, node.op_type)
                value = fn(ins, node.attrs)
                # 结果直接变成常量,节点消失,消费者照常引用这个名字
                g.set_constant(node.name, np.asarray(value))
                g.inputs.append(node.name)
                g.remove_node(node.name)
        return g
```

**逐行拆**：

| 行 | 在干嘛 |
|---|---|
| `g = graph.clone()` | 无副作用（第 3 课讲过为什么 pass 都要这样） |
| `for node in list(...)` | 遍历所有节点（`list()` 快照，因为循环里会删节点） |
| `all(i in g.constants for i in node.inputs)` | **判断：所有输入都是常量吗？** |
| `ins = [g.constants[i] for i in node.inputs]` | 取出常量值 |
| `fn = getattr(RefImpl, node.op_type)` | 找参考实现（第 2 课的执行器！） |
| `value = fn(ins, node.attrs)` | **在编译期执行一次** |
| `g.set_constant(node.name, ...)` | 结果变成新常量 |
| `g.remove_node(node.name)` | 节点从图里消失 |

**注意那个 `fn = getattr(RefImpl, ...)`**——它就是参考执行器！
常量折叠 = **把参考执行器搬到编译期跑一遍，把结果焊进常量表**。
"一个执行器，两种用途"，这是本课要你记住的第一个点。

**为什么"节点消失但消费者还能用"？** 因为消费者的 `inputs` 里引用的是
`conv1_lt_1` 这个**名字**。现在这个名字从"一个节点"变成了"一个常量"，
消费者的引用不用改，自动指向了常量值。这是"张量名 = 节点名"设计的好处。

## 4. 手算"折叠前后，运行成本差多少"

我们的图在**布局之后、折叠之前**，运行时要做 10 次操作（6 个节点 +
4 个权重/偏置转置）：

```
运行时: x →[转]→ conv1 →[转]→ conv2 →[转]→ reshape → matmul
        + 4 次权重/偏置转置(每次都是全数组搬移!)
```

**折叠之后**（跑 `python -m course.runner 5`）：

```
conv1_lt_1/conv1_lt_2/conv2_lt_1/conv2_lt_2  全部从节点列表消失
(它们变成了 input 列表里的常量)
```

运行时只执行 6 个算子，且**没有一次权重转置**。

> 假如这个模型每秒钟推理 1000 次，折叠省下的就是"每次省 4 次全数组转置"。
> 次数越多、模型越大，折叠的收益越夸张。

> **手算：一次权重转置到底多少钱？**
>
> 拿 `conv1_w` 举例：`(4, 3, 3, 3)` = 108 个 float32 = 432 字节。
> 转置 = 读 432 字节 + 写 432 字节 = 搬 864 字节。以 100 GB/s 带宽算，约 8.6ns。
>
> 4 次转置 = 4 × 8.6ns ≈ 35ns / 次推理。
>
> **折叠的关键不是"省 35ns"，而是"把编译期和运行时的边界挪了"**：
> - 折叠前：这 35ns **每次推理都付**，一辈子都付（模型部署一年，付一年）
> - 折叠后：这 35ns 只在**编译期付一次**，运行时归零
>
> 这就是"编译期 vs 运行时"的本质：**能提前做的，绝不拖到运行时**。
> 哪怕每次只省 35ns，那是因为"次数"放大到"亿次推理"，任何固定的
> 编译期开销都能摊薄到可以忽略。**折叠 = 用固定成本换摊薄收益**。

## 5. 一个你没见过的细节：折叠也要"节制"

真实 TVM 的 `fold_constant.cc`（447 行）里，有个我们 toycc 没做的判断：
`ShouldBeFolded`——**折叠前先问"值不值得"**。

```cpp
/*!
 * \brief 检查折叠 expr 是否值得。
 * 折叠是在 IRModule 里物化一个常量, 用"编译期成本"换"运行时成本"。
 * 例如折叠 zeros/ones/full 这类"创建算子", 会把大常量塞进二进制, 增大体积。
 */
bool ShouldBeFolded(Expr expr) {
  static constexpr int64_t kMaxFoldElements = 1024;
  ...
  if (num_elements <= kMaxFoldElements) return true;   // 小 → 折

  // 大输出: 只有"有张量输入"(不是纯创建)才折
  for (const auto& arg : call->args)
    if (ExprContainsTensor(arg)) return true;
  return false;
}
```

**为什么 fold `zeros(1, 1000000)` 是坏事？**

- `zeros` 不需要输入，运行时"生成 100 万个 0"几乎免费
- 如果折叠它，就在编译产物里**物化一个 100 万元素的常量数组**
  → 二进制变大、加载变慢、内存占用变高
- 收益是负的！

所以 TVM 的规则是：**输出很小就折；输出很大但"有输入"才折（因为能顺带
消掉上游依赖）；纯创建的大算子不折。** 这就是"折叠也有成本，不是无脑做"。

toycc 没做这个权衡（我们全折）——因为我们的常量都很小。但你要知道：
生产级编译器里，**每个优化都有"值不值得"的成本模型**。

## 6. TVM 怎么"执行"一个算子来做折叠？（对比）

我们 toycc：`getattr(RefImpl, op_type)(ins, attrs)` —— numpy 直接算。

TVM：`ConstEvaluateCallTIR` 内部——

```cpp
// 1. GetCachedBuild(prim_func)  → 用 LLVM 把 TIR PrimFunc 编成可执行函数
// 2. 分配输出, 调用它, 拿到结果
// 3. 把结果包成 Constant 放回 IR
```

**为什么 TVM 不用 numpy？** 因为 TVM 折叠的对象是**已经下降到底层**的
TIR PrimFunc（C++ 侧的东西），没有 numpy 可用。它选择"真的用 LLVM 编译一遍
再执行"。思想和你完全一样：**求值 → 焊进常量**，只是求值引擎不同。

还有一个我们没做的检查——**折叠对象必须是纯函数**：

```cpp
// MatchPrimFunc: 确认这是纯函数、没有 side effect、输出形状是常量
// 不满足就不折 —— 否则把"有副作用"的东西提前算掉会改变语义
```

比如一个"打印日志"或"计数器自增"的算子，被折叠成常量后副作用就没了，
语义就被破坏了。toycc 的所有算子都是纯的，所以没这层检查；
真框架必须检查。

## 8. 课后答疑

**Q：折叠和"死代码消除(DCE)"是什么关系？**
A：折叠把节点变成常量；如果这个常量没人用，DCE 会把它删掉。两个 pass 配合。
我们的 toycc 没实现 DCE（图里留下的常量也无害）。

**Q：折叠会不会把"编译产物"搞得巨大？**
A：会，这就是 `ShouldBeFolded` 存在的理由。真实编译器在"物化常量"和
"减小体积"之间权衡。

**Q：折叠后权重从哪来？运行时拿到的权重是什么？**
A：折叠只处理"编译期已知的常量"。真正的推理权重（部署时的模型参数）
是运行时绑定的（`relax.vm` 里的 `bind_params`）。toycc 为了教学
把权重当编译期常量处理了。

**Q：`g.inputs.append(node.name)` 这行什么意思？**
A：节点 `conv1_lt_1` 被删了，但它的名字还在被别的算子引用。
把它加进 `inputs` 列表，等于说"这个名字现在是个输入"，而它的值在
`constants` 里。参考执行器第一行就是 `vals = dict(constants)`，
所以能取到值。

## 9. 本课小结

- 二分法：**编译期（一次）vs 运行时（每次都发生）**；优化=往编译期搬
- 常量折叠 = 把"输入全是常量"的算子**在编译期执行掉**，结果焊进常量
- 它**复用参考执行器**当求值引擎
- 生产级折叠有"值不值得"的权衡（`ShouldBeFolded`）+ "纯函数"检查
- 与 DCE 配合使用效果更干净

## 10. 扩展阅读 A：折叠对象不只有权重——折叠的各种形态

第 5 课讲的是"layout_transform(权重) 折叠"。但常量折叠能做的远不止这些：

| 形态 | 例子 | 折叠效果 |
|---|---|---|
| 常量布局转换 | 权重 NCHW→NHWC | 运行时 0 成本 |
| 常量拼接 | `concat([w1, w2], axis=0)` | 提前拼好 |
| 常量切片 | `slice(w, 0, 5)` | 提前取出 |
| 常量算术 | `w * scale + 0.5` | 提前算好 |
| 形状特化 | `reshape(w, (…) )` | 提前改形状 |
| 常量转置 | `transpose(w)` | 提前排好 |

**它们的共同点**：输入全是常量 → 结果也是常量 → 编译期算掉。

真实编译器里，常量折叠还常和**形状特化**配合：
模型编译时"绑定"一批形状（如 batch=1），所有依赖该形状的计算
都能被折叠/简化。这就是第 9 课 `bind_params` 的动机之一。

## 11. 扩展阅读 B：折叠与死代码消除的经典配合

第 5 课 FAQ 提过 DCE。这里把配合讲清楚，因为这是最常见的 pass 组合：

```
图:  w → [layout_transform] → t → [reshape] → 只有 t 被用
                    (折叠掉 t, 但 w→reshape 分支还在)
```

折叠把 t 变成常量后，`w` 和 reshape 节点**可能没人用了**——但它们还在图里。
这时需要 DCE（第 12 课会实现）把它们清掉。

**实际管线中的配合**（TVM 里常见）：

```
FoldConstant → DeadCodeElimination → (可能再来一轮)
```

这就是"pass 组合拳"：每个 pass 做一件事，配合起来完成完整清理。
**你以后写优化时，也要习惯"我的 pass + DCE"一起跑。**

## 12. 扩展阅读 C：折叠的边界——什么看起来能折其实不能？

初学的人常犯的错：以为"常量输入"就是折叠的全部条件。其实还要满足：

1. **纯函数**：算子不能有副作用（打印/读文件/全局状态）
2. **形状确定**：输出形状不能依赖运行时信息
3. **不爆炸**：折叠产物不能大到塞爆编译产物（`ShouldBeFolded`）
4. **不需要 eval 链**：如果折叠它需要"先执行一个更复杂的算子"，
   要确认那个执行是安全的（比如不会触发未定义行为）

**一个经典反例**：`random_normal` 输入为空、看起来是"常量算子"。
但折叠它会产生一个**固定的随机数**——每次推理都用同一批"随机"数！
这在语义上可能没问题（有些场景需要），但会破坏"每次推理随机性"的期望。
所以这类算子标了"副作用"，编译器**不折**。

**结论**：折叠 = 纯函数 + 形状确定 + 不爆炸 + 无副作用。
toycc 全满足所以全折，真实编译器每个条件都要检查。
