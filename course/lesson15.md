## 1. 一句话总览：计算机是一个"速度差距巨大"的层级系统

现代 CPU 内部，不同存储的速度差距**是数量级级别的**：寄存器到 DRAM
差上百倍（0 周期对 200 周期），DRAM 到 SSD 还要再差几个数量级
（200 周期对百万周期以上）：

```
速度(快 → 慢)       容量(小 → 大)        延迟(典型)
寄存器                几十个                0 周期
L1 缓存               几十 KB                4 周期
L2 缓存               几百 KB               12 周期
L3 缓存               几 MB ~ 几十 MB       40 周期
内存(DRAM)            几十 GB               200 周期
磁盘/SSD              TB 级              百万周期以上
```

这张表藏着一对矛盾：**越快的层越小**——寄存器快但只有几十个，DRAM
够大却要 200 周期。所以缓存优化、寄存器分配、内存规划拆开看是三门
手艺，合起来是同一份工作：

1. **算热度**：哪些数据会被反复用（分析）
2. **选楼层**：把热数据放进"装得下"的最快一层（分配）
3. **排座位**：装不下时按用量从高到低排序，用得少的先下去

快层小、慢层大——所以编译器永远只能优先照顾"回头客"。

> 记忆锚点：**一次内存访问 ≈ 上千次计算**。所以"少搬一次数据"
> 往往比"少算几次"更值钱——第 3 课融合的动机再次呼应。

> **手算：为什么"一次访问 ≈ 上千次计算"？**
>
> 用 A100 的典型数字：FP32 峰值约 19.5 TFLOP/s，HBM 带宽约 1.6 TB/s。
> 算"一次计算和一次访问的时间比"：
>
> - 算一次 FP32：`1 / 19.5e12 s ≈ 0.05 ns`（吞吐口径：每秒能出这么多结果）
> - 等一次全局内存访问：延迟约 400 周期（A100 时钟约 1.4 GHz → 约 285 ns）
> - 两下一除：`285 / 0.05 ≈ 5700` —— 等一次内存的时间，够算几千次乘法
>
> 注意：这个数用带宽（1.6 TB/s）算不出来。带宽是"连续搬一大块"的
> 吞吐口径，延迟是"随机等一次"的等待时间，两者不是一回事。
>
> 关键不是这个商，而是**几何直觉**：算力每年增长 ~60%，带宽每年只涨
> ~20%。两者的差距（"内存墙"）**逐年拉大**。20 年前一次内存访问 ≈ 上百次计算，
> 现在 ≈ 上千次，未来更高。
>
> **对编译器意味着什么**：硬件在向你喊话——"计算随便用，带宽省着花"。
> 所以：
> 1. **融合**（第 3 课）：省一次中间结果 write+read，就是在省最贵的带宽
> 2. **布局**（第 4 课）：让一次缓存行搬来的数据被用满 16 次，而不是 1 次
> 3. **分块**（第 11 课）：让一个小块待在上层缓存反复用
>
> **一句话**：现代编译器优化的第一准则不是"少算"，是"少搬"。
> 你后面学的一切优化，几乎都能翻译成"少搬数据"这一句话。

## 2. 缓存（Cache）——最值得编译器花心思的地方

### 2.1 缓存怎么工作

CPU 读内存不是"按字节读"，而是**按"缓存行（cache line）"读**：
一次读一整行。真机一行典型 64 字节 = 16 个 float；本课模拟器
（`hardware.py`）为教学简化把一行设为 4 个 float——下文实验里
"一行/行利用率"都按模拟器的 4 个 float 口径算。

```
内存地址:  ... | x0 x1 x2 x3 | x4 x5 x6 x7 | ...  ← 每 4 个 float 一行
```

**两个核心概念**：

- **时间局部性（temporal locality）**：刚用过的数据，很快还会用
- **空间局部性（spatial locality）**：用了一个数据，旁边的数据也快用了

**编译器想尽办法制造"局部性"**：布局（第 4 课）、分块（第 11 课）、
循环重排，全都在干这件事。

### 2.2 缓存的三个组织参数

| 参数 | 含义 | 影响 |
|---|---|---|
| 行大小 | 一次读多少 | 行越大空间局部性越强 |
| 相联度(ways) | 一个位置能放几行 | 越大冲突越少、越贵 |
| 容量 | 总共能放多少 | 越大命中率越高 |

**冲突缺失**：两块数据映射到缓存同一位置，互相踢 → 这是
"循环顺序"影响性能的核心机制（下面实验会看到）。

### 2.3 实验：同一个 matmul，循环顺序不同，缓存表现差 10 倍

```bash
python -m course.runner 15
```

看这张表（32×32 matmul + 一个小 L1 缓存）：

```
顺序    访问数    缺失数    命中率    延迟(周期)
ijk    66560    34476    48.2%    6961760
ikj    66560     8359    87.4%    1738360
kij    66560     3044    95.4%     675360
tiled  73728    11704    84.1%    2414528
```

**为什么 ijk 这么慢？** 在 `ijk` 顺序里，内层循环是 `k`：

```python
for i: for j: for k:
    A[i*K+k]   # k 变化 → 扫 A 的一行 → 空间局部性好
    B[k*N+j]   # k 变化 → 跳着访问 B 的一列 → 每行只用 1 个 → 缓存行浪费!
```

`B` 是按行存的，但 `ijk` 是按列访问它——每读一个 B 元素，**拉进来一整行缓存，
却只用 1 个**（模拟器里一行 4 个 float，行利用率 1/4），然后那行再也不会被用。
看表里的**访问数/缺失数**：ijk 共访问 66560 次、缺失 34476 次——一半以上的
访问都要从内存重新拉行。因为模拟 L1 只有 8 组 × 2 路 × 4 字 =
64 个字（256 字节），远小于 32×32 的工作集；B 的列访问又几乎每次都要重新
拉行——缓存被白白刷爆。

**kij 为什么快？** 内层 `j` 扫 B 的一行，行利用率 4/4；A 的标量被反复复用
（时间局部性）。缺失数只剩 3044（命中率 95.4%）。这就是
"循环重排"（第 11 课 reorder）为什么是性能差异最大来源之一。

**对照 toycc/schedule.py**：第 11 课你亲手把 matmul 调度成
`reorder(k, ...)` ——现在你知道**为什么**了：让 B 按行访问。

> **亲手玩**：打开 `toycc/hardware.py`，改缓存参数
> （比如 `num_sets=16, ways=4`）或矩阵大小，看命中率怎么变。
> 你会发现：缓存越大，各种顺序差距越小（都能装下就不挤了）。

## 3. 寄存器（Registers）——最快、最小、但极易耗尽

### 3.1 寄存器是什么

CPU 算数**必须在寄存器里做**：`A[i]+B[i]` 得先把 `A[i]` 加载进寄存器、
`B[i]` 加载进寄存器、相加、结果存回寄存器。内存到寄存器的搬运
是显式的（load/store）。

寄存器是**最贵的资源**（x86 通用寄存器约 16 个，ARM 约 31 个）。

### 3.2 编译器为什么关心

一个值从被算出（出生）到最后一个消费者用完它（死亡）之间，必须
一直占着一个寄存器。同一时刻还活着的值的个数，叫**寄存器压力
（register pressure）**。

```
x = a + b      ← x 出生; a、b 用完即死
y = x * c      ← x 的最后一个消费者 → x 在这里死掉
z = y + d
```

单链融合的压力其实很小：每个中间结果被下一个算子用完就死，链
再长，同时活着的也只有 2~3 个。压力真正变大来自三个地方：

1. **多消费者**。一个中间结果被两个以上算子用，就要活到最后一个
   用完为止。ResNet 的 skip connection 是典型：add 的两个输入
   必须同时活着。
2. **算子自带操作数**。每个算子除了消费上个算子的输出，还要把
   权重、bias、scale、常量搬进寄存器。50 个算子各带各的操作数，
   加起来就是几十个活值。
3. **循环展开**。把循环体复制 N 份，每份的中间值各自占位，
   活值直接乘 N。

寄存器数量是硬件定死的：x86 通用寄存器约 16 个，ARM 约 31 个，
GPU 每线程上限 255 个，还要按 SM 总量分配。装不下时，多余的活值
被**溢出（spill）**到内存：

```
st %r5, [sp+8]    ← 活值太多, 把 r5 写回栈
...               ← 等下次用到 r5:
ld %r6, [sp+8]    ← 再从内存读回来
```

溢出一次，热循环里就多一次"内存→寄存器→用→写回"的往返。一次
内存访问的时间够算上千次乘法，所以反复溢出的 kernel 会把融合
省下的访存原样加回去，甚至更慢。

融合的边界因此画在这里：**融合后活值 < 可用寄存器数**，还要给
地址计算、循环计数留位。编译器做融合决策时会估算每种方案的
寄存器用量，超预算就拆开——"融合要有限度"的量化依据就是这条。

GPU 上还多一层约束：寄存器按线程分配，SM 的寄存器文件总量固定。
一个线程多占几个寄存器，一个 SM 能同时驻留的 warp 就少几组，
延迟隐藏能力跟着掉。GPU 的 spill 落在 local memory（逻辑私有、
物理在显存里），代价比 CPU 栈溢出更大。

编译器怎么自动决定溢出谁？3.4 从 IR 层回答：活值分析 → 冲突图
→ 图着色。

### 3.3 实验

```bash
python -m course.runner 15
```

看 `register_pressure_demo()` 输出。记住结论：
**寄存器是稀缺资源，编译器要么省着用（复用、减少活值），
要么接受溢出代价。**

### 3.4 和 IR 的关系

第 14 课的 LLVM IR 里 `%result` 是"虚拟寄存器"——数量无限。
LLVM 后端的**寄存器分配器**（register allocator）负责把无限虚拟寄存器
映射到有限的真寄存器，冲突时选择溢出谁。这是编译器的经典难题
（图着色问题，和内存规划是同构问题！）。

## 4. SIMD 与向量化——一条指令算多个数

### 4.1 什么是 SIMD

SIMD（Single Instruction Multiple Data）：**一条指令，同时处理多个数据**。

```
标量:  c0=a0*b0; c1=a1*b1; c2=a2*b2; c3=a3*b3   ← 4 条指令
向量:  c[0:4] = a[0:4] * b[0:4]                  ← 1 条指令(4 通道)
```

现代 CPU 有 SSE（4 个 float）、AVX（8 个）、AVX512（16 个）。
GPU 是极端版 SIMD。

### 4.2 编译器为什么关心

第 11 课的 `vectorize` 就是让编译器把内层循环**展开成向量指令**。
但前提是**数据要排布好**（布局，第 4 课）——这就是 NHWC/NCHW4c
存在的意义之一。

**向量化失败的原因**（编译器常见坑）：
- 数据不连续（跳着访问）→ 无法打包成向量
- 循环次数不是向量宽度的倍数 → 需要"尾部处理"
- 循环内有分支/别名 → 无法证明可向量化

## 5. 延迟 vs 带宽——两种"慢"不一样

| | 延迟（latency） | 带宽（bandwidth） |
|---|---|---|
| 定义 | 单次访问等多久 | 单位时间能搬多少 |
| 类比 | 快递单件到货时间 | 每秒钟能发多少件 |
| 优化手段 | 减少访存次数（局部性） | 提高并行度（同时搬） |

**编译器两种手段都要**：
- 减少**次数**：缓存复用、分块（针对延迟）
- 提高**并行**：多线程、流水线、同时发起多个访存（针对带宽）

**关键认知**：现代硬件瓶颈往往是**带宽**（"每秒能搬多少"），
因为计算越来越快、搬数据跟不上。这就是为什么融合（少搬一次）、
布局（搬得更顺）收益巨大。

## 6. GPU 模型：大规模并行的内存与线程

GPU 和 CPU 结构差异很大，编译器（尤其 AI 编译器）必须懂：

```
GPU:
  线程(thread)  → 最小的执行单位
  线程块(block/CTA) → 一组线程, 共享共享内存(shared memory)
  网格(grid)   → 所有块
  调度单位: warp = 32 个线程, 一起执行同一条指令(锁步)
```

| 概念 | 作用 | 编译器决策 |
|---|---|---|
| 线程数 | 并行度 | 调度时 `bind` 到线程 |
| 共享内存 | 块内共享、快 | `cache_read` 到共享内存 |
| warp 锁步 | 32 线程同步执行 | 分支要"同向"否则浪费 |
| occupancy | 块占 SM 的比例 | 限制寄存器/共享内存用量 |

**为什么 GPU 编程/编译"反直觉"**：不是线程越多越好——
太多线程抢寄存器/共享内存，会降低 occupancy，反而慢。
这就是为什么 GPU 编译器要在"并行度"和"资源"之间平衡
（meta_schedule 的搜索空间里有一大块是在找这个平衡）。

## 7. 指令级并行（ILP）与流水线

一条指令从发出到完成要过很多级（取指、译码、执行、写回），
现代 CPU 用**流水线**让它们重叠——就像工厂流水线，虽然单个产品
要 5 个工序，但流水线满载时每周期出一个产品。

编译器利用 ILP 的手段：
- **减少依赖**：让后面的指令不依赖前面的结果（就能并行执行）
- **循环展开**：复制循环体多份，让多次迭代并行（消除跳转开销）

这解释了**为什么代数化简（第 12 课）有意义**：化简后依赖链更短，
ILP 更高。

## 10. 课后答疑

**Q：缓存不是硬件自动管的吗？为什么还要编译器管？**
A：缓存自动管"最近用过的数据"，但它**不知道程序未来的访问模式**。
编译器提前把访问顺序排好（分块、重排），让缓存"自动命中"。
这是"软件配合硬件"的经典合作。

**Q：为什么我明明按行访问，缓存命中率还是低？**
A：可能的原因：① 数据集太大装不进缓存（需分块）；② 存在冲突缺失
（数据映射撞车）；③ 伪共享（多线程写同一缓存行的不同元素）。
用 `perf`/`valgrind --tool=cachegrind` 这类工具能测出真相。

**Q：编译器怎么知道"一次访存 = 多少周期"？**
A：编译器内置**目标描述（target description）**：每种硬件记录的
延迟/容量/指令延迟表。调度器用这些数字做代价评估（我们的
`LATENCY` 表就是这个的简化版）。

**Q：我要不要先把《计算机组成原理》读完再学编译？**
A：不用。这门课已覆盖编译需要的常用硬件知识主体。遇到具体问题
（如某指令延迟）再查目标文档即可。**边做边补**比先啃教材高效。

## 11. 本课小结

- 内存层次：寄存器 < L1 < L2 < L3 < DRAM，**速度差上百倍**
- 缓存：按行读、局部性、冲突缺失 → 编译器用布局/分块/重排来"配合"
- 寄存器：稀缺资源，溢出代价大 → 控制融合规模、寄存器分配
- SIMD：一条指令多个数 → 向量化（依赖数据排布）
- 延迟 vs 带宽：一个是"等"，一个是"搬"；现代瓶颈多是带宽
- GPU：线程/块/warp/共享内存 → 调度与资源平衡
- **硬件知识 → 编译器决策**的因果表是核心产物

## 扩展阅读：硬件参数表的三个用法

### A. 这些数字到底从哪来？

缓存大小、寄存器数、延迟周期——**不是你猜的，是芯片手册写的**。
真实工作里，你入职第一周就要拿到你们芯片的"硬件参数表"（hardware spec），
里面就是这些数字。**`hardware.py` 就是那张表的教学版**。

### B. 为什么"延迟"和"带宽"要分开记？

很多人把"内存快不快"当成一个问题。其实是两个：
- **延迟**：发起一次访问，要等多少周期才有结果（隐藏它靠"并行"）
- **带宽**：单位时间能搬多少字节（填满它靠"连续访问"）
第 19 课的 roofline 就是把这两个数合在一起算"性能天花板"。

### C. 缓存模拟器的局限

`hardware.py` 是个**教学模拟器**——它假设缓存行为是理想的。
真实硬件有"预取"、"写回策略"、"替换算法（LRU/随机）"等复杂细节。
但作为编译器开发者，**你不需要精确模拟，只需要"大概知道哪层快哪层慢"**——
这已经够你做 80% 的优化决策了。
