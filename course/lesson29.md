# 第 29 课：二进制格式与模块加载——编译产物怎么"活"起来（目标文件、重定位、JIT）

> 本课风格：概念 + 手算重定位 + 运行时 JIT 流程图。
> 目的：搞懂"汇编文本 → 目标文件 → 链接 → 加载 → 运行"这最后一公里，
> 以及 GPU 生态为什么要把"源码"塞进二进制（fatbin + PTX 的真相）。
> 前置：第 24 课（工具链全景）、第 25 课（MC 层产出物就是本课的输入）。

---

## 1. 编译器输出的最后一公里

```
你写的 pass ──► TIR ──► codegen(第7/24课) ──► 汇编文本(第25课 MC)
      ──► 汇编器(assembler) ──► 目标文件(.o, ELF 格式)
      ──► 链接器(linker) ──► 可执行/镜像
      ──► 加载器(loader) ──► 运行时/JIT 执行(第17课 VM 的硬件版)
```

之前只给了"assembler/linker"两个名词，本课填内部：**目标文件里
到底有什么、链接时发生什么、加载时发生什么**。GPU 工具链工程师
天天和这三种文件打交道：

| 文件 | 本质 | 出场方式 |
|---|---|---|
| `.o` 目标文件 | ELF，符号未定址 | 编译中间态 |
| cubin | 一种 ELF（SASS 代码 + kernel 元数据） | 设备二进制 |
| fatbin | 打包容器：多代 cubin + PTX "源码" | `cudaModuleLoad` 的输入 |

## 2. GPU 目标文件的特殊之处：kernel 元数据

普通 CPU 的 `.o` 里就是代码段 + 数据段 + 符号表。GPU 的目标文件
**额外带一段 kernel 元数据**——因为启动一个 kernel 不只是跳进
一个函数，还要告诉硬件"派多少线程、占多少资源"：

```
kernel 描述(元数据):
  name          向量add
  gridDim       128 块 × 256 线程     ← 怎么启动
  regs_per_kernel  40                  ← 占用率(第21课)的输入
  smem_size       4096 B               ← 共享内存需求(第21课)
  param_layout   [ptr A, ptr B, ptr C] ← 参数怎么放(第24课 runtime)
```

> **关键认知**：`cudaLaunchKernel` 的第二个参数为什么是
> `dim3 grid/block`？因为**它只是把元数据里的数字搬到硬件寄存器**。
> 编译器在编译期就算好了这些数字，
> 存进二进制，运行时零计算就是启动。

## 3. 重定位：链接时发生的事（手算）

### 3.1 为什么需要重定位

汇编器生成的目标文件里，跨文件的符号（`call foo`、`ld addr`）
**还不知道地址**——因为每个文件独立编译，不知道别的文件多大。
链接器把多个 `.o` 拼成一个镜像，然后把"占位"填成真地址。

### 3.2 手算：两遍链接

```
文件 a.o:  [指令 1(4B)] [call printf(4B)]   (call 的占位是 0, 附重定位项:
           指向符号 printf, 偏移 4)
文件 b.o:  [printf 代码, 长度 40 字节]   (符号表: printf @ 0)

第一遍: 收集符号表, 排布每个段的位置
  假设 a.o 代码段从 0x1000 开始, 长度 8(两条 4B 指令); b.o 从 0x1008 开始
  printf 地址 = 0x1008

第二遍: 把 a.o 里"call printf"的占位填上
  call 位于 0x1004(代码段内偏移 4), PC 相对寻址:
  目标 = 0x1008 - (0x1004 + 4) = 0
  重定位项说"偏移 4 处填符号 printf 的值", 填完这轮才完整
```

> **手算要点**：重定位项的格式是 `(段内偏移, 符号名, 类型)`，
> 类型决定"怎么从符号值算最终值"（PC 相对 / 绝对 / GOT）。GPU
> 的 kernel 间互相调用（device function）同样走这套——在你自研
> 芯片的编译工具链里，**链接器是绕不开的一块**（此前一直当黑盒，现在你知道黑盒里的步数）。

### 3.3 GPU 特殊：kernel 入口放在"函数表"

GPU 镜像里有个**全局 kernel 入口表**（类似 ELF 的 `.symtab` 特化）：
运行时的"按名字查 kernel"（`cuModuleGetFunction`）就是查这张表。
这就是 `getGlobal`/`getFunction` 这类 API 的物理真相。

## 4. fatbin 与 PTX：为什么二进制里要打包"源码"

### 4.1 直接看现象

```
一个 10 MB 的 fatbin 文件, NVCC 编出来的:
  ├─ cubin(Ampere 代)      ← 本代芯片直接跑
  ├─ cubin(Ada 代)
  ├─ cubin(Hopper 代)
  └─ PTX "源码"            ← 每次都要带
```

### 4.2 为什么必须带 PTX

SASS（机器码）只对**特定一代微架构**有效（ptxas 逐代优化）。但程序要跑在"未来还没出的芯片"上——你不可能为每代
芯片都编一个版本。解法：**打包 PTX，遇到新芯片运行时 JIT 重编**。

```
老 cubin ──► 新芯片 ──► 不能跑 ✗
PTX      ──► 新芯片上的 nvrtc/driver ──► 现场编译出新 SASS ✓
```

> **关键认知**：这里的 PTX 就是前面见过的 PTX——一个**稳定的
> 虚拟 ISA 层**。NVIDIA 的策略本质是：**承诺 PTX 的兼容，不承诺
> SASS 的兼容**。对自研芯片的启示：**定义你自己的"稳定中间层"
> （类 PTX 的伪指令集），用快速 JIT 适配新硬件**。你用 MLIR 建方言，就是为这一层铺路。

## 5. 运行时 JIT：`nvrtc` 背后发生了什么

```
应用程序(编译期没编过的 kernel)
   │
   ├── 路径 A: CUDA C 源码 ──► nvrtc(完整编译器: 前端 + 优化 + PTX 后端)
   │
   ├── 路径 B: PTX 字符串 ──────────────────────────┐
   ▼                                              ▼
driver JIT: PTX → SASS → cubin(可执行字节流)
   ▼
载入设备内存 → 解析 kernel 元数据 → 返回句柄
   ▼
cudaLaunchKernel(句柄, grid, block, 参数...)
```

两条路线的分工：**nvrtc 只吃 CUDA C 源码**（它是个完整编译器，
出 PTX）；**PTX 由 driver JIT 编译**（只做 PTX→SASS 这一步）。
运行时环境里塞的不是 nvrtc 一个东西，是"nvrtc + driver JIT"接力。

**运行时 JIT 的代价**：第一次启动比 AOT（预先编译）慢——每个
kernel 要现场编译几百毫秒到几秒。所以生态里处处有**缓存**：
编译结果按 (PTX 哈希, 芯片型号) 缓存到磁盘，第二次直接命中
（`CUDA_CACHE_PATH` 控制的位置）。

> **手算：JIT 缓存命中率的账**
>
> ```
> 500 个 kernel × 每个 JIT 编译几百 ms = 分钟级的首次启动开销
> 缓存 100% 命中 → 启动 ~0 ms
> 缓存过期(换驱动版本/芯片) → 全部重新编译
> ```
>
> 自研芯片的运行时设计里，**"缓存放哪、键怎么算、何时失效"**
> 是三个必须写进设计文档的字段——这是工程细节，但用户的
> 第一印象就来自这几百毫秒。

## 6. 对自研芯片：你要交付的四样东西

```
1. 指令编码规范    汇编文本 ↔ 字节 的对应(第25课 TableGen 帮你生成)
2. 镜像格式        你的 ELF 或自定义格式 + kernel 元数据段(第2节)
3. 加载器/驱动     解析镜像 → 载入设备内存 → 入口表查询(第30课)
4. 稳定中间层      "类 PTX"伪 ISA + JIT 编译器 + 缓存(第4/5节)
```

**验证清单（怎么做算完成）**：

| 项 | 验收 |
|---|---|
| 汇编器 | `写成文本 → 汇编 → 反汇编` 能还原成同一条指令 |
| 镜像格式 | 用 `readelf`-类工具能列出段和 kernel 入口表 |
| 加载器 | 加载一个 100-kernel 镜像并逐个取句柄，耗时 < 1 ms（示例验收线） |
| JIT | 改一行源代码 → 缓存失效 → 重新编译 200 ms 内（示例验收线：单个 kernel JIT 本就是几百 ms 量级，重编一次不应更慢） |

## 7. 课后答疑

**Q：为什么 GPU 不直接用 ELF，要搞 cubin/fatbin？**
A：**就是 ELF**（cubin 是一种 ELF 变体）。新增的是：kernel 元数据段、多代打包（fatbin 容器）、和"代码段特殊化"（SASS 不通用）。
你学过的 ELF 知识全部适用。

**Q：JIT vs AOT，自研芯片选哪个？**
A：**AOT 为主 + JIT 兜底**。AOT 快、可审计、省电；JIT 用于
"还没发布的芯片"和"热修复"。NVIDIA 是"双轨"：大多数路径 AOT
（nvcc 编好 cubin），JIT 只是胖二进制里的 PTX 备胎。

**Q：为什么 fatbin 这么臃肿？**
A：版本兼容的代价：多代 cubin + PTX 全打包。瘦身手段：
只带本代 cubin + PTX（启动时 JIT 一次），很多框架这么干。

**Q：kernel 元数据谁写的？**
A：**编译器**。元数据段存的是 regs/smem 等**占用率的输入**；
占用率依赖 grid/block 启动配置，由运行时按配置推出。
这就是"编译器决定、运行时执行"分工的实体化。

## 8. 本课小结

- 目标文件 = 代码段 + 数据段 + 符号表 + **kernel 元数据段**
- **重定位**把占位填成真地址（两遍链接：先排布、后填值）
- **fatbin = 多代 cubin + PTX**；PTX 是"稳定虚拟 ISA"的兼容层
- 运行时 JIT = 拿着 PTX 在设备上现场编译 + **按哈希缓存**
- 自研芯片四件套：指令编码规范 / 镜像格式 / 加载器 / 稳定中间层

## 扩展阅读：二进制层的三个工程问题

### A. ABI 与版本：兼容性的真实战场

驱动接口（`cuModuleLoad`、`cuLaunchKernel`）升级时，老程序还
必须能跑。业界做法：**版本号编码进二进制**（驱动查版本决定
行为）+ 接口"只加不改"。你的镜像格式必须留版本字段——第一天
定格式，第十年都改不动它。

### B. 代码段特殊化：为什么 SASS 不通用

ptxas 为每代芯片做寄存器重分配和指令选择（第 22 课）：同样一段
PTX，在 Ada 和 Hopper 上生成的 SASS 可能完全不同。所以"一个
SASS 通吃"不可能——这也逼出了"稳定中间层"策略。**你的芯片
换代时，SASS 契约断层是必然**，设计时就告诉大家"兼容只在
中间层"。

### C. 安全：可执行格式的信任边界

加载器要校验：镜像签名（防止注入恶意 kernel）、元数据越界检查
（防止恶意参数耗尽寄存器/内存）。自研芯片若做多租户（云），
**加载器的校验强度 = 你的安全底线**——这是专门的安全团队在审的东西。
