# 第 0 课：总览——一个模型是怎么被"编译"的

> 本课不写任何代码，只做一件事：让你脑子里装下一张完整的地图。
> 之后的每一课都是在把这张图放大、逐个房间走进去看。
> 学完本课，你应该能**用自己的话**给别人讲"编译器到底干了什么"。

---

## 0. 先回答一个"最基础但没人好好讲"的问题：为什么需要编译器？

你写的神经网络，比如 PyTorch：

```python
class Net(nn.Module):
    def forward(self, x):
        x = self.conv1(x)        # 卷积
        x = F.relu(x)            # 激活
        x = self.fc(x)           # 全连接
        return x
```

这段代码**本身不是来推理的，它是来"描述一个计算"的**。真正要跑在
GPU/CPU 上、每秒执行几千次推理的，是另一份东西——一份**针对具体硬件的、
极其啰嗦的、人不想写也写不出来的**代码。

**编译器的本质工作，就是完成这次"翻译"。**

- 输入：一个"计算的高层描述"（模型 / 计算图）
- 输出：一份"在目标硬件上高效执行的代码"

关键在"高效"二字。翻译谁都会，难的是翻得好：
- 同一个 `conv2d`，在 A100 GPU 上和在手机上，该生成的代码**完全不一样**
- 同一个模型，融合过和没融合过，速度能差 2~4 倍
- 同一个算子的内存排布错了，性能差一个数量级

所以编译器真正难的部分不是"翻译"，而是**优化**——在翻译过程中做出一大堆
"怎么算更快"的决策。这就是这门课的全部内容。

---

## 1. 一张总图：编译流水线的完整样子

```
  ┌─────────────────────────────────────────────────────────────┐
  │ 模型文件 (PyTorch / ONNX / 你的手写计算图)                     │
  └─────────────────────────────────────────────────────────────┘
                              │  第 1 步:前端导入(Frontend)
                              │  把它翻译成编译器的内部表示(IR)
                              ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  IR: 计算图                                                 │
  │    conv → add(bias) → relu → conv → ... → matmul             │
  └─────────────────────────────────────────────────────────────┘
                              │  第 2 步:一串 Pass 反复改写这张图
                              │  (每次改写都保证"算出来的结果不变")
                              ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  优化后的图                                                  │
  │    conv(融合了 bias+relu) → conv(融合了 bias+relu) → matmul    │
  └─────────────────────────────────────────────────────────────┘
                              │  第 3 步:代码生成(Codegen)
                              │  图 → 带循环的真实代码
                              ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  C 代码 / CUDA 代码 / 机器码  +  运行时                       │
  │    for (n...) for (oc...) ... { acc += ...; }                │
  └─────────────────────────────────────────────────────────────┘
```

注意整条链里**数据没变**——`x` 从输入到输出，一路算的都是同一份数据。
变的是**怎么算**：用几个核、内存怎么排、循环怎么写。

## 2. 三个阶段，各自回答一个"什么问题"

### 阶段一：前端（Frontend）——"这是什么模型？"

把 PyTorch/ONNX/你手写的图，翻译成编译器自己的内部表示（IR）。

我们的 toycc 没有"从 PyTorch 导入"这一步，因为我们的模型**直接用 Python 手写**
成计算图（`toycc/examples/model.py`）。真实编译器里这一步是最"枯燥"的，
因为要对接几十种框架格式。

### 阶段二：Pass 管线——"怎么算才快？"

这是一遍一遍**改写计算图**的流水线。每个 pass 读入一张图，吐出一张
"等价但更优"的图。我们的 toycc 里跑 4 个 pass：

| pass | 干了什么 | 一句话直觉 |
|---|---|---|
| 算子融合 | `conv + relu + bias` 并成一个 | 少跑几个核，少搬几次内存 |
| 布局优化 | 数据改成 NHWC 排法 | 让卷积在内存里"顺路" |
| 常量折叠 | 权重转换提前算完 | 运行时少干活 |
| 内存规划 | 让中间结果共用内存 | 内存省 70% |

**每个 pass 的铁律：结果必须和改之前一模一样。**
这条铁律是后面所有"验证"工作的来源，第 2 课会专门讲。

### 阶段三：代码生成（Codegen）——"最终长什么样？"

把优化后的图翻译成真的代码。我们的 toycc 生成两种：

- `out.c`：可在装了 gcc 的机器上编译成原生程序
- `out.py`：用纯 Python 循环复刻同一套计算，用来**验证**生成代码没算错

真实编译器这一步对应的是：图 → 底层 IR（TIR）→ CUDA 代码 / x86 汇编。

## 3. 拿我们真实跑出来的数字，把这张图"填满"

下面是我们这个项目里实际发生的事（你可以跑 `python -m toycc.examples.demo` 看）：

### 我们的模型（10 个算子）

```
conv1 → bias_add1 → relu1 → conv2 → bias_add2 → relu2 → reshape → matmul → bias_add3 → relu3
```

### 第一步：融合（10 个 → 4 个）

```
conv1+bias+relu  →  conv2+bias+relu  →  reshape  →  matmul+bias+relu
```

原来要"写 3 次中间结果、再读 3 次"，现在**在同一个核里算完直接出**。

### 第二步：布局（conv 改走 NHWC，只在边界搬数据）

```
x(NCHW) →[转 NHWC]→ conv1 → conv2 →[转回 NCHW]→ reshape → matmul
```

只插 2 次真正搬数据；中间整条链都继承 NHWC。

### 第三步：常量折叠（权重/偏置的转置在编译期算掉）

运行时剩下的算子只有 6 个，其中 4 个"权重转置"直接在编译期变成了常量。

### 第四步：内存规划（6 个中间张量 → 2 个缓冲区）

```
朴素方案(每张量独占):  848 元素
复用方案(峰值):        256 元素
内存节省:              70%
```

### 最后：生成代码，并验证

生成 `out.c` / `out.py`，跑出来和"参考执行器"的结果
`max|Δ| = 5.55e-17`（浮点舍入级别，等于完全一致）。

> 你马上会反复看到 `max|Δ|` 这个符号——它是全课的"对错判据"。第 2 课详解。

## 6. 常见误区 FAQ

**Q：编译器和解释器有区别吗？**
A：有。解释器（PyTorch eager 模式）是"跑到哪算到哪"，编译器是"先把整段计算
规划好再一次性执行"。编译器能看到的更多，所以能优化得更好。这正是 PyTorch
也有 `torch.compile`、ONNX Runtime 能做图优化的原因。

**Q：为什么不能直接让 PyTorch 跑，非要编译？**
A：可以跑（eager 模式就是），但慢。编译的收益来自全局优化：
跨算子的融合、内存复用、针对硬件的排布——这些都需要"看到整张图"。

**Q：编译一次是不是很慢？会不会每跑一次都编译？**
A：编译（包括优化）确实比推理慢几个数量级。所以工程上分两阶段：
**编译期**（一次，慢点没关系）和**运行时**（每次，必须快）。
你会在第 5 课（常量折叠）里再次看到这条分界线。

**Q：把图改来改去，怎么保证没改错？**
A：三个保险：① 每个 pass 都有数值验证（和参考结果对比）；② 大量测试图；
③ 形式化验证（生产编译器里才有）。我们的 toycc 用第 ① 种，第 2 课专门讲。

## 7. 本课小结 + 下一步

- 编译器 = 前端(导入) → Pass 管线(优化) → 代码生成(后端)
- 优化的是"怎么算"，不是"算什么"
- 三个词：**IR / Pass / 后端**
- 每个 pass 的铁律：**语义等价**

## 8. 深层拓展 A：把"编译期 vs 运行时"这条线彻底拉满

第 5 课会专门讲这条分界线，但你现在就该建立完整直觉。任何编译器决策，
问两个问题就能归类：

```
这个决定, 在"模型编译时"就能定下来吗?
   是 → 编译期决策(只做一次, 慢一点没关系)
   否 → 运行时决策(每次都做, 必须快)
```

举例：

| 决策 | 编译期还是运行时 | 为什么 |
|---|---|---|
| 要不要融合 conv+relu | 编译期 | 图是静态的, 融合规则是确定的 |
| 权重布局用 NCHW 还是 NHWC | 编译期 | 权重在编译时就已知 |
| 中间张量放哪个缓冲区 | 编译期 | 依赖静态生命周期分析 |
| x 是 (1,3,8,8) 还是 (1,3,100,100) | **运行时** | 输入张量运行时才知道 |
| 模型要走哪个分支 | **运行时** | 取决于当前输入 |

**最后两行是难点**：一旦有"运行时才知道"的信息，编译器就要**支持动态形状
/ 动态分支**，很多优化做不了。这也是为什么：
- 静态形状模型容易优化（TVM/ONNX 都爱它）
- 动态形状（NLP 里 batch 变化）是优化难点，Relax 正是为此设计的

> 记住这张表，第 5 课我们会在常量折叠里再次用到它。

## 9. 深层拓展 B：为什么 pass 能"任意组合、随便排"？

第 0 课我们把 pass 描述成"流水线上的工序"。但实际比流水线更灵活：
**你可以自由决定跑哪些 pass、按什么顺序跑**。为什么能这么自由？

三个设计保证：

1. **pass 无副作用**：每个 pass 输出一张**新图**，不改原图。
   所以"先融合再布局"和"先布局再融合"都合法——原图一直在。
2. **每个 pass 都保证语义等价**：任何 pass 之后，算出的结果都一样。
   所以 pass 组合不会累积错误（错误在 pass 内部就被验证拦住了）。
3. **pass 之间有依赖约定**：有些 pass 需要另一些先跑（比如布局 pass
   最好在融合后跑）。这通过"依赖声明"管理，不是硬编码顺序。

真实 TVM 里这个灵活性的体现：
- `relax.transform.Sequential([...])` 你可以自由传 pass 列表
- 每个 pass 有 `required`（前置依赖）声明，编译器帮你检查
- 你可以写一个**自定义 pass** 插进任意位置

**这就是为什么"编译器是插件化的"**：优化不是写死的，而是可以编排的
pass 集合。理解这一点，你就能理解 TVM 里大量"pass 组合拳"的讨论。

## 10. 深层拓展 C：亲手算一笔账——优化到底省了什么

不要停留在"融合很快"这种口号上，我们算一笔具体的账。

假设我们的模型：
- 每个中间张量读写一次要花 `T` 时间
- 融合前：conv → 中间结果 → relu，要**写一次 + 读一次**中间结果 = `2T`
- 融合后：直接算完 = `0T`

**融合省下 `2T`**，这 `2T` 是纯数据搬运，跟计算无关。在带宽受限的硬件上，
`2T` 可能比计算本身还大。

内存优化同理：第 6 课会算 `848 → 256`。这省下的是**设备内存占用**——
在端侧设备（手机/嵌入式），内存不够直接导致"模型跑不了"，比速度更致命。

**做题**：如果融合省掉 3 次中间张量的写+读，每次 `T=0.5ms`，
模型每秒推理 1000 次，融合一天省多少毫秒？

> 答案：`3 × 0.5ms × 1000 × 86400 = 1.3×10^8 ms ≈ 36 小时`。
> 这就是为什么编译器优化在部署场景"值钱"——量大时每次省一点都巨大。
