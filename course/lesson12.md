## 1. 一个重要的认知升级：编译器不只有"融合"

前几课我们把融合讲得很重，因为它是"性价比之王"。但真实编译器有**几十个
pass**，各自解决不同问题。这一课给你一张完整的"优化地图"，以后讨论时
你能说清"这个优化属于哪一类、和融合什么关系"。

按"优化的是什么"分四大类：

| 大类 | 优化的是什么 | 例子 |
|---|---|---|
| 1. 图结构 | 算子之间的关系 | 融合、合并、内联、DCE |
| 2. 计算本身 | 数学表达式 | 常量折叠、代数化简、CSE |
| 3. 数据排布 | 内存怎么放 | 布局、内存复用、存储重写 |
| 4. 执行方式 | 循环/线程怎么写 | 调度（第 11 课）、并行化 |

前 7 课你已经见过：融合（类1）、布局（类3）、常量折叠（类2）、内存（类3）、
调度（类4）。这一课补全**类 1 和类 2 剩下的**：DCE、CSE、代数化简、内联、
合并。

## 2. 亲手实现：死代码消除（DCE）——类 1 的代表

### 2.1 什么是死代码

**死代码 = 计算结果没人消费、也不是图输出的节点。** 它纯粹浪费：
编译产物变大、加载变慢。删掉它，结果不受任何影响。

看 `runner 12` 造的图：

```
conv1 = conv(x, conv1_w)
dead1 = relu(conv1)      ← 没人消费它
dead2 = sigmoid(conv1)   ← 没人消费它
out   = relu(conv1)      ← 图输出
```

`dead1`/`dead2` 就是死代码。为什么会出现？可能是某个 pass 改写后留下的
"孤儿"，也可能模型本身就带了没用上的分支。

### 2.2 读我们的 DCE 实现

```python
class DCEPass:
    def __call__(self, graph):
        g = graph.clone()
        queue = [n.name for n in g.nodes.values()]
        while queue:
            name = queue.pop()
            if name in g.outputs:
                continue                        # 图输出绝不能删
            node = g.nodes.get(name)
            if node is None:
                continue
            if not g.consumers(name):           # 没消费者 = 死代码
                g.remove_node(name)
                queue.extend(node.inputs)       # 它的输入可能因此也死了
        return g
```

**逐行**：
- 工作队列（BFS）：所有节点先排队检查
- **图输出永远跳过**——删了输出，整个编译就失败了
- `not g.consumers(name)`：没人读它 → 死
- 删除后，把它的输入加入队列：因为"它"死了，它的输入可能也因此没人用了

**为什么用队列而不是一遍扫描？** 这是**不动点（fixpoint）**思想：
删除一个节点会"释放"更多死节点，必须删到"再无可删"。
一遍扫描做不到，队列天然支持"删了 A，接着查 A 的输入"。

> **不动点**是编译器里反复出现的思想：pass 反复执行直到图不再变化。
> 很多优化都是"应用到稳定为止"。

### 2.3 验证

`python -m course.runner 12` 输出对比：DCE 前 5 个节点，DCE 后 3 个，
`dead1`/`dead2` 消失，输出还是 `out`，结果不变。

## 3. 类 1 的其它成员：合并 / 内联

### 3.1 合并（Combine）：把"并联"的算子并成一个

```
y1 = matmul(x, W1)      y2 = matmul(x, W2)      y3 = matmul(x, W3)
                ↓ 合并
Y = matmul(x, [W1;W2;W3])    # 权重横向拼接,一次算完
y1 = Y[:, 0:M];  y2 = Y[:, M:2M];  y3 = Y[:, 2M:3M]
```

**为什么省？** 一次 matmul 的启动/内存开销，摊到三个算子上；
GPU 上还能并行利用所有计算单元。TVM 有 `CombineParallelMatmul` 就是这个。

### 3.2 内联（Inlining）：把函数体展开到调用处

```
f(x) = x + 1
y = f(z)
        ↓ 内联
y = z + 1
```

省掉一次函数调用开销，还给后续优化（常量折叠、CSE）创造机会。
TVM 有 `InlineFunctions`。**融合其实也算一种"局部内联"**——把子算子
展开进父算子。

## 4. 类 2 的成员：代数化简 / CSE

### 4.1 代数化简（Simplify）：用数学恒等式消掉计算

```
x * 0 → 0                 (如果 x 安全)
x + 0 → x
a*b + a*c → a*(b+c)       (提取公因子)
(x*2) + x → x*3
(x > 0) ? y : y → y       (条件恒真)
```

**为什么省？** 有的化简直接减少计算量；更重要的是**给别的优化铺路**——
化简后的图更容易匹配融合 pattern。TVM 的 `SimplifyExpr` / 表达式化简器
在 `src/arith/` 里，是个巨大的规则库。

### 4.2 公共子表达式消除（CSE）：同一件事只算一次

```
y1 = a * b + c
y2 = a * b + d
        ↓ 提取公共子表达式
t  = a * b          # 只算一次
y1 = t + c
y2 = t + d
```

**什么时候有用？** 当 `a*b` 计算代价高（比如矩阵乘）且结果被多次使用时。
**注意**：CSE 不是白捡的——它增加一个中间变量（占用寄存器/内存），
所以编译器要权衡"省的计算" vs "多的存储"。TVM 有 `EliminateCommonSubexpr`。

## 5. op_pattern 系统：融合规则真正的"语法"

### 5.1 从 toycc 的手写规则到 TVM 的模式标注

第 3 课我们手写了融合规则：

```python
_POINTWISE = {"relu", "sigmoid"}
_BIASABLE = {"add"}
_ROOTS = {"conv", "matmul"}
```

**但 TVM 不是"给每个算子手动登记能不能融合"的**——算子有几千个。
它抽象出了 **op_pattern（算子模式）**，把算子按"计算形态"分类，
融合规则写成"模式之间的规则"。这样新增算子只要标一个 pattern，
融合规则自动适用。

### 5.2 五个 pattern 的含义（必须背下来）

| pattern | 含义 | 例子 |
|---|---|---|
| `kElemWise` | 输出每个元素只依赖输入**对应位置** | `relu`, `sigmoid` |
| `kBroadcast` | 逐元素 + 支持广播（输入可不等形状） | `add`, `mul` |
| `kInjective` | 每个输出一一对应一个输入（无计算，纯搬移） | `reshape`, `transpose` |
| `kCommReduce` | 归约：多个输入元素 → 一个输出 | `sum`, `maxpool` |
| `kOpaque` | 计算密集、不可分解 | `conv`, `matmul`, `batch_norm` |

### 5.3 融合规则 = 模式的"能吸收谁"

TVM 的 `AnnotateTIROpPattern` pass 给每个算子打上 pattern，
然后 `FuseOps` 按模式匹配规则分组。规则的直觉：

```
kElemWise/kBroadcast (逐元素)  → 能融进任何"祖先"核
kOpaque (计算根)               → 能当融合的"根"吸收下游
kCommReduce (归约)             → 只能当根, 不能吸收别人
kInjective (搬移)              → 通常作为融合边界(reshape/transpose 会挡)
```

**对照 toycc**：
- `_POINTWISE = {"relu","sigmoid"}` ≈ `kElemWise`/`kBroadcast`
- `_ROOTS = {"conv","matmul"}` ≈ `kOpaque`
- `reshape` 挡融合 ≈ `kInjective`
- 我们 toycc 没实现 `kCommReduce`（maxpool 是归约）

### 5.4 为什么模式化是必要的

想象：TVM 有 2000 个算子。手写"哪个算子能融进哪个"要 2000×2000 条规则。
模式化后：**规则数量 = 模式数量（5 个）**。新算子 `gelu` 标成 `kElemWise`，
立刻获得"能被融合"的全部待遇。这就是抽象的力量。

## 6. 支配分析：读懂 fuse_ops.cc 的最后一块拼图

第 8 课读 `fuse_ops.cc` 时，看到"后支配树"就过去了。现在补上
"支配"到底是什么——它是**编译器数据流分析的基石**，值得单独讲清。

### 6.1 支配（dominate）：谁是"必经之路"

在一张 DAG 里，如果**从入口到节点 Y 的所有路径都经过节点 X**，
就说 **X 支配 Y**（X dominates Y）。

```
       入口
       /  \
      A    B
       \  /
        C        ← C 的支配者是谁?
        |
        D
```

从入口到 C 有两条路：`入口→A→C` 和 `入口→B→C`。
两条都经过入口，所以**入口支配 C**。A、B 各自只经过一条路，所以**不支配 C**。

**支配的直觉**："X 支配 Y" = "只要 Y 执行了，X 一定已经执行过"。

### 6.2 立即支配者（immediate dominator）

每个节点（除入口）有**一个**特殊的支配者：它本身被所有其它支配者支配的那个。
它叫**立即支配者（idom）**。把所有 idom 边连起来，得到**支配树**。

```
       入口
      /    \
     A      B
      \    /
       C     ← idom(C) = 入口 (唯一支配 C 的)
       |
       D     ← idom(D) = C
```

### 6.3 后支配（post-dominate）：反向看

把上面的定义"反向"：如果**从节点 Y 到出口的所有路径都经过 X**，
就说 **X 后支配 Y**。

**为什么融合用后支配？** 回到融合的场景：我们想知道"一个算子 c 能不能
安全地融进它下游的算子"。如果节点 p 后支配 c（c 之后所有路径必经 p），
那么**c 算完，无论走哪条分支，最后都会到 p** —— 这时候把 c 的语义并进 p
是安全的，因为 p 是"必经汇合点"。

再看第 8 课那个菱形：

```
       conv2d
      /  |  \
     /   |   \
   op   op   op
    \    |    /
     \   |   /
     add       ← 三个 op 都必经 add → add 后支配它们
```

三个 op 都后支配于 add，所以 add 是"安全的汇合点"，融合规则可以覆盖整段。
**贪心（toycc）做不到这种全局判断，后支配树可以。** 这就是 TVM 选它的原因。

### 6.4 支配分析在其它地方

- **控制流优化**：删掉不可达代码（不被任何支配路径到达的节点）
- **循环分析**：找回边（循环检测）
- **代码提升**：把不变的代码移到循环外（loop-invariant code motion）

## 8. FAQ

**Q：为什么我的图里会出现死代码？我又没写死代码。**
A：大多数死代码是**其它 pass 产生的**：融合后有些中间节点没被用；
常量折叠后有些旧节点没被消费；内联后旧函数没人调。所以 DCE 通常是
管线里"收尾"的 pass。

**Q：CSE 和"复用"有副作用吗？**
A：有。它增加中间变量（多占寄存器/内存），有时反而更慢。
所以编译器里 CSE 是**可选的、有收益判断的**优化，不是无脑做。

**Q：为什么 `kOpaque` 算子不能"被吸收"只能"当根"？**
A：`kOpaque` 计算密集，把其它算子融进它，共享的只是"读一次输入"；
但如果把 opaque 融进别的算子，等于把它拆开，失去它"整块优化"的意义。
所以 opaque 只当根。

**Q：支配分析是运行时算吗？**
A：不。支配树是**编译期**在图/CFG 上静态算出来的，一次算好存起来复用。
它属于"数据流分析"家族，是整个编译器优化的地基。
