## 1. 先回答一个问题：工具链 = 编译器 + 什么？

很多人以为"工具链 = 编译器"。其实编译器只是工具链的一环。
一个完整的自研 GPU 工具链，通常长这样：

```
                        你写的编译器(TVM 风格)
  模型 ──> 图优化 pass ──> TIR 调度 ──> codegen ──> 汇编/kernel
                                                       │
              ┌─────────────────────────────────────────┘
              ▼
  ┌─────────────────────────────────────────────────────┐
  │                    编译器 (Compiler)                  │
  │   你的代码: 优化 + 生成可执行 kernel                    │
  └─────────────────────────────────────────────────────┘
              │
  ┌───────────▼──────────────┐    ┌──────────────────────┐
  │     汇编器 (Assembler)     │    │   链接器 (Linker)     │
  │  汇编 → 机器码/二进制       │    │  把多个模块拼起来      │
  └───────────┬──────────────┘    └──────────────────────┘
              │
  ┌───────────▼──────────────┐
  │     驱动 (Driver)         │
  │  和硬件对话: 分配内存/启动核 │
  └───────────┬──────────────┘
              │
  ┌───────────▼──────────────┐    ┌──────────────────────┐
  │     运行时 (Runtime)      │    │  性能分析器 (Profiler) │
  │  调度 kernel / 管理资源    │    │  测性能/找瓶颈        │
  └───────────┬──────────────┘    └──────────────────────┘
              │
  ┌───────────▼──────────────┐    ┌──────────────────────┐
  │     调试器 (Debugger)     │    │   SDK/文档/样例       │
  │  查崩溃/看变量/单步        │    │  给上层开发者用       │
  └──────────────────────────┘    └──────────────────────┘
```

**你的工作范围（通常）**：上半部分（compiler + assembler）+ 参与下半部分
（driver/runtime/profiler）的协作。

## 2. 各组件的"干什么"逐一拆解

### 2.1 编译器（Compiler）——你的主战场

前面 20 课全在讲它：模型 → 优化 → 代码。输入是高层图，输出是"目标代码"。

**你写的编译器输出什么**？两种可能：
- **C/CUDA 风格的源码**：交给你们的 C 编译器再编译（最省事）
- **直接出目标指令**：汇编级（更硬核，但性能可控）

> **原理深挖：输出"源码" vs 输出"汇编"，一个会改变一切的早期决定**
>
> 这是自研 GPU 芯片工具链的**第一个架构决定**，两条路各有代价，而且
> 直接影响后续每个组件的形状：
>
> **选 C 源码**（靠现有 C 编译器）：
> - 前端只需把 TIR 打印成 `for`/`if`/数组，**编译器难度最低**
> - 代价：底层细节交给 C 编译器——它不知道你的 GPU，做不出
>   合并访问、寄存器 bank 分配。最终性能天花板低
> - 适合：芯片和 x86 相似（CPU 类）、团队人少、时间紧的阶段
>
> **选直接出汇编/机器码**：
> - 编译器自己决定每条指令、每个寄存器、合并访问——**性能上限高**
> - 代价：必须**自己写汇编器**（把 `add r1,r2,r3` 变成字节），
>   以及完整的寄存器分配、指令选择（第 10 课 codegen 的全部，都要针对
>   你们芯片重做）
> - 适合：芯片有自定义 SIMD/张量指令，不走 C 编译器能拿到 10 倍性能差
>
> **一句话**：先想清楚"我的芯片的大部分性能差距，能不能靠 C 编译器补 上"。
> 能 → 输出 C 源码快速起跑；不能 → 从第一天就走汇编级。这个决定
> 会在你们的 roadmap 上占掉一整年的人力，所以**值得在最开始就用
> roofline（第 20 课）算清差距再拍板**。

### 2.2 汇编器（Assembler）——汇编 → 机器码

把"汇编代码"翻译成"机器码"（二进制）。每个硬件平台都需要。
- 如果你们芯片有 ISA 文档，汇编器照着它把 `add r1, r2` 变成二进制字节
- **自研芯片：汇编器是你必须写的**（用 LLVM 的 MC 框架能省很多事）

### 2.3 链接器（Linker）——把多个模块拼起来

一个程序可能分成多个编译产物（编译单元）。链接器把它们拼成一个可执行文件，
解决符号引用、地址重定位。**新手一般不用深写**，但要懂它是干嘛的。

### 2.4 驱动（Driver）——和硬件直接对话

驱动是"操作系统的插件"，负责：
- 分配 GPU 内存（`cudaMalloc` 就是调驱动）
- 把 kernel 发给 GPU 执行
- 处理中断、电源、内存管理

**编译器和驱动的接缝**：编译器生成"要执行哪些 kernel、
用多少资源"，驱动负责"真的去执行"。

### 2.5 运行时（Runtime）——面向开发者的那一层

开发者调用的 API（如 `cudaRuntime`、`tvm.runtime`）就是运行时。
它**打包调用驱动**：分配内存、启动 kernel、同步、错误处理。
你的编译产物要能被运行时"加载并执行"——这就是第 19 课的 VM。

### 2.6 性能分析器（Profiler）——第 23 课的核心工具

测性能、找瓶颈。自研芯片需要自己的 profiler（把硬件计数器暴露出来）。
**指标就是你学过的**：占用率、带宽利用率、指令 stall。

### 2.7 调试器（Debugger）——查崩溃、看变量、单步

让开发者能在 GPU kernel 里打断点、看变量。这是最难做的部分之一。

## 3. 怎么给 TVM 加一个新后端（你的芯片）——具体步骤

这是最直接的"上手动作"。TVM 的可插拔后端设计就是为此：

### 步骤 1：写 target 描述（target description）

告诉 TVM 你的芯片特性：

```python
# 概念示意, 真实是 TVM 的 Target 系统
target = tvm.target.Target({
    "kind": "my_chip",                # 芯片名字
    "max_threads_per_block": 512,      # 每块最大线程
    "warp_size": 32,                  # warp 大小
    "shared_memory_per_block": 96 * 1024,   # 共享内存
    "max_num_threads": 512,
    ...
})
```

**关键**：这些数字就是第 15 课 `hardware.py` 里那张表。
**你要填的就是这张表**。

### 步骤 2：写 codegen（TIR → 你的芯片指令）

实现 `relax.ext.my_chip` 的 codegen 函数：

```python
# 概念示意
@tvm.register_func("relax.ext.my_chip")
def my_chip_codegen(functions, options, constants):
    # 把 TIR PrimFunc 翻译成你们芯片的 kernel 代码
    # 这里做第 7 课/第 22 课讲的 codegen 事
    return compiled_modules
```

### 步骤 3：写运行时驱动（runtime driver）

让 TVM 的 VM 能调用你们的驱动：分配内存、启动 kernel。

### 步骤 4：跑 meta_schedule 搜调度

让 autotune 在你的芯片上搜出最优调度参数（第 13 课）。

### 步骤 5：写测试 + CI

参考第 17 课，为你的后端写测试，保证没人改坏。

## 4. 入职第一周：我该做什么？

**第一天**：
- 装好环境（附录 B）、跑通 TVM demo（第 9 课）
- 把 toycc 跑起来，每课跑一遍（`python -m course.runner N`）

**第 2~3 天**：
- 看公司的 target 描述文件（就是它，你们芯片的"硬件表"）
- 看一个现有的 kernel 是怎么生成/调度的
- 跑一个现有测试，改一个小地方，看测试怎么过/怎么挂

**第 4~5 天**：
- 认领一个 good-first-issue（公司内部的）
- 写一个最小的改动（改一个 pass 规则、加一个算子支持）
- 跑 CI、提 PR、请同事 review

**第二周**：
- 读你们芯片的 ISA 文档（汇编级）
- 跑 meta_schedule，看怎么在你的芯片上调参
- 提一个真正的 PR

## 5. 术语表（补充，工具链/芯片场景专用）

| 词 | 含义 |
|---|---|
| ISA | Instruction Set Architecture，指令集架构（汇编级规范） |
| microarchitecture | 微架构（ISA 的具体硬件实现） |
| codegen | 代码生成（TIR → 目标代码） |
| MC | LLVM 的 Machine Code 层（写汇编器的框架） |
| BYOC | Bring Your Own Codegen，外部后端接入 |
| RPC | 远程过程调用（编译产物发到真实设备） |
| occupancy | 占用率（活跃 warp / 最大 warp） |
| coalescing | 合并访问（32 线程读连续地址） |
| divergence | 分支发散（warp 内不同路径） |
| spill | 寄存器溢出（装不下写回内存） |
| workload | 工作负载（一个要编译的算子/模型） |
| golden | 参考/金标准（对验证正确的实现） |

## 6. FAQ

**Q：我是不是要写一个完整的新编译器？**
A：**不是从零写**。TVM 已经把"图优化 + 调度 + 前端"做完了，
你要写的是**最后一公里的后端**（codegen + target 描述 + runtime 驱动）。
这就是为什么这门课先学 toycc 的"图 + 后端"——你就是来干"后端"这段的。

**Q：自研芯片起步，先做什么最值？**
A：**target 描述 + codegen 出 C**（路线 A）。先有"能跑通"的后端，
再谈性能。别一上来就写汇编器。

**Q：我的 LLVM 后端（如果有）和 TVM 后端冲突吗？**
A：不冲突。LLVM 后端出通用机器码，TVM 后端出"AI kernel"。
两者甚至能共存：TVM 负责 AI 优化，LLVM 负责 CPU 侧指令。

**Q：我需要懂硬件到什么程度？**
A：能看懂 ISA 文档、知道共享内存/寄存器/warp 的限制、
能填 target 描述的数字。**不需要设计硬件，但需要"读懂硬件"。**

## 深层拓展：自研芯片工具链的三个"坑"

### A. "能跑通"和"能用"之间隔着什么？

你按第 24 课五步做出来一个后端——**它能跑通，但不一定能用**。
差距在哪：
- **性能**：跑通了但比手工慢 10 倍
- **覆盖度**：只支持 10 个算子，真实模型有 50 个
- **稳定性**：边界 case 就崩
这三件事，每一件都是数月的工作。**"能跑通"是 20%，"能用"是剩下 80%**。

### B. 为什么工具链要"先出 C 再出汇编"？

直接从 TIR 生成你们芯片的汇编，看似"一步到位"，但**调试极其痛苦**——
汇编错了你没法 printf。**先出 C 源码，用你们已有的 C 编译器验证逻辑**，
逻辑对了再下沉到汇编。这是所有自研芯片团队的"血泪经验"。

### C. 工具链的"版本兼容"怎么考虑？

你们芯片会换代，工具链也会更新。**如果 V1 的编译产物在 V2 上跑不了，
用户会疯**。所以要么像 PTX 那样搞"抽象中间层 + 每代汇编器"，
要么提供"版本转换工具"。**这是工具链设计里最被低估的一环**。
