# 第 30 课：驱动与命令提交——编译器到硬件的最后一步（命令缓冲、门铃、GPU MMU）

> 本课风格：概念 + 手算 + 自研芯片的交付清单。
> 目的：搞懂"运行时把编译产物交给硬件"的完整机制：
> 命令如何提交、内存如何管理、开销从哪来。
> 前置：第 24 课（工具链全景）、第 29 课（二进制与加载）。

---

## 1. 系统分层回放：24 课盒子的内部

第 24 课给了 driver/runtime 的盒子，本课讲"盒子之间传什么"：

```
应用程序 / AI 框架
   │ 运行时 API (cudaLaunchKernel / tvm runtime)
   ▼
用户态库 (libcuda / libtvm_runtime)
   │ IOCTL(系统调用)  ← 命令批里唯一一次进内核
   ▼
内核态驱动 (GPU 驱动)
   │ 命令缓冲 → 门铃
   ▼
GPU 硬件 (命令前端硬件 → SM)
```

关键事实：**每发一个 kernel，几乎全在用户态完成**（命令构造、
参数打包都是写内存），只有最后一步"通知 GPU"通过一次系统调用。
这是 GPU 高性能的密码之一——**批量构造 + 少切内核态**。

## 2. 命令提交：CPU 怎么"叫醒"GPU

### 2.1 命令缓冲（command buffer）

CPU 在共享内存里构造命令描述（GPU 侧有命令队列结构）：

```
一条 kernel launch 命令(命令缓冲里的一个条目):
  [CMD_LAUNCH]  kernel_handle=0x1F   ← 第29课入口表查到的
                grid=(128,1,1) block=(256,1,1)
                param_ptr -> 参数块
                stream_id=3           ← 第3节
```

GPU 侧有"命令前端"（command frontend）硬件持续扫描命令队列，
读到 CMD_LAUNCH 就分发到空闲 SM。

### 2.2 门铃（doorbell）

CPU 写完命令后，往 GPU 的一个**特殊 MMIO 地址写一个值**（门铃）：
"队列有新命令了"。GPU 收到门铃才去看队列——避免轮询浪费。

> **手算：门铃 vs 轮询的能耗账**
>
> ```
> 每秒 50 万个 kernel:
> 轮询: GPU 每 100 ns 查一次命令口 = 每秒查 1000 万次
>       每次查询都要唤醒命令前端 → 巨量无效功耗
> 门铃: GPU 空闲时完全静默, 命令到达才醒来 → 功耗趋近于 0
> ```
>
> 所以业界标配门铃。你的芯片手册同样要定义：门铃地址、
> 写门铃的语义（写值=序号，防丢命令）、多队列怎么分配。

### 2.3 命令流是"程序"吗

命令队列本质是**硬件执行的微程序**：有 [CMD_LAUNCH]、
[CMD_MEMCPY]（拷贝）、[CMD_WAIT_EVENT]、[CMD_BARRIER] 等指令。
第 17 课 VM 的指令流（alloc_tensor / call_tir / kill_tensor）
在这里有了"硬件执行版"。**GPU 工具链工程师设计命令格式时，
借鉴的就是编译器设计 IR 的那套思路**——第 26 课 MLIR 的
方言设计哲学可以直接复用。

## 3. context / stream / event：并发执行的编排

### 3.1 三个概念

- **context（上下文）**：隔离的执行域——自己的页表、内存、
  模块集合。多进程（多租户）靠 context 隔离资源。
- **stream（流）**：一个**有序命令序列**。同流内命令保证顺序；
  不同流之间**互不保证顺序** → 可并行执行。
- **event（事件）**：跨流的同步点（第 28 课 4.3 节）。

### 3.2 手算：两个流怎么重叠

```
流 A:  [kernel K1 耗时 3ms]   [K3 2ms]
流 B:           [K2 耗时 3ms]        [K4 2ms]
(SM 数量足够, K1/K2 不互相挤占资源)

串行排: 3+3+2+2 = 10 ms
按流并行: 3+2 = 5 ms        ← 一半时间里两个 kernel 同时在跑
```

**条件**：K1 与 K2 竞争同一资源（都占满 SM）就重叠不了；
小 kernel 的重叠收益最明显。这是第 23 课"小 kernel 慢"的
另一个答案：**等待 + 串行**——流就是"让不同的 kernel 并行等"。

### 3.3 编译器怎么参与

第 17 课 VM 若支持异步执行，**指令流里要显式编码 stream 与
event 操作**（launch 带 stream 号、record/wait event）。自研芯片
运行时的"流表"和"事件表"是两张核心数据结构——**要写进驱动设计文档**。

## 4. GPU 内存管理：MMU、页表、惰性分配

### 4.1 GPU 有自己的 MMU

GPU 不是"直接读物理内存"，它有自己的 **MMU + 页表**（device
page table）：每个 context 一份，把"GPU 虚拟地址"映射到
物理页（设备显存或系统内存）。好处：**隔离 + 惰性分配 +
统一寻址（UVA）**。

### 4.2 cudaMalloc 背后到底做什么（手算开销）

```
cudaMalloc(100MB):
  1. 驱动: 保留 100MB 虚拟地址空间    (快, 只动页表描述)
  2. 物理页: 惰性分配!                (不立刻建页)
  3. 首次内核访问 → 缺页 → 驱动现场分配物理页 (page fault)

所以: 10 万次 cudaMalloc(小量) 慢在哪?
  每次都要驱动调用 + 页表操作 + 可能的缺页处理
  ≈ 2~5 us × 10万 = 200~500 ms  → 比 kernel 本身还贵!
```

> **手算结论**：**频繁分配是最常见的性能陷阱**。解法：**内存池
> 预先分配**（一次大 malloc 反复复用）——这是第 6 课"内存规划
> 省内存"思路在运行时层的兄弟：编译器层面省"峰值用量"，
> 运行时层面省"分配次数"。

### 4.3 跨越 host/device：统一寻址（UVA）

UVA 下，CPU 指针和 GPU 指针在**同一个虚拟地址空间**：内核访问
"系统内存地址"时，驱动自动做 PCIe DMA；缺页时自动迁移数据
（HMM 模型）。好处是编程简单；代价是**隐式同步**（迁移时有
stall）——高性能代码仍用显式拷贝 + pinned 内存。

## 5. 手算：launch 开销 vs kernel 时长——小 kernel 被谁吃死

```
固定开销(每 launch):
  用户态命令构造   ~1 us
  系统调用         ~1~3 us
  门铃 + 硬件响应  ~0.5 us
  ────────────────
  合计固定 ~3~5 us

如果 kernel 本身只跑 2 us:
  实测吞吐 = 2 / (5 + 2) ≈ 28%  ← 70% 的时间在"发射"没在"算"
```

**解法**（按成本从低到高）：
1. **持久 kernel**：kernel 里有循环，一次发射吃掉所有数据
   （persistent kernel / megakernel）
2. **命令合并**：批处理多个小任务进一条命令（cuGraph 图执行）
3. **编程模型升级**：把"成千上万个小 kernel"改成"几个大 kernel"——
   这就是编译器图优化的任务（第 3 课融合在这里产生了运行时收益）

> **与课程闭环**：第 3 课融合"省了启动开销"这句话现在才算落地——
> 每融合掉一个 kernel，就省掉一次 3~5 us 的发射。算一笔账：
> 模型里 500 个算子，融合率 80% → 剩 100 个 launch → 省 400 × 3.5 us
> ≈ 1.4 ms/次推理。**融合的收益，一半在编译器里，一半在这里**。

## 6. 遥测：性能计数器 → profiler

第 23 课的 profiler 数据从哪来？——**硬件性能计数器（PMC）**：
SM 里的专用寄存器记录：指令发射数、内存事务数、stall 原因、
cache 命中率。驱动把它暴露出来：

```
应用 → profiler 工具(ncu) → 驱动接口 → 读 PMC 寄存器
                              ▲
                        内核在被分析时, 驱动要
                        "打开计数 + 定时快照 + 传回 host"
```

**自研芯片的 PMC 设计**是硬件+软件一起定的：计数器放哪几个、
能同时数几个事件、profiler 怎么配置（第 23 课 3.3 节读的指标
全是这里出来的）。没有 PMC，profiler 就是摆设——这也是工具链
的一部分，别等流片后补。

## 7. 自研芯片的驱动/运行时交付清单

```
1. 命令格式    CMD_LAUNCH/MEMCPY/EVENT/BARRIER + 队列组织(第2节)
2. 门铃机制    地址/写值语义/多队列(第2.2节)
3. context    每进程隔离: 页表+内存+模块句柄(第3节)
4. stream/event  有序序列+跨流同步(第3节)
5. 内存管理    MMU 页表 + 惰性分配 + UVA/HMM(第4节)
6. 遥测        PMC 计数器 + profiler 接口(第6节)
7. 错误路径    缺页/非法 launch/超时 → 可诊断的错误码(第8节 FAQ)
```

**每项的验收标准**（全部可执行）：

| 项 | 验收 |
|---|---|
| 命令格式 | 冒烟测试：同一批命令按两种顺序执行，结果一致 |
| 门铃 | launch 500 个 kernel，无丢命令（序号校验） |
| context | 两个进程同时跑，互不可见对方内存（页表隔离） |
| 内存 | 10 万次小分配，池化前后耗时差 100 倍级 |
| 遥测 | profiler 能看到每个 kernel 的发射数/访存数 |
| 错误 | 越界 kernel 报出"哪条命令、哪个参数"的错误 |

## 8. 课后答疑

**Q：为什么要有"用户态驱动"和"内核态驱动"两层？**
A：**频繁操作走用户态**（命令构造/内存池），**特权操作走内核态**
（页表切换/中断/映射系统内存）。三层封装（runtime→用户库→内核）
的每一层都是为了减少系统调用。新硬件甚至把命令提交完全做到
用户态（user-mode queue），内核只做初始化。

**Q：多 GPU / 多进程怎么隔离？**
A：每个 context 一张页表（第 4.1 节）。GPU 的地址翻译按
"当前 context 的页表"走——这就是硬件上下文切换。虚拟化
（VM 直通）也是同一套：给虚拟机一张页表 + 一块显存。

**Q：kernel 崩溃了怎么查？**
A：分两层：**驱动层**（校验 launch 参数、缺页、非法内存访问 →
返回错误码）+ **调试器层**（断点/单步，第 24 课 debugger）。
公司里 90% 的"GPU bug"其实是"驱动 报的错没看"。

**Q：门铃写值丢了怎么办？**
A：门铃写值带**单调递增序号**（第 2.2 节）：GPU 发现序号跳变
= 丢了命令 → 报错重放。命令队列还有"队尾指针回写"机制让 CPU
确认"GPU 真的消费完了"——**每层不可靠都要有协议层面的应对**。

## 9. 本课小结

- 命令提交 = 用户态构造 → 一次系统调用 → 门铃唤醒 GPU
- context 隔离 / stream 并行 / event 同步，是运行时编排的三件套
- GPU 有**自己的 MMU 页表**：隔离 + 惰性分配 + UVA
- 频繁分配、小 kernel 发射，是运行时层最贵的两个陷阱
- 性能计数器（PMC）→ profiler 的所有指标来源
- 自研芯片交付七件套 + 每项验收标准

## 扩展阅读：驱动层的三个工程问题

### A. 用户态队列（user-mode queue）是趋势

老方案每次 launch 都进内核（慢）；新方案把命令队列放在共享内存，
CPU 直接写队列 + 写门铃，**零系统调用**（如 NVIDIA 的 UMQ、
AMD 的显式同步）。自研芯片要评估：你的门铃/队列设计能不能支持
\"完全用户态路径\"——这是推理延迟竞争的决定性细节。

### B. 错误恢复：GPU 比 CPU 更怕"挂"

CPU 单核崩溃 → 核心转储重启线程。GPU 一个 kernel 非法访存
可能**带崩整个上下文**（显存被写坏）。所以驱动要有：kernel
超时/看门狗、context 回收、状态恢复（重放命令）。嵌入式场景
（车规）还要热重启。**错误路径设计 = 交付前的最后一关**。

### C. 进程优先级的公平性

共享 GPU 时，一个占满 SM 的进程会饿死别人。驱动做**时间片 +
优先级 + KILL 策略**。你的多租户方案（虚拟机/容器）要不要
时间片，取决于命令前端硬件是否支持"抢占"。这是芯片定架构时就
该决定的——写到第 21 课那种硬件规格表里。
