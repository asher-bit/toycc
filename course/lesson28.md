# 第 28 课：GPU 内存模型与并发原语——"同时跑"不是"随便跑"（原子、fence、同步层级）

> 本课风格：概念 + 手算 + 对照自研芯片的指令清单。
> 目的：搞懂 GPU 上"数据竞争怎么发生、靠什么原语避免"，
> 以及编译器面对多线程时必须遵守哪些规则。
> 前置：第 22 课（SIMT 编译）、第 27 课（模拟器——本课的实验都跑在它上面）。

---

## 1. 缺口：前面 27 课缺的那一半"并发"

第 22 课讲了 SIMT 的"意面"：32 个线程锁步执行同一指令流。
但"同时跑"还有一个问题没讲：**线程之间共享数据时，谁保证结果对？**

```
warp 0:  counter = counter + 1      ← "同时"执行
warp 1:  counter = counter + 1      counter 最终是 1 还是 2?
```

普通指令不是原子的：`counter + 1` 分三步——读旧值 → 加 → 写回。
两个 warp 交叠执行时，可能都读到旧值 0，各写回 1——**丢了一次更新**。
这一课补上"对一个多线程芯片，指令集必须提供什么、编译器必须生成什么"。

> **为什么不早讲**：toycc 是单线程的，第 2 课参考执行器天然无竞争
> ——所以前 27 课不需要。但你的自研芯片是**多 SM、每 SM 多 warp**，
> 内存模型是 ISA 设计中第一批就要定的东西。

## 2. 数据竞争与原子操作

### 2.1 手算：一次"丢更新"

```
共享地址 X 初值 0, 两个线程各执行 X = X + 1:

线程 A: 读 X=0 ──► 算 1 ──► 写 X=1       交错:
线程 B:             读 X=0 ──► 算 1 ──► 写 X=1
       X 最终 = 1   (正确应为 2)          ← 丢了一次更新
```

机器码视角（第 22 课的 load/store 风格）：

```
ld.global r1, [X]     ← 必须"读-改-写"连成一体才安全
add      r1, r1, 1
st.global [X], r1
```

普通 `ld/add/st` 三条约指令之间，另一 warp 可以插入任意操作。
**原子指令（atomic）把"读-改-写"在硬件里做成不可分割的一步**：

```
atom.add.global [X], 1      ← 一条指令完成全部三步, 硬件串行化冲突
```

### 2.2 手算：原子指令的代价

```
1000 个线程对同一地址原子加 1:
无原子:  约 1 个周期/线程, 但有竞争 → 结果是错的(约几百)
有原子:  冲突的原子操作在 L2 原子单元排队执行,
        1000 个操作 ≈ 1000 × 排队延迟(每跳 ~30 周期) ≈ 3 万周期
```

结论：**原子操作保正确、但把并行降成串行**。所以 kernel 设计
永远遵循"能不进原子就不进"：先各自算局部结果（每线程私有累加），
最后合并一次（reduction）——这就是第 23 课 matmul 分块累加器的道理。

### 2.3 ISA 里出现的是哪些原子

```
atom.add  / atom.sub  / atom.max / atom.min   (算数类)
atom.cas / atom.exch                          (比较交换, 万能原语)
atom.and / atom.or  / atom.xor                (位运算类)
```

`atom.cas`（compare-and-swap）最重要：任何复杂更新（链表插入、
引用计数、锁）都能用 CAS 循环拼出来。自研芯片 ISA 至少要定
**add + cas + exch + max/min** 这五个。

## 3. 内存序：为什么 GPU 用"弱内存序"

### 3.1 什么是内存序问题

原子操作保证"这一步不可分割"，但**两个线程的两个独立原子操作，
谁先谁后没有保证**：

```
线程 A:  atom.add [flag], 1         线程 B:
         st [data], 42                 loop: 读到 flag==1 才继续
                                       然后读 [data]  ← 可能读到旧值!
```

硬件上：`st [data]` 可能还在缓存/写回队列里，而 `atom.add [flag]`
先到了 L2——B 看到 flag=1 却看到 data 是旧的。**对同一地址的重排
不会发生（地址一致性），但不同地址之间的顺序没有保证**。

### 3.2 手算：重排是怎么发生的

```
线程 A 发了两个操作:
  st.global [data], 42        ← 走写回队列, 可以晚点落地
  atom.add  [flag], 1         ← 原子操作直达 L2

硬件视角: L2 先收到 flag 的原子(它被"插队"了),
         data 还在写回队列排队 → 顺序 = flag 先, data 后
```

要阻止这种插队，需要 **fence（内存屏障）**：fence 之前的访存
全部生效之后，fence 之后的操作才允许开始。

```
线程 A:                           线程 B:
  st.global [data], 42               loop: ld [flag]  (普通读)
  fence.release      ← 屏障            fence.acquire
  atom.add [flag], 1                  读 [data]  ← 现在保证是最新
```

`release`（发布）：我发布的数据，你先看到 flag 就能看到全部。
`acquire`（获取）：我看到 flag 更新，就等于看到了对方发布的全部数据。
**release/acquire 成对出现**，这是所有现代内存模型的通用语言
（C++ memory_order、Rust、GPU 的 `.release/.acquire` 修饰符都是它）。

> **为什么 GPU 用弱内存序而不是像 x86 那样"强"**：
> x86 为了让程序员省心，硬件每条访存都默认严谨（TSO 模型），
> 代价是**每条访存都要做额外的同步检查，慢**。GPU 追求吞吐，
> 把"要不要严格"的选择权交给程序和编译器：**默认宽松 → 快**，
> 需要保证的地方显式写 fence/原子修饰 → 程序员自己买单。
> 弱内存序 = 吞吐优先的设计决策，不是硬件的缺陷。

## 4. GPU 同步原语的四个层级

按协作范围从局部到全局，原语一层一层变"重"：

| 层级 | 原语 | 语义 | 开销 |
|---|---|---|---|
| 线程内 | 无 | 单线程天然顺序 | 0 |
| warp 内 | `__syncwarp` / shuffle 配合 | warp 锁步执行, 只需防编译器重排 | 很小 |
| block 内 | `bar.sync`(`__syncthreads`) | 全 block 线程到齐才放行 | 中等 |
| grid 级 | cooperative groups `grid.sync` | 全 grid 线程同步 | 大(依赖硬件支持) |
| host-GPU | event | CPU 等 GPU / GPU 等 CPU | 最大(见 4.3 事件) |

### 4.1 bar.sync 的语义与死锁

`bar.sync` 的做法：每个线程到达屏障后**等待**，直到同 block 的
**所有线程都到达**，然后一起放行（block 内线程数由 `blockDim` 决定）。

> **手算：bar.sync 死锁是怎么写出来的**
>
> ```
> 一个 block 64 线程, 代码:
>   if (tid % 2 == 0) {
>       ... 做一半 ...
>       __syncthreads();     ← 只有偶数线程到达!
>   }
>   ...共用数据...             ← 依赖屏障后的数据?
>
> 结果: 32 个奇数线程永远等不到"全部到齐" → 整个 SM 卡死
> ```
>
> 规则：把 `bar.sync` 放在**所有线程必然经过的路径**上
> （条件分支外的公共点）。编译器不会替你检查——
> **死锁是程序员责任**，而这正是 GPU 调 bug 最大的坑之一
> （cuda-gdb 断到"卡在 bar 上"基本就是死锁）。

### 4.2 屏障 = 编译器的一堵墙

bar 不只是硬件等待，还约束**编译器**：跨越 bar.sync 的访存
**不允许互相重排**（第 22 课说过编译器会重排访存来隐藏延迟）。
对优化 pass 的含义：屏障是**依赖图里的墙**——第 12 课学的依赖分析，
遇到同步点必须"墙外不能搬进墙内"。写后端/调度 pass 时，
"别把访存搬到 bar 对面"是一条必须写进代码的规则。

### 4.3 host↔GPU 同步：事件（event）

CPU 和 GPU 之间怎么同步？——**事件 + 流（stream）**，第 30 课详讲。
这里给结论：`event.record`（GPU 测打个标记）→ CPU `event.wait`
（阻塞直到 GPU 执行到那个标记）。类似的还有 `stream.synchronize`。
**这些也是编译器要生成的**——第 17 课的 VM 若加"异步执行"，就得
在指令流里编码 event 操作。

## 5. 对照 toycc / 自研芯片：你的 ISA 要定哪些原语

给自研 GPU 写 ISA 文档时，**内存模型这一章**长这样（清单）：

```
1. 原子指令集:   atom.add / cas / exch / max / min/ and/or/xor
                 在哪些地址空间可用? (全局+共享都要)
2. 内存序修饰:   每个原子可带 .relaxed/.acquire/.release/.acq_rel
                 普通访存默认 .relaxed(宽松) —— 快
3. fence 指令:   membar.gl / membar.sys(全芯片级, 最贵)
4. 同步指令:     bar.sync(block 内)  + 可选的 grid 级同步
5. host 同步:    事件/信号量(驱动层, 第 30 课)
6. 编译器义务:   pass 不得跨同步点重排访存(写进后端文档)
```

**这些原语在模拟器里也要实现**（第 27 课）——差分测试要专门
为并发生成"随机交叠"，这是并发 bug 比单线程 bug 难抓 10 倍的原因。

## 6. 课后答疑

**Q：`__syncthreads` 为啥比普通指令慢这么多？**
A：它要等"全 block 最慢的线程"，还要做硬件级同步计数；
而且它把编译器对访存重组的能力废了一半（墙）。**够用就行，
别同步强迫症**——很多新手每两行就 sync 一次，性能直接腰斩。

**Q：我没写任何原子/屏障，程序也对了，为什么？**
A：运气。单个 warp 内锁步执行确实像"顺序的"，但跨 warp、
跨 SM、涉及共享内存写后读时，没有同步就是**未定义行为**——
今天对不代表明天对。kernel 换调度参数就可能炸。

**Q：GPU 的全局内存是"缓存一致"的吗？**
A：**L2 这一层是全局一致点**（所有 SM 的写都要回到 L2），
但 SM 私有 L1 不自动失效。所以"写共享变量 → 别人立刻读到"
没有保证——这恰恰是 fence/原子存在的理由（见本课的扩展阅读 A）。

**Q：原子操作影响性能，那自研芯片的原子单元放哪？**
A：放 **L2**（全局一致点）做原子合并/串行化，是业界标准做法。
共享内存的原子则由 SM 内单元处理。这决定了你的内存层次设计
（第 21 课）和模拟器的 L2 建模（第 27 课）。

## 7. 本课小结

- 普通"读-改-写"不是原子的 → **原子指令**把三步做成一步，
  代价是冲突串行化
- GPU 用**弱内存序**：默认宽松换吞吐，需要时用 release/acquire 对
- 同步原语分四级：warp / block(bar.sync) / grid / host(event)
- bar.sync 必须放在**全员必经路径**，否则死锁；它是编译器的"墙"
- 自研芯片 ISA 的内存模型章 = 原子集 + 内存序 + fence + 同步 + host 事件

编译产物从"模拟器里的指令流"变成"能加载的二进制"，中间要经过
重定位、格式设计、运行时 JIT——那是编译器的"最后一公里"。

## 扩展阅读：内存模型的三个深层问题

### A. 为什么 GPU 的 L1 可以不一致

CPU 的 L1 缓存一致（硬件自动失效）——因为 CPU 假设程序乱共享。
GPU 设计成：**只有 L2 一致，L1 不跨 SM 共享**。代价是程序员要用
fence/原子显式声明；收益是 L1 不用做一致性协议（省芯片面积）。
这是"吞吐优先"路线在缓存系统上的贯彻，和弱内存序是同一笔账。

### B. 从 x86(TSO) 到 GPU(弱序)：越强越慢

x86 的 TSO 模型下，写操作不会晚于后续操作被看到（store buffer
前推），硬件做了一大堆保证。RISC-V/ARM 的默认弱序与 GPU 类似。
**移植到新芯片的程序最容易出 bug 的地方就是内存序假设**
——x86 上"碰巧对"的代码换到弱序芯片上立刻炸。

### C. 自研芯片的"一致性层次"是架构决策

原子在 L2 做 → 跨 SM 的原子慢、同 SM 共享内存原子快。编译器据此
决定"归约放哪个池子"。这个"哪层一致"的决策直接决定你 kernel
库（第 23 课）能写多快——设计 ISA 时就要想清楚，别流片后才发现。
