# GPU 第 10 章：GEMM 优化案例——从 30% 到 85% 峰值的分步证据链

## 1. 本章目标

- 看完一个真实形状的优化过程：每一步都有"现象 → 证据 → 改动 → 收益"四件套，而不是只给结论；
- 把第 1~7 章的账（合并访问、bank conflict、occupancy、spill、roofline）连成一条优化流水线；
- 学会"优化顺序"：先归因再动手、一次一个变量、每步用数字验收；
- 能独立把同样的流程套到任意一个新 kernel 上。

前置：第 1 章（访存/occupancy）、第 3 章（寄存器/spill）、第 7 章（profiler 协议）。本案例数字为 Ampere 上 fp16 4096³ GEMM 的**示例值**（相对关系真实，绝对值随机器变化）——重点是证据链的形状，不是背诵数字。

## 2. 起点：一个"朴素但正确"的 GEMM

```text
起点实现: 每线程算 C 的 1 个元素, 三重循环, 全局内存直接累加
基线测量: 30% 峰值(fp16 Tensor Core 口径)
```

第一步永远是**确认正确**（对照 cuBLAS 结果，max|Δ| < 1e-2 量级），再开始谈速度——第 2 课"参考执行器当裁判"的纪律原样适用。

## 3. 六步优化：现象 → 证据 → 改动 → 收益

### 第 1 步：合并访问（第 1 章第 7 节）

```text
现象:  基线只有 30%
证据:  ncu 的 DRAM 部分显示访问事务数是理想的 ~8 倍
归因:  朴素实现按列取 B, 每个 warp 的访存落到 32 条 cache line
改动:  线程映射改成行主序访问(每线程连续取元素)
收益:  30% → 45%
```

手算对照：一个 warp 读 128 B 连续数据 = 1 条 cache line；按列 = 32 条（第 1 章 7.2/7.3 节的账）。**证据先行**：ncu 里事务数下降，收益才随之而来。

### 第 2 步：共享内存分块（第 4 章第 4 节）

```text
现象:  45% 后卡住, DRAM 吞吐接近上限
证据:  roofline: 每元素仍从 global 读 K 次 A 元素 → 带宽墙
改动:  A/B 各载入 shared tile(BLOCK_M×BLOCK_K), 复用 tile 内数据
收益:  45% → 62%
```

手算对照：无分块时算术强度 ≈ 0.5 FLOP/B（第 4 章 3.1 节）；分块后 DRAM 只搬运每份数据一次，强度跃过拐点——**这一步是"带宽受限 → 算力受限"的转折点**。

### 第 3 步：bank conflict 与 padding（第 1 章第 8 节）

```text
现象:  62% 但 ncu 的 shared 部分波形有规律尖峰
证据:  数格子: tile 行宽 32 个 float, 按列取 shared 时全撞同一 bank
改动:  shared tile 行宽加 1 列 padding(32 → 33), 或改取数顺序
收益:  62% → 70%
```

手算对照：`s[k][0]` 的 bank = `(32k) mod 32 = 0` → 32 路冲突；padding 后 `(33k) mod 32 = k` → 无冲突（第 1 章第 8 节的数格子法）。

### 第 4 步：寄存器 tile 与 Tensor Core（第 3/4 章）

```text
现象:  70% 但 SM 利用率不高——很多时间在等 shared 取数
证据:  Warp State 显示 shared 访问是主要 stall 来源
改动:  每线程算 8×8 输出 tile(64 个累加器留寄存器), 用 mma 指令
收益:  70% → 80%
```

手算对照：累加器进寄存器后，shared 只做一次取数喂多次 FMA；mma.m16n8k16 一条指令 = 2048 MAC（第 4 章 4.1 节）——**从 CUDA core 换成 Tensor Core 是 80% 以后的主要动力**。

### 第 5 步：寄存器压力与 occupancy 平衡（第 3 章第 4 节）

```text
现象:  80% 后把 tile 加大到 16×16 反而变慢
证据:  ptxas -v: 每线程寄存器 168 个 → occupancy 掉到 25%, 且 spill 512 B
改动:  回到 8×8 tile, 或用 __launch_bounds__ 压预算后对比
收益:  回退保住 80%; 换 8×4 tile 平衡后 83%
```

手算对照：128 寄存器/线程 × 256 线程 = 2 blocks → 25% occupancy（第 3 章例 2 的账）。**这步的教训：更大的 tile 不是免费午餐**——寄存器账必须在改之前先算。

### 第 6 步：软件流水（第 5 章第 7 节）

```text
现象:  83% 后仍有"取数等待"
证据:  Nsight Systems 时间线上 shared 载入与计算没有重叠
改动:  num_stages=4 的双缓冲流水(加载下一 tile 与计算当前 tile 并行)
收益:  83% → 85%
```

手算对照：stages=4 × 32KB/tile = 128 KB shared（第 5 章第 7 节的账）——还在 164 KB 上限内，所以流水能成立；stages 再加就触顶。

## 4. 六步的总账

| 步 | 改动 | 收益 | 对应的课内账 |
|---|---|---|---|
| 1 | 合并访问 | 30→45% | 事务数手算（01·7） |
| 2 | shared 分块 | 45→62% | 算术强度/roofline（04·3） |
| 3 | bank padding | 62→70% | 数格子（01·8） |
| 4 | 寄存器 tile + mma | 70→80% | mma 形状账（04·4.1） |
| 5 | 平衡寄存器/occupancy | 80→83% | occupancy 公式（03·4） |
| 6 | 软件流水 | 83→85% | stages shared 账（05·7） |

三条方法论总结：

1. **证据先行**：每一步的"现象"都是 profiler/报告里的具体数字，不是感觉；
2. **一次一个变量**：每步改完立刻测，收益归属清楚；
3. **手算在前**：第 3、5 步的"回退"靠的是提前算 occupancy/冲突——**先算账的优化才不浪费一周**。

## 5. 常见错误与归因

| 现象 | 根因 | 修正 |
|---|---|---|
| 优化后比基线还慢 | 一次改了多个变量，归因失效 | 回到上一步，逐个重放 |
| 大 tile 反而不快 | 寄存器/spill/occupancy 没先算 | 第 5 步的账：先算再改 |
| profiler 显示"没有瓶颈" | 测的是单次运行/没 warmup | 第 7 章六步协议 |
| 每一步都"应该快"但没快 | 证据是猜的不是测的 | 回到 ncu 的事务数/stall 报告 |
