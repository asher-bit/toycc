# 教材写作与维护规范

这份规范用于保证后续新增章节仍然像一本教材，而不是不断增长的百科目录。

## 1. 每章只回答一个主问题

标题应该能改写成一个问题，例如：

- “为什么需要 TIR？”
- “一个 Pass 如何证明自己的变换是合法的？”
- “一个 CUDA kernel 为什么会被寄存器限制？”

如果一章同时讲五个互不依赖的主题，应拆成专题或放到参考资料中。

## 2. 固定的叙事顺序

推荐每章使用下面的结构：

```text
本章目标
  → 工作中的问题
  → 最小例子
  → 核心概念
  → toycc/真实源码
  → 实验或观察
  → 常见错误
  → 章末检查点
  → 扩展阅读
```

“扩展阅读”必须放在主线之后，并用一两句话说明它和主线的关系。不要在正文中间突然插入一段与当前例子无关的术语列表。

## 3. 每个概念都要落到一个对象上

第一次出现术语时，按“中文名（英文名）+ 一句话定义 + 对应对象”的方式介绍：

> 基本块（Basic Block）是一段只有一个入口、以终结指令结束的指令序列。在代码中，它对应 `BasicBlock` 对象。

后面优先使用同一个称呼，不要在“基本块、块、BB、block”之间无说明地来回切换。

## 4. 代码片段必须说明身份

每段代码都要标注它属于哪一种：

- **可运行代码**：给出文件路径、命令和预期输出；
- **源码摘录**：给出仓库、文件和作用，不暗示可以直接编译；
- **概念伪代码**：明确写“示意代码”，避免读者拿去运行；
- **输入/输出样例**：说明它来自哪一步。

特别是 CUDA、PTX、LLVM、MLIR 代码，要同时注明版本或目标架构可能影响语法和命令。

## 5. 一段只做一件事

一个自然段尽量只完成以下一种任务：解释、举例、比较、推导或总结。不要在同一段里同时定义术语、评价性能、跳到另一个项目，再回到当前代码。

常用的过渡句包括：

- “有了这个对象，下一步才能解释……”
- “上面的直觉在 toycc 中对应……”
- “这个例子还没有回答性能问题，下面继续看……”
- “到这里，我们只证明了正确性；下一节再讨论速度。”

## 6. 区分事实、经验和近似

- 项目 API、目录和命令是事实，应给出版本边界；
- “通常”“常见”“工程上建议”属于经验，应避免写成绝对规律；
- 公式和架构数字是近似，应说明假设条件；
- “能跑通”不等于“性能好”， “性能好”也不等于“覆盖完整”。

## 7. 每章必须有可检查的产出

章末至少给出一种检查方式：

- 能否画出一条数据流或调用链；
- 能否手算一个小例子；
- 能否运行一个命令并解释输出；
- 能否修改一处代码并写测试；
- 能否对一个错误现象提出分层排查顺序。

“看懂了”“掌握了”不能单独作为验收标准。

## 9. 交叉引用不进入正文句子

正文句子应该自包含：读完这一段，不需要去翻别的课。

- 允许：每课底部的"导航"行、"对照"表格、"扩展阅读"区块的指引、"前置知识"标记。
- 不允许：在解释的句子中间夹"（第 X 课）""第 X 课讲过""见第 X 课"。需要用到前文的结论时，用一两句话把结论重述一遍，而不是指路。

## 10. 比喻克制，数字优先

- 一个概念最多用一处比喻（"账本""回头客"这类），且比喻出现后要立刻落到数字或代码上。
- 优先用可手算的数字、可运行的指令说明道理；形容词（"暴跌""白拉"）只用在结论处，不代替推导。

## 11. 维护时优先修正的信号

看到下面的信号，应优先重写，而不是继续追加内容：

- 同一个术语在相邻章节有不同定义；
- 一章出现多个“深层拓展”但主线没有收束；
- “下一步”链接跳到不相干的知识域；
- 一个表格列出很多名词，却没有前后因果；
- 代码示例没有输入、输出、版本或可运行说明；
- 章节结尾只说“很重要”，没有给出练习或检查；
- 正文句子中频繁出现“（第 X 课）”式指路；
- 同一概念反复使用比喻而没有数字支撑。
