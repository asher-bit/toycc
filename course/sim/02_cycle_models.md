# 模拟器专题 第 2 章：周期模型的设计——从五级流水到 GPU warp 调度器

## 1. 本章目标

- 能画出周期模拟器的总体架构（功能核 + 时序模型分离），并解释"功能优先"设计为什么必要；

- 能说清周期模型的校准与验证链条（功能差分 → 周期对齐 → 悲观校准）。

前置：第 1 章的解析式模型（本章是它的"逐周期版"）；第 27 课第 3.2 节的手算；toyisa 的 ISA 与 `cycle.py`。本章的手算全部可以在 `python -m toyisa.demo` 第 4 节验证。

## 2. 总体架构：功能核与时序模型的分离

周期模拟器的标准架构是**两部分解耦**：

```text
功能核(functional core):  只算语义 —— 寄存器值、访存地址、分支方向
时序模型(timing model):    只算时间 —— 每周期谁在哪个阶段、为什么等
```

**为什么必须分离**：时序模型需要"程序接下来走哪条路"才能推演（分支方向、跳转目标、访存地址），而这些都是功能核的产物。真实项目叫 **functional-first 设计**——先跑通语义，再往上叠时序。`toyisa/cycle.py` 就是按这个架构写的：指令的发射周期由计分板决定（时序），但分支是否 taken、ld/st 的地址用"当前提交的寄存器值"算（功能）。

分离的直接好处：**功能验证与性能验证互相独立**——第 27 课的差分测试只测功能核，周期对齐只测时序模型，两个 bug 不会混在一起。

## 3. 五级流水：一个逐周期状态机

`cycle.py` 的流水线（对照其代码注释）：

```text
IF(取指) → ID(译码/读寄存器) → EX(执行) → MEM(访存) → WB(写回)
```

每周期，每条在途指令向下一级推进一格；各级之间的等待产生 **stall**。三种冒险（hazard）各有一个处理机制：

### 3.1 结构冒险（structural hazard）

两个指令同时要同一个硬件单元。`cycle.py` 约定**单发射**（每周期最多 1 条），所以结构冒险被"上一条发射 +1"隐式解决。真实设计里它是**发射宽度（issue width）**参数——改成 2 就是双发射，改 4 就是四发射，周期数大致除以对应倍数。

### 3.2 数据冒险（data hazard）——计分板 vs 前向

生产者还没写回，消费者就要读。两种设计：

```text
无前向(cycle.py 的约定): 消费者必须等生产者 WB 完成
  movi r1,1 → add r1,r1,r1: 停 3 拍(手算: add 被推到 c4)

有前向(forwarding): 结果算出来就旁路给消费者, 不等 WB
  同例: 只停 1 拍(EX 结果在下一拍的 ID 直接用)
```

**计分板（scoreboard）**是记录"哪个寄存器什么时候就绪"的表——`cycle.py` 里的 `ready[]` 数组就是它。前向网络是真实 CPU 的标准配置（GPU 也有），代价是旁路比较器与连线；教学模型选无前向，因为它**stall 更明显、更好手算**。给 `cycle.py` 加前向是延伸任务（stall 从 3 拍降到 1 拍，直接观察 IPC 变化）。

### 3.3 控制冒险（control hazard）——分支冲刷

分支在 ID 解析出来之前，IF 已经取了下一句。跳转发生 → **冲刷（flush）**刚取的那条 → 1 拍惩罚。`cycle.py` 的手算：`beq(r1==r2) → nop` 时 nop 被推到 c2，branch_stall +1。更深的流水线惩罚更大（所以真实硬件有分支预测器——那是"提前猜方向"来省这 1 拍的机器）。

## 4. 三组进阶设计取舍

### 4.1 顺序 vs 乱序

顺序（in-order，`cycle.py` 的模型）：指令按程序序发射，一条卡住后面全卡。乱序（out-of-order）：靠**保留站（reservation station）**暂存已译码指令、**重排序缓冲（ROB）**按程序序提交——独立的指令可以越过卡住的那条先算。乱序的核心代价：硬件结构复杂一个量级，**功耗与面积账**在自研芯片上是要上评审的。教学模型选顺序，因为"一条卡住全卡"的 stall 账最好懂。

### 4.2 延迟 vs 吞吐

每个功能单元有两个数：**延迟（latency）**——一条指令从发射到结果可用的周期数（FMA 约 4 拍）；**吞吐（throughput）**——每多少周期能再吃一条同类指令（FMA 每 2 拍 1 条时，吞吐 = 0.5 条/拍）。两者分离的意义：

```text
延迟决定依赖链的长度(关键路径账, 第 1 章 3.2 节)
吞吐决定无依赖时的发射密度(带宽账)
```

`cycle.py` 为简单把两者合一（每单元每周期 1 条、延迟 4 拍）；真实模型把它们拆成参数表——**参数化 = 一行配置改延迟/吞吐**。

### 4.3 存储层次建模

访存不是固定 4 拍：命中缓存一个数，缺失又是另一个数。建模层级：

```text
L1 命中 → 短延迟;  L1 缺失 → L2 → ... → DRAM 长延迟
带宽限制 → 每周期只能服务 N 个字节的访存请求(排队)
```

`cycle.py` 的 `MEM_LATENCY` 是"固定 4 拍"的最简版；延伸任务"命中 4 拍/缺失 20 拍"就是缓存模型的雏形。真实 GPU 模型还要加**事务粒度**（第 1 章合并访问的 32B sector——一次 warp 访存拆成几个事务，直接进带宽账）。

## 5. GPU 周期模型比 CPU 多出来的四样

GPU 的周期模型在 CPU 五级流水之上，多四类建模对象：

| 对象 | 建模什么 | 对应课内账 |
|---|---|---|
| warp 调度器 | 每周期每个调度器从"eligible warp"里挑一个发射（有就绪指令、无 stall） | 第 21 课 occupancy：warp 越多，越有得挑 |
| stall 原因分类 | 每个 warp 为什么没发射：等内存（long scoreboard）/等同步（barrier）/等固定延迟 | 第 7 章 Warp State 统计 |
| 访存事务模型 | 一次 warp 访存 = 几个 32B sector → 内存子系统按事务服务 | 第 1 章合并访问 |
| 寄存器 bank / 共享内存 | 读寄存器与 shared 的 bank 冲突拍数 | 第 1 章 bank conflict 数格子 |

GPU 模型的正确性标准也分两层：**功能层**（第 27 课差分测试）和**周期层**（stall 分类的分布对齐真实 profiler）——后者就是"周期模型的悲观校准"在 GPU 上的形态：模型的 stall 分布必须与 Nsight 报告同形状，否则编译器团队拿到的调优信号是假的。

## 6. 参数化、校准与验证链条

周期模型的完整生命周期：

```text
① 参数化: 发射宽度/前向/延迟表/缓存配置 → 一份参数文件 = 一款芯片
② 功能验证: 与参考执行器差分(第 27 课) —— 只管"对不对"
③ 周期对齐: 与 RTL 仿真或老芯片实测对齐 —— 只管"准不准"
④ 悲观校准: 系统性略悲观, 误差阈值团队定(第 1 章第 6 节的连锁反应)
⑤ 性能回归: 参数/微架构改动前后, 同一批 benchmark 的周期数进 CI 对比
```

链条上任何一环断开，下游就会拿错数据做决策：功能错 → 优化全错；周期太乐观 → autotune 数据库作废；没有回归 → 参数改动悄悄引入性能回退。

## 7. 与 toyisa/cycle.py 的对照表

| 设计点 | cycle.py 的实现 | 真实硬件的对应 |
|---|---|---|
| 功能/时序分离 | 功能状态 + 计分板并行推进 | functional-first 架构 |
| 结构冒险 | 单发射（prev_issue+1） | 发射宽度参数 |
| 数据冒险 | 计分板 `ready[]`，无前向 | 保留站/ROB + 前向网络 |
| 访存延迟 | `MEM_LATENCY` 固定 4 拍 | 缓存命中/缺失分级 + 带宽 |
| 控制冒险 | 分支 ID 解析，冲刷 1 条 | 分支预测器 |
| stall 观测 | data/mem/branch 三类计数 | profiler 的 Warp State / stall 分类 |

## 8. 常见错误与归因

| 现象 | 根因 | 修正 |
|---|---|---|
| 模型比实测快很多 | 漏建了资源冲突（端口争用/带宽）或没悲观校准 | 第 6 节链条逐环查 |
| 周期数手算与模型对不上 | 前向/冲刷/填充的约定不一致 | 先对齐模型约定再手算 |
| 功能对但周期完全不可信 | 时序模型与功能核状态不同步 | 检查功能优先设计是否被破坏 |
| 改参数后模型行为怪异 | 参数之间有隐含耦合（如缓存与带宽共用队列） | 参数化时画出资源依赖图 |
