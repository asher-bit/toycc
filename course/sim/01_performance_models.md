# 模拟器专题 第 1 章：性能模型的设计——解析式、trace 重放与代价模型

## 1. 本章目标

- 能说出性能模型与周期模型的本质区别（"估整体" vs "逐周期推演"）；
- 能按"特征提取 → 公式/系数 → 输出"三步设计一个解析式性能模型，并手算一个 toyisa 程序的估计时间；
- 能解释 trace 重放模型与机器学习代价模型各自解决解析式的什么缺陷；
- 能说清"模型参数化"与"悲观校准"为什么是性能模型的生命线。

前置：第 27 课第 3 节的两种路线概览；roofline（第 19 课）是本章解析式模型的著名特例。手算部分使用 toyisa 的约定（`cycle.py` 的流水线参数）。

## 2. 性能模型解决什么问题

性能模型回答"这段程序大概跑多久"，**不保证逐周期正确**。它的三个真实用途：

```text
1. 架构探索: 还没流片, 改一个参数(缓存大小/发射宽度)值不值得 → 快速扫一遍
2. 调度决策: 编译器在几十种调度里选一个 → 每个都跑周期模拟太慢, 先用模型剪枝
3. autotune 代价模型: 搜索空间里"没测过的配置"预测快慢(第 13 课的 CostModel)
```

三个用途的共同要求：**快**（毫秒到微秒级）和**相对排序准**（A 比 B 快即可，绝对值可以糙）。这就是它和周期模型的分工边界。

## 3. 路线一：解析式模型——特征提取 + 公式

### 3.1 设计逻辑

```text
输入程序
  → ① 特征提取: 指令混合 / 访存字节 / 依赖链深度 / 分支率
  → ② 套公式或经验系数(每硬件一组参数)
  → ③ 输出: 时间估计(或瓶颈归因)
```

**特征提取是灵魂**。一个 matmul 的特征不是"它叫 matmul"，而是：

```text
指令混合:  FMA 占 ~90%, ld/st 占 ~8%
访存字节:  每 tile 读 A/B 各 TM×TK×2B + 写 C
依赖链:    tile 内累加器串行深度 × FMA 延迟
分支率:    ~0(内层无分支)
```

### 3.2 手算：一个 toyisa 程序的解析式估计

程序（对照 toyisa 语法）：

```text
movi r1, 1
add  r2, r1, r1      ← 依赖 r1
add  r3, r2, r2      ← 依赖 r2
halt
```

用解析式模型估：指令数 4，其中 ALU 2 条、其他 2 条；**依赖链深度 2**（两条 add 串行）。假设每周期最多发射 1 条、ALU 延迟 4 拍（`cycle.py` 的约定）：

```text
时间 ≈ max(指令数 / 发射宽度, 依赖链 × 关键延迟)
     = max(4 / 1, 2 × 4) = 8
```

对照逐周期模拟的真实答案（9 拍）：解析式给了 8，**差 1 拍是因为流水线填充/排空没算**。这正是两类模型的经典关系：解析式抓"主导项"（这里依赖链），周期模型给精确值。加 1 拍填充修正后两者一致——**好的解析式模型 = 正确的特征 + 明确标注的修正项**。

### 3.3 解析式模型的三个变体

| 变体 | 公式形状 | 例子 |
|---|---|---|
| 指令混合 × CPI | `时间 = Σ(指令数_i × CPI_i) / 发射宽度` | 老式 CPU 估算法 |
| 带宽/算力墙 | `时间 = max(算力时间, 带宽时间)` | roofline（第 19 课） |
| 关键路径 | `时间 = 依赖链 × 关键延迟` | 上面的手算 |

**组合用法**：三者取 max，就是"瓶颈是发射、带宽还是依赖"的粗粒度归因——与第 23 课"健康度"的排查逻辑同构。

## 4. 路线二：trace 重放模型

解析式的软肋是**看不见程序的具体行为**（哪个分支走了、访问序列长什么样）。trace 重放的思路：

```text
① 用功能模拟器(ISS)跑一遍程序, 记录动态指令流 + 访存地址序列(trace)
② 重放 trace: 给每条指令叠加延迟, 模拟资源占用, 不改功能状态
③ 输出: 时间估计 + 瓶颈统计
```

两个真实权衡：**trace 体积**（十亿条指令的 trace 就是十亿行记录，通常要压缩或抽样式截断）；**参数不敏感**（trace 是"某一次运行"的记录，改了硬件参数后程序行为会变，trace 却不变——所以架构探索用它要小心）。折中是**采样**：只重放有代表性的片段。

## 5. 路线三：机器学习代价模型

解析式的系数靠人拍，trace 又太重。第三条路：**把特征喂给学出来的函数**。

```text
训练:  (特征向量, 实测时间) 成对样本 → 训练模型(如梯度提升树)
预测:  新配置 → 特征向量 → 模型 → 时间估计
```

这正是第 13 课 meta_schedule 的 CostModel：SearchSpace 采样一批配置 → Runner 实测 → 特征（tile 大小、访存量、向量化宽度……）+ 时间喂给模型 → 用模型预测没测过的配置。**模型的质量上限 = 特征的信息量 + 训练样本的覆盖**——特征里没有"bank conflict 程度"，模型就永远学不会 bank conflict 的影响。设计代价模型的第一件事不是选算法，是列特征清单。

## 6. 参数化与悲观校准：模型的生命线

性能模型的所有公式都挂在一组**硬件参数**上（带宽、延迟、发射宽度、缓存大小）。参数化的意义：

```text
同一套模型代码 + 两份参数文件 = 两款芯片的模型
改架构探索问题 = 改参数, 不改代码
```

**悲观校准**（第 27 课扩展阅读 B 的账在这里展开）：模型通常偏乐观——它看不见真实硬件里那些"想不到的慢"（资源冲突的边角、功耗墙降频、冷启动）。乐观模型的连锁反应：

```text
模型说 90% 占用率 → 编译器团队按它调参 → autotune 数据库全按它建
→ 流片实测只有 60% → 数据库作废, 全部重跑
```

校准做法：拿**已流片的老芯片**或公开数据做基准，把模型误差调成"系统性略悲观"，误差阈值由团队定（如 ±5%），关键原则是**同一基准、同口径对比**。

## 7. 真实工具对照

- **roofline**：解析式模型的教科书（第 19 课的完整推导）；
- **llvm-mca**（LLVM 机器码分析器）：解析式 + 指令流水线建模的真实工具——喂一段汇编，输出每条指令的调度周期与端口占用，正是 3.2 节手算的工业版；
- **TVM CostModel**：第 5 节机器学习路线的生产实现；
- **toyisa/cycle.py 的 stall 分类**：周期模型的输出，被解析式模型拿来当"特征真值"。

## 8. 常见错误与归因

| 现象 | 根因 | 修正 |
|---|---|---|
| 模型排序都反了 | 特征没抓到真实瓶颈（漏了访存/依赖） | 先做瓶颈归因再选特征 |
| 预测值系统性偏高 | 模型乐观，没做悲观校准 | 老芯片基准标定误差 |
| 换配置后模型失效 | 特征/系数对旧参数过拟合 | 参数化 + 重新校准 |
| autotune 选出的配置很差 | 代价模型训练样本没覆盖该区域 | 检查采样分布与特征清单 |
