## 1. 先学判断"瓶颈在哪"：Roofline 模型

### 1.1 一句话

**Roofline**：判断一个 kernel 是"受计算限制"还是"受带宽限制"。

```
性能上限 = min( 峰值算力(FLOP/s), 峰值带宽(Byte/s) × 计算强度 )
```

其中 **计算强度（arithmetic intensity）** = 做了多少次计算 / 搬了多少字节。

### 1.2 画出来（roofline 图）

```
性能(FLOP/s)
   ▲  ┌─────────────────── 算力屋顶(水平线)
   │  │
   │  │        ▲ 斜率 = 带宽
   │  │     ▲
   │  └────▲─────────────────────────→ 计算强度(FLOP/Byte)
   │      ↑
   │   带宽受限区      计算受限区
```

- **计算强度低**（搬得多、算得少）→ 撞**带宽墙**（横轴）
- **计算强度高**（算得多、搬得少）→ 撞**算力墙**（纵轴）

### 1.3 手算判断我们的 matmul

32×32 matmul：
- 计算量 = `2 × 32³ = 65536` FLOP
- 搬运量（读 A+B、写 C）= `3 × 32² = 3072` 元素 × 4 字节 = 12288 字节
- 计算强度 = 65536 / 12288 ≈ **5.3 FLOP/Byte**

假设峰值算力 100 GFLOP/s、带宽 10 GB/s：
```
带宽墙: 10 × 5.3 = 53 GFLOP/s  < 100(算力墙)
→ 这是"带宽受限"的!
→ 优化方向: 减少搬运(分块/复用) 而不是 加算力
```

**这就是为什么调度（第 11 课分块）对 matmul 有用**——它把计算强度
往上推，从带宽受限区挪向算力受限区。

> **roofline 的实战价值**：讨论性能时，"这 kernel 是 compute-bound
> 还是 memory-bound"一句话就能定方向。这就是工程师判断力的来源。

> **原理深挖：为什么上限是"两个墙取小"，而不是别的公式？**
>
> roofline 的本质是**一个超级简单的经济模型**：
> 你有一段计算要完成，它要做 `F` 次运算、搬 `B` 字节。
>
> - 如果算力是瓶颈：时间 = `F / 峰值算力`
> - 如果带宽是瓶颈：时间 = `B / 峰值带宽`
> - **真正的时间 = max(两者)**——因为这两个资源同时忙，谁更慢谁做主。
>
> `min(算力墙, 带宽墙×强度)` 就是 `max(F/算力, B/带宽)` 翻个面。
> 强度 `I = F/B` 把它写成 `min(算力, 带宽×I)`，让你一眼看出
> "往哪个方向推有收益"：
>
> - 算力墙下：`带宽×I < 算力` → 加 `I`（少搬数据）**立竿见影**
> - 算力墙上方：`带宽×I ≥ 算力` → 加 `I` 也白搭，得加算力（换硬件）
>
> **它最好用的地方不是算得准，而是"把优化讨论变成确定性问题"**：
> 你说"这个 kernel 慢"，同事第一反应就是问"roofline 显示受啥限制"。
> 这个公式就是你们讨论的共同语言——也是你入职后每天都要用的判断工具。

## 2. 科学测速的坑（benchmark 方法论）

"这个优化后快 2 倍"——别急着信，先检查测量是否科学。常见的坑：

| 坑 | 正确做法 |
|---|---|
| 冷启动（第一次跑慢） | **warmup**（先跑几次热起来） |
| 噪声（中断/调度抖动） | 跑多次取**中位数**（不用平均，平均被最大值拉偏） |
| 编译器优化 | 确认对比的是"同样的优化级别" |
| CPU 频率波动 | 尽量锁频或多次测量 |
| 没算传输 | 只测"计算"还是"含搬数据"要说明 |
| 比错了量 | 延迟（latency）vs 吞吐（throughput）要分清 |

**一句话方法论**：
```
warmup 几次 → 测 N 次取中位数 → 报告 (中位数, 标准差) → 注明测的是什么
```

TVM/ONNX 里计时：
```python
import time
t = time.perf_counter()
vm["main"](x)
dt = (time.perf_counter() - t) * 1000   # ms
```

**meta_schedule 的 Runner**（第 13 课）内部就是这么做的：
多次测量、取中位数、算标准差——保证 autotune 的结论可信。

## 3. 卷积怎么被加速：im2col（卷积 → GEMM）

### 3.1 核心思想

卷积很难优化（多维、滑窗）。但**矩阵乘法（GEMM）是极致优化的**。
**im2col** 把卷积转成矩阵乘法：

```
输入 x (1, C, H, W) → 拆成滑动窗口, 重排成矩阵 X_col
                     形状: (C*KH*KW, 输出位置数)
权重 w (OC, C, KH, KW) → 重排成矩阵 W_col
                     形状: (OC, C*KH*KW)
卷积结果 = W_col @ X_col
```

### 3.2 例子

输入 1×1×3×3，kernel 2×2，stride 1，输出 2×2 位置：

```
X_col (4, 4):  每个输出位置对应一个 2×2 窗口(4 个值), 共 4 个位置
W_col (1, 4):  权重展平成一行
结果 (1, 4) = W_col @ X_col   ← 一个 matmul!
```

> **手算：拿真实数字走一遍 im2col**
>
> 输入（1 通道、3×3，仅 1 个 channel）：
> ```
> x = [ 1 2 3
>       4 5 6
>       7 8 9 ]
> 权重(1 个输出通道)  w = [ 1 0
>                           0 -1 ]
> ```
> 卷积在 4 个位置滑窗 → 每个位置取 2×2 窗口，**展平成一列**：
> ```
> 输出(0,0): 窗口 [1 2; 4 5]  → 列 [1, 2, 4, 5]
> 输出(0,1): 窗口 [2 3; 5 6]  → 列 [2, 3, 5, 6]
> 输出(1,0): 窗口 [4 5; 7 8]  → 列 [4, 5, 7, 8]
> 输出(1,1): 窗口 [5 6; 8 9]  → 列 [5, 6, 8, 9]
>
>      ┌ 1  2  4  5 ┐
> Xcol=│ 2  3  5  6 │     Wcol = [1, 0, 0, -1]  (权重按 [tl,tr,bl,br] 展平)
>      │ 4  5  7  8 │
>      └ 5  6  8  9 ┘
> ```
> 验证单个输出：`Wcol · 第1列 = 1×1 + 0×2 + 0×4 + (-1)×5 = -4`
> 手算直接卷积：(0,0) 位置 `1×1 + 2×0 + 4×0 + 5×(-1) = -4` ✓ 一致。
>
> **看两个工程含义**：
> 1. **"重复拷贝"从哪来**：`5` 出现在第 1 列和第 2 列——滑窗重叠
>    让同一份数据被复制多份（本例复制到 4 个窗口）。所以 im2col
>    是"用内存换 GEMM"。第 17 课说 legalize 有代价——这就是代价。
> 2. **为什么值得**：GEMM 的极致优化（第 5 节微内核）按行/列连续
>    访问，而卷积的窗口访问是跳着的。转 GEMM 后，CPU/GPU 的
>    SIMD/Tensor Core 才能全速发挥。**im2col 的本质是"把不规则访问
>    变成规则访问"**——这句话到第 24 课自研后端时还会用到。

### 3.3 代价与权衡

- **代价**：X_col 是**重复拷贝**（滑动窗口重叠 → 数据多存几份）
- **收益**：能直接复用 GEMM 的全部优化（分块、向量化、Tensor Core）

**实际工程**：很多库（cuDNN、oneDNN）用小窗口时走 Winograd，
大窗口或特殊场景走 im2col+GEMM。编译器（如 TVM 的 topi）也会
提供"conv → GEMM"的下降选项。

## 4. Winograd：用"更多加法"换"更少乘法"

### 4.1 思想

对于小卷积核（3×3），Winograd 用**变换域**减少乘法次数。

直接卷积 3×3 对 2×2 输出：每个输出 9 次乘法，4 个输出 = 36 次乘法。
Winograd F(2,3) 只需要 **16 次乘法**（省 56%）。

```
1. 输入变换  B^T d B     (加法/加减法为主)
2. 元素相乘  GgG^T ⊙ ... (16 次乘法, 这是关键)
3. 输出变换  A^T ... A
```

> **手算：F(2,3) 到底省在哪？（一维版 F(2,3) 就能看清机制）**
>
> 一维卷积：2 个输出，每个要 3 次乘加 → 6 次乘法。看 Winograd 怎么做：
>
> ```
> 输入 d0 d1 d2 d3, 核 g0 g1 g2（padding 后）
> 直接法: y0 = d0g0+d1g1+d2g2      y1 = d1g0+d2g1+d3g2      （6 乘 4 加）
>
> Winograd:
>   m1 = (d0 - d2) * g0
>   m2 = (d1 + d2) * (g0+g1+g2)/2
>   m3 = (d2 - d1) * (g0-g1+g2)/2
>   m4 = (d1 - d3) * g2                    （4 乘）
>   y0 = m1 + m2 + m3
>   y1 = m2 - m3 - m4                      （加减法组装）
> ```
>
> 展开核对 y0 = d0g0 + d1g1 + d2g2（恒等式成立——这就是它的"证明"）。
> 注意：**乘法从 6 降到 4，加法则从 4 涨到 8 左右**。
>
> **为什么划算**？在硬件上，乘加单元（FMA）是两个操作一个周期，
> 但"加法的门数/功耗成本远低于乘法"。更关键的是：**代价是加法、收益是
> 乘法——而乘法省下来意味着你可以在同样的 FMA 吞吐上做更多**。
> 于是 3×3 卷积（ResNet 主力）直接获得 1.5~2 倍收益。
>
> **工业界的取舍**：cuDNN 在 3×3 上默认 Winograd（除非数据分布糟糕），
> 1×1 永远是 GEMM。编译器要做的是**按 kernel 尺寸自动选择**——这就是
> 第 17 课"下降时机"和 topi 模板在干的事。

**关键**：乘法省了，但加法和变换开销多了。**只有当变换开销
（加法）便宜、乘法贵**时才划算——这正是硬件特点（加法不占乘加单元）。

### 4.2 什么时候用

- 3×3 小卷积：Winograd 是大赢家（ResNet 的卷积几乎全 3×3）
- 大卷积核：变换开销过大，不划算
- 1×1 卷积 = matmul，直接用 GEMM

> 编译器（TVM topi 的 `conv2d_winograd`）会在特定 kernel 尺寸下
> 自动选 Winograd。这就是"算子模板"存在的原因。

## 5. GEMM 微内核：极致优化长什么样

矩阵乘法是最优化的算子。经典"微内核（micro-kernel）"结构：

```
外层: 分块(tile)  —— 缓存分块 + 寄存器分块
  中:  循环重排  —— 让数据连续访问
  内:  寄存器累加 —— 一次算 6×8 个输出(48 个累加器)
  向量化        —— SIMD 乘加
  双缓冲/预取   —— 隐藏内存延迟
```

**寄存器分块**：内层一次维护 6×8=48 个累加值在**寄存器**里，
对每个 k，读 6 行 A + 8 列 B，做 48 次乘加——最大化计算/搬运比。
这就是第 15 课"寄存器压力"的正面应用：**多占寄存器来减少访存**。

**为什么 GEMM 值得极致优化**：
- 几乎所有模型 90% 算力在 GEMM/conv（conv 也能转 GEMM）
- 1% 的 GEMM 性能提升 = 全模型 1% 提升
- NVIDIA cuBLAS / CUTLASS、oneDNN 就是干这个的（TVM 也集成 CUTLASS）

## 6. 这些技术怎么"进编译器"

| 技术 | 在编译器的位置 |
|---|---|
| roofline | 你分析"该优化啥"时的判断框架 |
| 分块/重排/向量化 | TIR 调度（第 11 课） |
| im2col | conv → GEMM 的**下降**（第 17 课 legalize 的一种） |
| Winograd | 算子的**模板实现**（topi 里选） |
| GEMM 微内核 | 手写/库/autotune 生成的 kernel（第 13 课） |
| 融合 | 省带宽（第 3 课），把强度往上推 |

**关键认知**：这些不是互斥选项，而是**由编译器在编译期组合**：
下降 → 选模板 → 调度 → autotune，层层叠加。

## 7. 课后答疑

**Q：我优化一个 kernel 后，怎么确认真变快了？**
A：按第 2 节方法论（warmup + 中位数 + 同条件对比），
再用 roofline 判断是否接近理论峰值。接近 = 到顶了，别白费力气。

**Q：计算强度怎么快速算？**
A：`总 FLOPs / 总搬运字节`。搬运 = 读所有输入 + 写所有输出
（如果重复使用中间数据，按"实际访存次数"算更准）。

**Q：Winograd 会损失精度吗？**
A：会一点（数值稳定性略差）。大数抵消时误差可能放大。
所以工业实现要验证精度，必要时回退直接卷积。

**Q：我是做编译器框架的，也要懂这些算子优化吗？**
A：**要懂原理**（能判断哪个优化方向、能读懂 topi 代码），
不必亲手实现微内核（那是库/autotune 的活）。理解"有哪些技术、
什么时候用"就够了。

## 8. 本课小结

- **Roofline**：性能上限 = min(算力墙, 带宽墙 × 计算强度)；
  先判断 memory-bound 还是 compute-bound，再定优化方向
- **Benchmark 方法论**：warmup + 中位数 + 同条件 + 区分延迟/吞吐
- **im2col**：conv → GEMM（代价是重复拷贝，收益是复用 GEMM 优化）
- **Winograd**：小卷积用"加法换乘法"，省 50%+ 乘法
- **GEMM 微内核**：分块 + 寄存器累加 + 向量化 = 极致性能
- 这些技术在编译器里 = 下降 + 模板 + 调度 + autotune 的组合

## 扩展阅读：性能工程的三个原则

### A. roofline 是"上限"，不是"目标"

roofline 告诉你"这个 kernel 最快能到多少"。但实际中你很难达到——
有分支、有同步、有 cache miss。**roofline 的价值不是"达标"，是"判断要不要继续优化"**：
如果你已经到 80% 峰值，就别浪费时间了。

### B. benchmark 的"比较条件"比数字重要

你测出 kernel 是 5ms，别人测是 3ms——**谁的数字有意义？取决于条件**：
batch 多大？warmup 够不够？有没有算数据传输时间？
**报告性能数字时，必须同时报告"测量条件"**——否则数字没有可比性。

### C. 算子加速的"投入产出比"

im2col 省时间但费内存，Winograd 省乘法但代码复杂，GEMM 微内核极致但难写。
**选哪个优化，取决于"这个算子在模型里占多少时间"**。
profile 先看大头，再决定优化哪个——别在小算子上浪费时间。
